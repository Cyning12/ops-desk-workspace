## 二、关键优势（附证据）

1. **层间职责切分准确，且六轮自洽**
   Q1 主动把「裁剪可见集」与「选定执行哪一个」拆开，明确 Gateway 不做语义路由；Q3 收尾选「只留一道闸」时选的也是副作用边界；Q5 砍掉「本体做选人器」的理由正是「与现网 Mode A 打架」。同一套判断标准贯穿全场。

2. **按失败模式的爆炸半径做决策，而非按覆盖面**
   Q3：「缺 args 精校最多是调不成，不会在未审批时改价」。
   Q4：对「已有副作用后失败」按分布式事务 in-doubt 处理——超时无收据先查票据、禁止直接再写；收出原则「**副作用以收据为真，不以模型叙述为真**」。

3. **用构造性隔离替代脆弱校验**
   Q6 把不变量从「先查对象属于谁再比」换成「Principal 真源 + 查询谓词下推」，并给出鉴权缓存纪律：「命中物化旧值**只能导致多拒，不能导致错放行**」。

4. **把方案做成可证伪的假设**
   Q5 给出负样本驱动主指标、保护检索基线不被重算、加防误伤阈值，并**预置证伪条件与对照组**（vs「仅 Policy high-risk」），明说「若三个月建不出稳定负样本集，这套本体不值得做」。

5. **技术诚实**
   Q1/Q3 两处「这里没有」都直说，并补上「当时为什么可以没有」；Q6 主动判自己设计「顺序不对」，并指出自己 Q2 那句「错 input 最多查空」是**需要闸才成立的结论**。

## 三、系统性缺口

### 缺口 A：强制性机制缺位 —— 同一个模式，你批评过一次又犯了一次
- Q2 你批评「硬编码 `CANDIDATE_CAPABILITY_IDS`」，主张改用授权投影；
- Q6 你的安全性完全建立在「能力执行必须带 `workspace_id = principal.workspace_id` 谓词」上，却**没给强制机制**——靠能力作者自觉写。
- **正解**：Host 从能力声明（如 `tenant_scoped=true`）解析后**强制注入谓词**；或注册时契约测试不通过即禁止 GA。**机制，不是约定。**

### 缺口 B：平台治理的反作用未评估
Q6 治理在机制上是对的（GA 门禁绑 ontology pin、同一变更单、事故归属进域 OKR、过期自动降级），但没算**域方的绕道成本**：门禁越重，域方越倾向把写能力绕出平台直连——那比本体没落更糟，你会失去可见性。需要配套的绕道检测，或降低门禁成本。

### 缺口 C：接缝处理不彻底
- **委派降权**：子能力投影必须 ⊆ 父能力投影，否则存在「父被锁死的高危能力，通过派一个拥有它的子 Agent 绕过」的间接提权；
- **Q3 × Q4 的接缝**：HITL 的一次性令牌在 Host-only 上下文里，而子 Agent 跑独立 run——令牌**如何跨 run 传递**不定死，要么审批失效、要么独立 thread 白设；
- **并发预算会计**：父总预算 → 派发时预留并锁定子预算 → 结束回收余额，余额不足则拒绝派发。

### 缺口 D：跨组织影响力未经验证
11 年同一家公司、无跳槽，平台与规范的推行经验全在单组织自建场景，且「规矩是你自己立的」。而本岗位的核心挑战恰是「把平台推给已有的团队」。Q7 的跨团队案例是真实的（AI Coding 规范推行），但结果是**部分成功**，且「若重来」只说了「更早定金样」，未触及「没证据就发文档」这个真正的顺序错误。

## 五、面试前最后 3 个动作

1. **把缺口 A 补成机制。** 准备一段 30 秒的话，说清「租户封闭谓词由 Host 强制注入，能力作者无法遗漏」——这是你整套方案最容易被追穿的一处，而你就栽在这个模式上两次。
2. **准备「跨组织推行」的第二段 STAR。** 不要再用百果园自建立规矩的场景，准备一段你真被**外部团队或上级否决**后调整策略的经历。这个岗位的失败模式不是技术不行，是推不动。
3. **带三个验证动作去反问面试官**：① 直调 Gateway 看是否仍被拦；② 在 plan 里塞 `allow_high_risk` / 异租户 `tenant_id` 看是否生效；③ 删掉 system prompt 里所有安全话术后重放负样本，看拒付率是否下降。**第三个最狠也最便宜——有闸的系统删掉 prompt 后拒付率不该变。**

## 附录：高危写能力的九道硬闸（可复用素材）

**硬闸判定标准（三条同时满足）**：① 判定输入不含模型可控字段；② 执行路径不经过模型；③ 绕过它要改代码或换凭证，而不是改 prompt。

按调用顺序：
1. 可见集裁剪（prompt 组装前）—— Host
2. Plan 解析 + allowlist 求交 + enabled / kind 检查 —— Host / Gateway
3. args_schema + 业务不变量校验（按 pin 的 version）—— Gateway / 域规则层
4. Policy 硬闸：判定输入不含模型可控字段 —— Policy PDP
5. 对象级租户授权：查询下推，不靠先查再比 —— 执行面
6. HITL 一次性令牌：绑定 args 指纹与目标对象，Host-only 存储 —— 审批服务
7. 幂等单飞（防重放）+ 写池与只读池物理分离 —— Runtime
8. 沙箱执行面：无外网 / 最小凭证 / 超时 / 审计 —— Sandbox
9. 域服务最终提交闸：不信任上游「已审批」结论 —— 域服务

**纸面 9 道，通常能坐实 4–5 道。** 最易假落地的是第 4、6 道——判定输入里一旦混进模型产出的字段，就退化成「长得像 Policy 的 prompt 校验器」。真正有重量的是第 9 道：它必须假设前面 8 道全被绕过。

**典型「未落地」形态**：prompt 里的「不要执行危险操作」· plan 里的 `allow_high_risk` / `confirmed` · 审批结论写进对话上下文。
