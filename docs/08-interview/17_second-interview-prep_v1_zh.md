## §1 一面带回的两道题（标准答法）

### Q1 · 为什么需要 supervisor？spec 生成场景好像没必要

**这是判断力测试，先认同一半再给判据。**

30 秒口语稿：

> 「您说得对——如果场景真的只是聊几轮、生成一份 spec 文档，supervisor 确实杀鸡用牛刀。我们上 supervisor 不是因为场景复杂，而是**约束复杂**：一，对话里混着检索、查工单、查 PR 状态、写回结论这些异构动作，能力分只读和写，必须让每类子任务只拿自己的最小能力集；二，企业要求写操作人审，审批颗粒度必须是『哪个具体动作』而不是『这整段对话』——只有拆解后才有这个颗粒度；三，回答要可审计，计划必须是显式中间工件，不能是模型脑子里的思维链。supervisor 是这三个约束同时出现时的结构化答案，不是目的。」

四判据（被追问「什么时候该用」）：

1. 能力异构且有风险分级 → 按子任务收窄菜单（三重交集：基线过滤 ∩ 可见集 ∩ 声明白名单，只收窄不放宽，builder.py）
2. 需要动作级权限与审批颗粒度 → 委派令牌绑单子任务能力集合，TTL 600s
3. 需要审计取证 → plan 显式工件 + 每步独立事件流 + replay 不重跑 LLM
4. 需要失败域隔离与预算治理 → 契约闸级联停、32 步预算、2 轮重规划上限

诚实收尾（必背）：「反过来，单一能力、低风险、无审计要求的场景我绝不会上 supervisor——规划那 40 多秒的 LLM 延迟就是白付的成本。架构选型的尊严在于知道什么时候不用它。」

### Q2 · agent 怎么知道要申请审核？

一面已答：①tool 有标记 ②流程签收痕迹（声明层+业务层，都对）。**升维：纠正问题前提。**

> 「严格说不是 agent『知道』要审批——**是系统不让它不知道也能出错**。审批的触发者不是模型，是确定性代码。」

三层展开：

1. 声明层：清单自报风险面（risk_level/side_effect/hitl_required）；但「清单只能声明危险，不能豁免危险」——放行键 Host-only，模型在 plan 里自写 allow_write 不生效（policy.py:23-33）
2. 编排层（关键层）：supervisor 规划时**无审批权**，只选能力；真正触发的是派发前签发委派令牌时的确定性判定：hitl_required → 拦截（blocked_by=delegation_issue_hitl_required）→ interrupt 挂起出人审单（nodes.py:999-1015）。**模型判断失误跳过审批的攻击面不存在**
3. 裁减层：审批只是三级响应的中间级——高危能力连可见集都进不去（模型连幻觉出它的机会都没有，baseline.py）；中危写默认硬拒；只有声明了可审批路径的才走到 HITL；不确定一律默认拒

收口金句：「把审批从『模型的自觉』变成『系统的强制』——自觉会犯错，强制不会。」

## §3 能力层 · 问题反查机制（主攻）

**核心不对称（先讲这个）**：执行才记回执，闸拒不落回执——被拒的调用走 logger+tracing span+metrics 计数，不污染回执表。「被拦不记账」是刻意的：回执是事实账，不是意图账。

| 问题类型 | 反查路径 | 锚点 |
|---|---|---|
| 谁被拒了 | metrics 按原因码计数（blocked_meta）；六类拒绝码词表 R-a~R-f | metrics.py:42-48 / delegation.py:54-57 |
| 写操作台账 | ops_capability_receipts（capability_id/ok/write_confirmed/subtask_id/idempotency_key） | models.py:387 |
| 防重判定 | ops_capability_idempotency + previous_captured 同键返回上次捕获 | http_generic.py:544-645 |
| 闸装没装 | 金句：write.blocked 恒为 0 可能不是没攻击，是闸根本没装上——配 /runtime 看 | metrics.py:4-9 |
| 灰度观察 | delegation observe 档记 would_block 不拦，量化误伤面再切 enforce | gateway.py:277-334 |

**实证故事**：本地 receipts 41 行全 testing.write.echo（captured 单薄）、idempotency 48 行全 oa.ticket.create——演示「证据面按能力维度可查」；契约闸拦截时 receipts 零行=「被拦不记账」实证。

**思考方向（被问改进）**：闸拒事件的审计持久化是个真问题——当前只 span 不落表，多实例下进程内计数各一份（metrics.py:11-13 已知边界）；方向是拒绝事件也进事件流，按拒绝码聚合出「谁在被反复拦」。

## §4 数据层 · 问题反查机制（主攻）

**三表+一机制的分工（一句话版）**：threads 管归属、turns 管对话原文（6+2 窗口源）、run_events 管帧证据（replay 真源不重跑 LLM）、checkpointer 管执行面挂起恢复。证据面与消费面分离。

**SQL 取证实战故事（今天刚发生，最鲜活的反查案例）**：用户报「批准了但恢复不了」——全程 SQL 反查：审批单表发现 thread_id 列为空串 → 比对历史 24 行全有值 → 锁定回归窗口 → 根因是 ruff UP007 风格收口把 observe_node 签名改成 PEP604，langgraph 1.2.11 字符串化注解注入丢失 → config=None。**讲法重点：fail-closed 设计让回归变成显式 409 而不是静默错误恢复——观测体系的价值就是把「不对劲」变成「可查证的证据链」。**

**反查键三级结构**：run_id 定伞（每帧必带，可 JOIN usage/HITL/回执）、seq 定时序（并行工人帧桥回主流共享全局序号轴）、subtask_id+agent_role 定分支。「证据链不是一条链，是一棵带序的树。」

**已知缺口口径**：answer 帧逐 token 落盘（19B/帧×1.1 万行）存储成本 vs 取证粒度是笔账；memory 三表 0 行（休眠，见 §5）。

## §5 记忆层 · 诚实口径 + 思考方向

**口径（先说死，不装）**：「记忆我们做了写入侧，消费侧实证零消费后**主动把注入下了**——先证消费再接注入。当前会话内靠 6+2 窗口，窗口外只剩占位标记（知道有，不知道是什么）。这是状态，不是遮羞布。」（memory facts ④b 裁定休眠 2026-10-20；SESSION_SUMMARY_ENABLED / QUERY_REWRITE 默认关）

**思考方向（讲「如果做，我会这样做」）**：

1. 记忆是另一种写操作——写入就该过同一条闸链（谁的事实、什么过期、冲突怎么裁、租户怎么隔离），不能因为叫『记忆』就绕过能力层的纪律
2. 先接消费再开写入的反向灰度：spy 模式观察『如果注入了会不会被用』，用数据决定上线——和我们 delegation observe→enforce 同一方法论
3. 记忆 vs 证据链的边界：记忆是消费面（帮模型答得好），run_events 是证据面（证明发生了什么）——绝不让记忆变成事实源，取证必须回到帧
4. 窗口外关联的三层补救路线：摘要替换占位条 → query rewrite 召回 → 长期记忆，按成本递进

## §6 模型层 · 诚实口径 + 思考方向

**口径**：「熔断、指数退避重试、usage 逐调用落表是生效的（基座 __init_subclass__ 统一包装，业务代码碰不到 HTTP）；预算硬闸设计了检查点但默认关——高危默认关的同一纪律，灰度没走完。」（base.py:39-156；预算 :44-47 默认直通）

## §10 详版叙事（m01469 点单：失败场景+最大事故+反问）

### A. 失败场景 · run cb2548「差一个单词」（2-3 分钟逐字骨架）

1. 背景一句：用户一句话「查一下 123 号 issue 的状态，然后写个总结」。
2. 规划 46.6 秒拆 2 子任务：查 issue（只读）→ 写总结（write，要过审批）；计划声明前者产出 title/body/status，后者消费 status。
3. 冲突：查 issue 工具 38 毫秒跑完——但实际输出字段叫 state，不叫 status。**就差一个单词。**
4. 闸动：派发前契约闸比对 consumes/produces，前驱产出没有 status → 当场拦下，写步零执行，blocked_by=contract_missing_field。
5. 转折：错误显式落帧；critic 判「有错但值得再给规划器一次机会」→ 重规划。
6. 暴露短板：重规划时模型只看到光秃一行「被拦了」，没有「实际可用字段是 state」的结构化清单——不知道病在字段名映射，第二次照犯。
7. 结局：两轮预算烧完，按 budget_exhausted 显式收官；用户拿到降级说明，不是假装成功的答案。
8. 三点升华（必说）：① 闸链按设计工作，写步一次都没误执行；② 失败全程显式，1206 帧一条 SQL 复盘到底；③ 它直接催生了改进 task——把可用字段清单反哺重规划。**失败不是终点，是需求。**

### B. 最大事故 · ruff 注解回归「一次零行为变化的 lint 收口」（3 分钟版）

1. 报案：用户反馈「HITL 批准了，点恢复，409，前端说会话无法恢复」。
2. 反查（全程 SQL，没看一行应用日志）：审批单表 thread_id 空串；历史 24 张单全有值 → 同一路径前后行为不同 = 回归，不是配置问题。
3. 锁定窗口：健康单 10-17，故障单 10-27；窗口内 PR 里有个 ruff UP007 风格收口，把 observe_node 签名 Optional[RunnableConfig] 改成 PEP604。
4. 隐蔽机制：文件顶部 from __future__ import annotations 使注解字符串化；langgraph 靠签名内省做依赖注入，1.2.11 认不出字符串化的 PEP604 → config 静默变 None → thread_id 落空串。**一次纯风格收口把运行时契约改没了。**
5. 反转（重点）：bug 没造成任何错误恢复或数据错乱——fail-closed 让 thread_id 缺失直接变显式 409，宁可拒绝也不假装能恢复；证据链让我全程 SQL 钉案，没复现环境、没加日志重跑。
6. 事后三动作：修复单独立 task（仓规：无 task 不改码）、回归测试断言节点收到 config、给上游 langgraph 提 issue。
7. 金句：**「注解也是 API」**——类型注解在签名内省框架里是运行时契约，lint 工具不知道。

### A 与 B 的分工（m01469 Q2）

## §13 · 上下文风险求值：北汽车控想法的 TokenOS 转世（m01569）

### 故事原型

车控场景：开窗/开门平时是正常操作，高速行驶中就是高危动作。**风险不是能力的静态属性，是能力×世界状态的函数。** 纯代码枚举易遗漏，当时想到引入本体（ontology）推理——未落地，只是一个方向想法。

### 为什么这个故事在 TokenOS 比在北汽更值钱

1. **北汽没接住的话题，TokenOS 是主场**：智能家居全是上下文相关风险——雨天开窗 / 无人时开燃气 / 有儿童时调热水器温度 / 夜间语音从门外开锁；
2. **反向案例更出彩**：跌倒检测后自动开门让急救人员进入——平时绝对禁止的动作，紧急上下文里**必须执行**。上下文不只升风险，也降风险——这正是纯静态声明做不到的；
3. **它直接戳 L0-L4 的本质缺陷**：自治等级不能只按能力划分，必须按（能力 × 世界状态）求值——「L3 自治」在高速/暴雨/无人时应该自动降级。

### 诚实状态 + 架构师的讲法（方案光谱，不卖银弹）

- 现状口径：「我现在的闸链是**静态风险模型**——manifest 声明 risk_level，Policy 按声明执行。车控那个场景让我看到下一层是**动态风险求值**。」（与自己架构的边界对齐，不吹已落地）；
- 方案光谱（从轻到重）：
  - **L1 世界状态快照进闸**：Policy 判定时除 manifest 外再读一份 world-state snapshot（车速/天气/在家人数），命中规则即风险升档→自动挂 HITL——工程成本最低，能覆盖 80% 场景；
  - **L2 规则引擎**：状态×能力的规则库独立维护，规则可评审可 diff——规则和 manifest 一样「可评审工件化」；
  - **L3 本体推理**：当规则多到相互作用、需要一致性检查和推理（「开窗 AND 雨天 AND 无人在家」组合爆炸）时引入——**本体是规则复杂度失控后的答案，不是起点**；
- 金句：「静态声明管『这个能力天生危险吗』，动态求值管『这个动作此刻危险吗』——两层都要有，第二层是端侧智能绕不开的。」

### 面试纪律

- **不点名北汽**——说「之前接触过一个车控场景的项目」即可；
- 主动声明未落地（与 §4 诚实纪律一致），落点在「这个认知是从真实场景长出来的，不是读论文来的」；
- 收尾反问：「TokenOS 现在的风险判定是纯静态的，还是已经考虑了家庭状态上下文？」——无论答案是什么，你都占据了对话的下一层。

### §13 补遗 · 信号可获得性 + 安全三层（m01577 用户反驳提炼——用户自己长出来的工程直觉）

**反驳实录（用户原话精华）**：天气和人体需实时传感；「无人时开燃气」不成立——小火炖汤必然无人；但灶上状态和油烟机更易传感，且天然气与油烟机应强绑定，**可代码写死**：灶开 X 分钟油烟机未启动→断气；洗澡识别儿童不易实现。

**提炼一 · 上下文信号按可获得性三级**：
1. **设备状态直读**（灶/锁/阀/油烟机/水浸/电表）→ 可直接进闸；
2. **可推断**（在家=门锁+人体传感+手机 Wi-Fi；夜间=时钟）→ 进闸但标置信度；
3. **难观测**（儿童身份/情绪/意图）→ **不进闸**，用代理信号（成员权限/时段上限）替代。

**提炼二 · 安全三层（联锁在 agent 之下）**：
- **L0 硬联锁**：灶×油烟机这类强绑定**代码写死、不过模型**——模型宕机不能是安全事故的单点；

金句：「**能写死的联锁绝不过模型；进闸的信号必须传感器真能读到；规则上线先量误伤。**」

## §14 · 「先量后闸」observe 方法论（m01588-m01594 提炼）

**定义**：observe = 只计量不决策的观察档——新闸/新规则/新功能先上影子模式：判定逻辑完整执行，但只记录不动作。

**vs 灰度发布（必分清）**：灰度切的是流量比例（5% 用户上新版本，回答「新版代码有没有 bug」，小比例用户真实承受风险）；observe 切的是动作生效与否（100% 流量跑新判定，结果只记录——回答「判定本身准不准、误伤多大」，用户零影响）。**纯代码变更走测试+灰度；observe 档专用于离线测不准真实分布的判定逻辑**（新闸/新阈值/模型行为类功能）。完整链路：golden set 离线过闸（已知场景不能退）→ observe 上线量真实分布（未知分布不伤人）→ 数据达标切 enforce。

**记什么三件事**：会拦多少（would_block 率）/ 拦的是谁（正常流量还是真攻击）/ 按原因码分桶（分布指修复方向：过期多→改 TTL，集合不匹配→改签发逻辑）。

**切换标准**：数据驱动不是时间驱动——误伤率压到 ≈0 或仅剩预期拒绝才切 enforce。「跑两周看看」不是标准。

**双向推广**：拦（减法：delegation 令牌、风险规则——记 would_block，做错代价显性=误伤）与给（加法：memory 注入 spy、主动服务——记消费率，做错代价隐性=token 白烧+虚假能力感）同一哲学「动作先生效于日志，再生效于系统」。**拦错的代价显性、给错的代价隐性——隐性的更需要数据来证，因为不会被投诉叫醒。** memory spy 实证：9 个 LLM 消费点零消费，不上 spy 直接上线=纯成本+自以为有记忆。

**配套纪律**：observe 档必须真跑判定逻辑（delegation observe 是完整验签非空转）否则量的不是真数据；记录要结构化可聚合。

金句：「闸的 bug 在 observe 档是自己的问题，在 enforce 档是用户的事故」/「切换标准是数据不是日历」/「新闸先量误伤，新供给先证消费」。实证锚点：delegation 三档 gateway.py:277-334 / memory spy continuity.py:5-12 / 炖汤反例 §13 补遗。

run_events 字段七件：run_id / seq（**uq(run_id,seq)** models.py:328）/ user_id / thread_id / ts_ms（相对毫秒）/ agent_role（表列 :340）/ event_type / payload JSONB。**三级关联键**：run_id 定伞（每帧必带 sse_stream.py:283；ops_llm_usage.run_id/HITL/receipts 同键可 JOIN）→ seq 定时序（emit 闭包单点分配 :279-280，并行工人帧经 progress_stream 桥回主流共享同一序号轴；并行可以乱序不行）→ subtask_id+agent_role 定并行分支。

写入纪律：emit 逐帧落盘**有条件 if user_id + 后台尽力**（sse_stream.py:295,318-323——落盘失败不挡主答，证据面塌了执行面照跑）；keepalive 不落盘（:73-75）；收尾判定 event_store.py:116-118,144,170。replay=POST /replay?run_id&after_seq（router.py:372-428）**原样回放不重跑 LLM**——成本零、结果确定。

金句：「turns 给模型看（窗口消费），run_events 给人查（取证审计），threads 给系统管（归属恢复）。」

### 15.3 Checkpointer（执行面）

**两 saver 互斥不双写**（run_worker.py:138-142 if-else）：LG_RAG_HTTP_CHECKPOINTER=postgres 且 supervisor 模式→AsyncPostgresSaver；否则（含 basic/router 模式）→InMemorySaver 默认。**默认关是刻意的 fail-closed**（checkpointer.py:33-36）：内存 saver 下跨进程恢复不可能，恢复入口显式报错（checkpointer_not_configured 503 / stranded_checkpoint 409）**不假装成功**。

**PG 四张框架表**（langgraph-checkpoint-postgres 包）：checkpoints（PK thread_id+checkpoint_ns+checkpoint_id，checkpoint JSONB=state channel_values，parent_checkpoint_id 链，metadata step/source）/ checkpoint_blobs（channel 大对象字节，msgpack）/ checkpoint_writes（中断点 pending writes，恢复时补放）/ checkpoint_migrations。

**写入时机**：每个 super-step 结束 + interrupt 挂起那一刻——router.py:11-17 注释「interrupt 挂起那一刻 checkpoint 必须已落盘，否则批准请求找不到恢复点」。**恢复**：resume→同 thread_id 取最新 checkpoint→父链重建状态→重放 pending writes→从挂起点继续；批准=解锁+摘出不可变前缀+剪旧结果+轮数归零（hitl/router.py:526-527）。金句：「**状态全在 PG 里，进程只是无状态执行器**」。

### 15.4 两面为什么分开 + 交叉点

分开理由：用途不同（回放取证 vs 恢复续跑）/ 生命周期不同（帧永久 append-only vs 快照可被新快照超越）/ 消费方不同（人+SQL vs LangGraph 运行时）。交叉点=HITL resume：既要 checkpoint（恢复图状态）又要 run_events（hitl.resumed 帧落盘+replay.cursor 追帧，hitl/router.py:603-611）。本地实证：checkpoints 1,106 行/86 thread；run_events 12,970 帧。

被追问「为什么不只用一张表」→「同一事实两种物化：帧是逐帧事实流（可回放可聚合），快照是状态物化（可恢复可续跑）；合并存会让回放成本=重跑成本，也会让恢复逻辑去读审计格式——**证据与状态，各有各的写放大和读模式**。」

### 15.5 三个高频误区的钉案（m01610 Q&A）

**误区一「恢复靠 run_events」→ 错，一帧不读**。恢复路径只读 checkpoint 表（thread_id→最新快照→父链重建→重放 pending writes）；run_events 在恢复里只有写（hitl.resumed 帧落盘）+给用户追帧（replay.cursor）。两套存储并行写、分开读；金句「拿审计日志当恢复源=让证据反串状态」。

**误区二「subtask 产出都在 events」→ 按粒度三载体**：步级摘要（subtask.progress 帧，截断级）→run_events / 完整产出（tool 结果全文、子任务 output）→checkpoint subtask_results channel / 最终答案→answer 帧+turns。子任务内部逐 token 流刻意不落任何地方（progress_stream.py:3-4）。已知断点：ops_llm_usage 有 run_id 无 subtask_id 列，子任务级成本归属靠 Langfuse span 树补。

**误区三「恢复上次对话=按 run_id 找最后一帧」→ 三种恢复三条路**：①视图恢复（断连追看进度）=replay by run_id+after_seq→run_events ✅ ②对话延续（新一轮接着聊）=6+2 窗口→turns ③执行恢复（HITL 挂起续跑）=resume by thread_id→checkpoint。金句：「**视图恢复查 run_events，对话延续查 turns，执行恢复查 checkpoint——三种恢复三条路，混一条就是 bug。**」另：PG 四表是 AsyncPostgresSaver 的存储，开启即建；本地 .env 已开（checkpoints 1,106 行/86 thread 实证），默认部署才是 InMemorySaver。

### 15.6 延伸两问（m01617）

**Q「subtask 是否该存完整对话」→ 该，但放错地方就是 bug**：主流设计（Claude Code/Vanor 子会话）子任务=一次性可观测对话窗口；我们审 Vanor 的批评点之一就是审批落父会话子会话 0 条。ops-desk 现状=存了一半：子图消息在 checkpoint 链（rag 子图 thread_id=subtask_id，nodes.py:1463）但那是状态物化非证据（msgpack 不可查、生命周期跟快照、默认内存）。补齐三候选判定：turns ❌（6+2 窗口的源，放子任务消息=污染收窄窗口）/ run_events 扩展 subtask.message 帧族 ✅ v1（同伞 run_id+seq、replay 继承、cursor 白拿；需两处改：该族全精度不吃截断+可见性标志用户 replay 默认过滤）/ 新专表 v2（查询量大再物化）。成本纪律：子任务消息是 token 大头，全量落=写放大大头；现三载体是刻意取舍非漏做，升级=闸控开关+先 observe 量写放大。TokenOS 钩子：数据不出盒→本地证据链必须自足→子任务 transcript 本地化是卖点；Langfuse 运维面（外部/采样/截断4000）替代不了证据面。

**Q「审批完成+后端跑完后换浏览器打开」→ 纯历史视图**：看到 turns 的问题+合并答案（恢复②对话延续）；看不到过程帧（live-plane 不自动重放已完成 run）与审批卡（单已裁决非 pending，审批过程对新浏览器不可见但 hitl_requests 有台账）；系统侧零恢复（无 SSE 可接、无 checkpoint 要读——checkpoint 只在 resume 挂起 run 时读）；过程取证=replay by run_id。金句：「换浏览器=换一个查看者不是换执行者——run 完成不依赖浏览器在场（执行传输解耦）、历史视图不依赖 run 活着（turns 与 run 生命周期解耦）、过程证据不依赖对话视图（run_events 独立可查），三面各自独立拼起来才是完整事实。」
