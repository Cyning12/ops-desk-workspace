## 一、段 1（12 min）：RAG agent 与需求分析 agent 怎么整合

### 90 秒开场稿

> 我先把结论说了：我没有靠**合并代码**来整合这两个 Agent，我靠的是**分层复用 + 单向依赖**。
>
> 具体是三层。最底层是一个黑盒的 RAG 答问链，它只暴露一个 `ainvoke` 入口，上层谁都能调，但它**不允许反向依赖任何上层**——这条依赖方向是写进模块边界登记表、有人签的。
>
> 中间层是 LangGraph 的三张图，而且是**渐进演进、不是替换**：`basic` 只一条 rag 就结束，我把它**留着当对照基线**；`router` 加了快路径和 LLM 三分类，分 rag / 直答 / 拒答，检索完还接一个评估节点做低质改写；`supervisor` 才是多 Agent 那张图——意图识别 → 策略构建算可见能力集 → Supervisor 拆解子任务 → 分发到 rag / 抽取 / 工具执行 → 汇聚 → Critic 回环。
>
> 最上层是能力执行，走 Capability Gateway 的精确 id 调用。
>
> 所以「整合」对我来讲是：**下层可以被黑盒复用，上层按需组合，依赖方向单向**。需求协同那个 Agent 能理解代码，靠的不是把 RAG 塞进去，是它拿到了图谱这个**结构化**输入。

### 展开要点（按这个顺序讲，每点 1–2 句）

1. **三张图是演进链，不是三个模块。** `basic`（Phase 1 对照）→ `router`（Phase 2–3）→ `supervisor`（Phase 4）。**保留 basic 当基线**——不为「新的一定更好」做无基线的替换。
2. **router 图的关键取舍**：数字类问题走快路径，其余 LLM 三分类，**fallback 落到 rag**（不落拒答）。检索后的评估节点**复用已有 gate、零额外 LLM 调用**；只有「低质且重试 < 2 次」才触发 LLM 改写，且**改写有熔断封顶**。
3. **supervisor 图的编排顺序**：Intent（结构化输出管道，`max_retries=1`）→ Strategy Builder 算 `allowed_capability_ids`（= 注册表 ∩ 策略）→ Supervisor 拆解 **≤4 个子任务**，**拆解失败时 fallback 成单条 rag**（保证有终态）→ 分发 → 回收结果 → 汇聚 → Critic。
4. **Critic 有三条出边**：`pass/end → END`、`retry_planner → 回 Supervisor`、`rebind → 回 Strategy Builder`。预算 1+1。
5. **H-β 的细节值得主动讲**：supervisor 总步默认 32，耗尽直接走汇聚；而且这个预算是**全局优先于 Critic 回环**的——否则两个回环（subtask 循环 + critic 循环）会互相打架，max_steps 反而失效。这是一个真实踩过的坑。
6. **结构化输出的分层**：解析/修复/校验/预算纠偏是**内核**，业务 schema 放在业务模块里，**内核不含业务模型**。
7. **两个 Agent 的真正整合点**：supervisor 的 rag 子任务**复用整张 router 子图**（不是重写），代码路径上有明确入口。

## 二、段 2（12 min）：需求协同怎么「读代码」——图谱作为 AI Coding 的副产物

### 90 秒开场稿

> 这个 Agent 能理解项目代码，靠的不是把代码塞进上下文，是靠一份**结构化图谱**——它本来是我做 AI Coding 时的副产物。
>
> 做法是两条轨。人写的是编辑源，机器读的是编译产物：源是分层的 `.graph.yaml`，跑一个编译脚本，产出同目录的 markdown（人看，带 Mermaid 和结构化表）和一份 `graph.json`（机器看的唯一真值）。所以人和机器读的是**同一份声明的两种表示**，不是两份会漂移的文档。
>
> 分层是三层的：顶层是路由与依赖总图，中间层是模块边界和逐条流程，最底层是**分域的**倒排索引——按路径、按符号，而且 chat 和另一个域是**分文件**的，不做单文件全仓汇总，命中才打开。
>
> 最关键的一点：**每条关系边上都带代码行号锚点**。所以这份图谱是可以被验证的、会漂移的、能被追责的——它不是一份写完就过期的文档。

### 展开要点

1. **副产物是重点**：图谱不是单独维护的项目，是 AI Coding 流程里**本来就要产出**的东西，被 Agent 复用了。这是「一份投入两份收益」。
2. **两轨分离**：`.graph.yaml`（编辑源）→ `graph-compile.sh` → 同目录 `.md` + `shared/graph.json`（唯一机器轨真值）。schema 版本化。
3. **三层物理分层 + 术语纪律**：G-L0 / G-L1 / G-L2，正文与任务里**禁止裸写「L0/L1/L2」作架构义**，必须带前缀。避免同一个词在不同上下文里指两件事。
4. **G-L1 是人签真值**：模块边界登记表有**四十多条人工签核记录**，每次改动留痕、留日期、留说明。**「谁改的、什么时候、为什么」是可追溯的。**
5. **G-L2 按需加载**：分域倒排（chat / lg_rag 各一份），禁止全仓单文件——这是对上下文预算的纪律。
6. **变更策略按层分级**：不同层用不同的思考预算与 review 强度，不是一套工装。
7. **→ 直通本体论的那句话（一面最该说的一句）**：
   > 这张图谱其实已经是本体的**最小可用形态**了——**类型化的对象**（节点分流程 / 结构 / 外部）、**类型化的关系**（依赖 / 分支 / 触发）、**可验证的锚点**。它缺的只有两件：**约束与推理**。
8. **为什么不是 OWL 重落地——这是克制，不是不会**：
   开源库 3.0 里有一条 **ONTO-OPEN 裁定**：图谱表面开放，但捆绑的本体文件只是自用元模型，**不提供消费者自定义类与关系**。理由是没有真实消费者。同时设了**三个重审触发条件**：真实消费者请求 / 本体检查稳定一个小版本后重评 / 生态拉动（且变更需人工闸）。
   > 讲法：「本体层我在 3.0 里**主动裁定不开放**。不是因为做不了 OWL，是因为**没有真实消费者的时候开放本体层，只会长出一套伪类型系统**——成本落在业务域，收益测不出来。所以我把它设成有触发条件的门，而不是一个常开的开关。」

## 三、段 3（12 min）：写操作与外部变更，靠什么保证不出事

### 90 秒开场稿

> 我的判断标准只有一条：**这个闸是模型改得了的，还是改不了的。**
>
> 按这个标准，写路径上有四类东西。第一类是**可见性**：不该被调用的能力，在拼上下文之前就不进目录——模型看不见，它就写不出那个 id。比如我那个受控写盘的服务，我刻意**不把它注册进能力注册表**，因为它一旦注册就会被模型看见。第二类是**策略键只在 Host 侧**：高危、沙箱、CLI 默认全部拦掉，放行键只有 Host 能给，plan 里写什么都没有用。第三类是**参数契约与作用域**：有 schema 就校形态，标了租户封闭的能力，缺租户谓词直接拒。第四类是**人工闸与退出码**：需要人签的流程，没签就不许往下走，CI 拿到的是硬停的退出码。
>
> 一句话：**凡是写进提示词里的安全约束，都不算闸。** 我只看删掉提示词之后，还有几道拦得住。

### 展开要点

1. **Capability 侧**
   - Policy 门：高危 / sandbox / cli **默认 blocked**；放行是 **Host-only 策略键**（双键），模型改不了。
   - **阶段 H**：`tenant_scoped` 的能力**缺 ctx 租户谓词即拒**；有 `args_schema` 则形态校验；span 落 args / policy / subtask 摘要。
   - 只读约束：本库 issue/PR lookup 走**摘要字段、不带原始负载**；**禁掉走外部 API 的热路径**。
   - MCP：**真 MCP 默认关，CI 不出网**。
2. **写盘侧（最值得讲的细节）**：受控写盘是一个**纯服务**，不是 Gateway 能力——**不进注册表、不进清单、没有 HTTP 路由**。它有目录白名单、默认 dry-run（`confirmed=False`）、**禁止代签的机械挡**、原子写。
   > 这里要说的那句是：**我把「能力」和「执行」分开了。能被模型看见的才叫能力；这个写盘服务不是能力，所以模型看不见它。**
3. **工程流程侧（开源库）**
   - 门禁退出码是**三态**：通过 / 用法错误 / **BLOCKED（CI 与代理必须硬停）**。
   - 任务文件里**必须有人工闸且状态为已批准**，才允许走到改码那一档。
   - 有一组**流程域的写入拒绝**：对任务、评审、调用记录这几类目录，工具层直接拒绝写入——只由一个常量保护。
   - 测试策略声明为必需时，**没有真实测试产物就报 BLOCKED**。
4. **迁移纪律**：旧接口下线时给 **410**，但**不删代码、不删图、不删表**。降级路径留着。

### 跨语言一致性怎么证明（追问二 · 已演练 · 这是目前最强的一答）

**核心立场**：Python 的 CI 只证明 Python 没自己回归，**不证明两边一致**。证明不靠"代码长得像"，也不靠把 `gateway.py` 翻译过去。

**证明物是第三份东西**：一份**语言无关的行为 fixture**，两套实现的 CI 都跑它。

- **只钉调用方看得到的结果**：同样的注册、同样的 `list` / `invoke`，必须得到同样的 `ok`、同样的错误码、同样的「adapter 有没有被调用」。
- **明确不锁**：不比异常类型、不比日志原文、不比 span 怎么打。ToolNode 桥不进这张表（本就不是可迁移内核）。
- **错误码用双方约定的稳定枚举**：`unknown_id` / `disabled` / `policy_blocked` / `args_schema_invalid` / `duplicate_id`，**不用 Python 的 `ValueError` 文本**。
- **契约锁的是门序**：查表 → enabled → Policy → schema → **最后才调用**。用假 adapter 记录有没有被调到就够；adapter 内部的 DB / MCP 不要求字节级一致。
- **第一批不新发明**：把现有单测收成 fixture——未知 id 不抛 / 重复注册拒绝覆盖 / 关掉的能力在过滤后的 list 里看不见 / 高危默认拦住 / 参数形态不对就拒。
- **治理规则**：两边 pin 同一份 fixture 版本；**谁和 fixture 不一致谁的 CI 红**；改契约必须升版本、两边一起改；**禁止只改一侧测试去迁就实现**。

**诚实收束（这段要留着）**：
> 「Python 侧这些行为已经被单测钉住，**它们就是以后的 oracle**。Java 侧还没跑过同一份 fixture，**所以我还没有跨语言一致性证明**。要拿到证明，就加这一个共享 fixture 作业——而不是在 JVM 里再写一套只对自己绿的测试。」

### 但这答法还有四处会被追（补了才算完整）

**1. 边界与组合用例 —— 错误码的优先级。** 你列的第一批全是单点负样本，缺**组合命中**：一个能力同时 `disabled` 且 `risk=high`，返回哪个码？`args_schema_invalid` 与 `policy_blocked` 同时成立呢？
**门序决定错误码优先级，而优先级恰恰是最容易跨语言分叉的地方。** 必须专门加一组"多门同时命中"的用例，把优先级钉死。

**2. fixture 只能锁「已想到的」行为。** 真正的分叉往往发生在没写进 fixture 的路径上。补一类**差分测试**：两侧跑同一批随机/生成输入，比较输出差异——用来**发现**你没想到的分歧，而不是验证你想到的。fixture 负责"不许退化"，差分负责"发现未知"。

**3. 共享 fixture 的托管与所有权没定。** 放哪个仓？用独立包、子模块还是制品仓？**谁有权改、谁审？** 这条不定，第一次改契约时就会扯皮。建议：独立制品仓 + 版本号 + 变更需双方 owner 共同批准。

**4. 比较口径必须先定，否则第一次跑满地红。** Java `long` vs Python `int`、`null` vs 字段缺失、时间格式、字符串编码、浮点精度——这些**不是契约要锁的，但会让 fixture 跑红**。必须先规定比较口径（例如统一走 JSON 规范化后比较、数字统一字符串化、时间统一 UTC ISO8601）。
**这条不定的后果很严重**：满地假阳性 → 有人开始改夹具迁就实现 → **正好破掉你第 6 条纪律**。所以要把它写进 fixture 规范的第一节。

**5.（小）其他三层没有 oracle。** 你把契约面列了四项（`CapabilitySpec` / `list`+`invoke` / Policy 门结果与 span 键 / Plan 数据结构），但这套 fixture 只覆盖了**能力层**。Plan 数据结构、Structured Output schema 的跨语言一致性靠什么钉？要么明确说"第二批再说"，要么就得各给一个对应物。

## 七、对方「已经有若干 Agent」——这是利好，但要防两个陷阱

> 新增背景：目标公司**已经有了若干 Agent**。这一条改变面试的提问重心，要调整定位。

### 先摆正：他们已有 Agent，对你是加分

- 从零做 Agent 的公司会问「你会不会做 Agent」，你的差异点被摊平。
- **已经有若干 Agent 的公司，痛点一定不在「再做一个」，而在「管起来」**：能力重复注册、权限说不清、谁调谁没有契约、观测分散、发版互相踩。**这恰好是你能力层最厚的地方。**
- 定位句（建议直接说出口）：
  > 「你们不缺 Agent，缺的是把已有 Agent 收进同一条治理线——**可见性、契约、策略闸**。我这套东西不是替代品，是**纳管层**。」

### 陷阱一：被问「那你会推翻我们现有的吗」

答「重做一套」＝扣分（不懂存量）。正解与你 Q2 的排序完全一致：
> 「**先不推翻。** 第一步只做授权可见集，把现有 Agent 逐个纳管——每个 Agent 只看见被授权的能力子集，invoke 前二次校验。这一步不需要动他们的实现。等可见性立住，再谈版本 pin 与契约统一。」

### 陷阱二：部署与运行时细节——这是你真实的短板区

对方已有若干 Agent，说明**有人在做运维**，面试官里很可能有后端/运维背景的人。会问到：

| 他会问 | 你要准备的实话 |
|---|---|
| 部署形态？单体还是多进程？容器化了吗？ | **进程内 dict 注册表**在多实例下每个进程各一份 → 一致性怎么保证 |
| 生产真的跑几个实例？多少用户？ | 必须有一个真实量级，**宁小勿大** |
| MCP 默认关、CI 不外网——生产上怎么开？凭证怎么管？ | 沙箱与凭证最小化策略 |
| PG / Qdrant / ES 谁运维？QPS 多少？ | 别吹规模 |
| 发版频率？回滚做过几次？出过线上事故吗？ | 直接讲 RAG 日期格式那次（业务不认账、链路重做） |
| 监控除了可观测平台还有告警吗？SLO 是多少？ | 诚实说没做到 SLO 化 |
| 模型供应商、token 成本量级、provider 宕机怎么办？ | 你有现成设计可讲（grader 故障即拒答，不伪造） |

**分布上这些不是一面的主战场**：一面尾部（若面试官是后端背景）→ 二面技术深度 → 三面/交叉面（技术负责人会问「生产跑多久、多少量」）。

### 应对模式：诚实三段式（别等被问，主动前置）

1. **规模事实**：几个实例、多少用户、多少能力、什么量级。**数字要真。**
2. **边界声明**：哪些没做。「我是内部系统，没做过多租户规模，也没做过跨语言部署。」
3. **迁移判断（最关键）**：**主动说出你这套在对方量级上第一个会破在哪。**
   > 「我这套在你们的量级上，**最先破的是注册表**——进程内 dict 在多实例下会分叉；**第二个破的是可见集求值**——200+ 能力下每次全量求交撑不住。这两处我都有改法，但没在你们这个量上验证过。」

**第三段是把短板变成长板的唯一方式**：你先说出它会在哪破，面试官就没得扣分，反而会认为你清楚自己的边界。

### 8.3 本体论该往哪落（本场最高价值的一段）

**不要讲通用 OWL / 知识图谱导论**——对方要的是「落地有一个方案」，不是理论。在他们语境里，本体的落点非常具体：

- **对象**：车辆、用户、设备（手机/手表/家电）、服务、场景、行程
- **关系**：归属（这台手机属于这个用户）、绑定（用户绑定这辆车）、授权（谁能控哪辆车）、依赖（这个服务依赖哪个设备在线）
- **约束**（**这才是价值所在**）：状态前置条件 + 安全边界
  - 「行车中不能开启座舱娱乐」
  - 「儿童座椅占用时不能……」
  - 「电量低于 X 不能远程开启驻车空调」
  - 「非车主手机不能执行车控写操作」

**这套约束现在的实现形态，是候选人最该去问的问题**：规则表？写死在代码里？还是让模型自己判断？——如果是第三种，那就是「靠自觉不靠机制」，正是你在上一块自己承认过的盲点，也是你能立刻给出方案的地方。

**建议落点表述（可直接说）**：
> 「本体在你们这儿不该落在『给模型更多知识』上——知识再多也管不住它点错东西。它应该落在**约束层**：把车、用户、设备、服务的对象与关系类型化，把『什么状态允许什么动作』变成**可校验的前置条件**。这样本体不是文档，是**执行前的一道闸**——模型看到的是一份说明，代码验的是一份真相。」

**分期路线（照 ONTO-OPEN 裁定的思路讲）**：
1. **先立对象与关系的最小集合**（车/用户/设备/服务 + 绑定与授权两类关系），**只覆盖一个高价值场景**（建议车控写操作），别铺全量
2. **约束优先于推理**：先做前置条件校验（可判定），暂不做推理与传递闭包
3. **每个事实带可验证锚点**：对象与关系挂在哪个域服务的哪张表/哪个接口上，能机器对账——**没有锚点的本体是文档，不是真源**
4. **边界声明**：这一层**对消费者保持封闭**（像你 SpecWave 3.0 的裁定），先只给内部执行链用，设 2–3 个复评触发条件再谈开放

### 8.4 四个反问（替换掉原来第五节的第 3 问）

按杀伤力排序，挑两个问：

1. **区分「知识」与「约束」的那一刀**
   > 「你们现在本体/图谱这一类东西，是落在**给模型做检索的知识层**，还是落在**给执行做判断的约束层**？——因为这两件事的验收标准完全不同。」
2. **跨域纳管的问责**
   > 「『1+N』里的 N（包含外部厂商的），能力是各自注册还是统一纳管？中枢把任务分解完之后，**谁保证它不会点到一个它不该点的能力**？」
3. **模型在场性**
   > 「中枢做完任务分解、到真正执行之间，有没有一道**模型改不了**的校验？」
4. **规则在哪里**
   > 「跨域写操作（比如远程车控）的授权和状态前置条件，现在是**用什么表达的**？规则表、代码，还是模型自己判断？」（**问完大概率能听到真实答案，也会听到痛点**）

### 8.5 三条纪律

- **不要教他们做本体论**，要说「你们已经有 15+ 在跑了，问题不是再造一个，是**给关系与约束一个可校验的落点**」
- **不要把公开报道当内部信息**，说的时候加一句「我看公开报道是这么讲的，不知道和实际差多少」
- **不要把车域当陌生领域**，用你的**对象/关系/约束**三分法去套，比硬背车机术语安全得多
