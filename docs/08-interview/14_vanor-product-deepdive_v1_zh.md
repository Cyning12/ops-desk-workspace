# 14 · 面试产品深聊手册：VanorOS 使用体验与发现

> 日期：2026-10-26 ｜ 状态：v1.1
> 用途：面试自我叙事之后，转向对方产品深聊的手册。面试公司 = VanorOS 所属公司；TokenOS 未上线不可见，只能探针提问。
> 真源：两份实测报告（见 §9 附录指针），全部结论可复现。

## §0 口吻三原则

| 原则 | 做法 | 反面 |
|---|---|---|
| 展示理解力，不展示优越感 | 「我注意到 X，猜想当时取舍是 Y，我自己项目用 Z，你们怎么看」 | 「你们这里缺 X」 |
| 先讲自己踩过的坑，再讲观察 | 自己的翻车经历开场，对方观察放后面 | 一上来点评对方代码 |
| 每个深聊点以开放式问题收尾 | 把话筒递回去 | 给改进建议汇总表（像工单） |

>
> （极简备选：「……整体架构设计完成、代码可跑，实现还在逐步完善中。」——代价是丢掉「清单」着陆点，被追问「哪些没做完」时少一句现成话。）
>
> 另外昨天我深度试用了贵司的 VanorOS，还专门触发了几轮真实审批做观察，对上线运行有了不少真实体感，待会儿也想请教几个问题。
>
> 我理解这次面试主要围绕 agent 方向——这个理解有偏差吗？

结构骨架：身份 → 前雇主两块 → 离职后深耕 → 昨天实测 VanorOS（钩子）→ 反问确认方向（把球抛回去）。结尾反问保留：这是全场第一个开放式邀请。

### 1.1 诚实修正说明（为什么不是「四层都落了代码」）

- 初稿「四层都落了代码」被本人指出过绝对：按模块确有不少未完善/缺失（critic 规则占位 stub、委派令牌 enforce 默认关、防重 store 闸控默认不启用、PG checkpointer 闸控、run 级 cancel 缺口、子任务级超时未做等）。
- 修正策略 v2（2026-10-26 本人定调）：「架构设计完成、代码可跑，实现还在逐步完善」——「完成」限定在架构设计、「完善」限定在实现，两词各配主语避免「到底做完没」的歧义；清单句保留为被追问着陆点。
- 「全部可查」已移除：可信度由「昨天实测+真实审批」钩子与两份报告承担，口述减负；代码可查性留到现场被问时再展示（那时更有冲击力）。
- 金句预案（被追问「哪些没做完」时）：**「我对自己的未完成清单，可能比完成的部分更熟。」** 清单真源 = doc 10 §5 红线表 + doc 13 缺口清单（25 条）。
- 「默认关闭」是故意埋的钩子：对方好奇「为什么会有关着的」→ 高危默认关 + 先观察后强制的方法论展开。

### 1.2 词↔层映射（为什么是四词不是五层）

四个口述词 ≠ 五层里的四层，是 5 层 → 4 词的重新打包：

| 口述词 | 对应五层 | 为什么不直接报层名 |
|---|---|---|
| 编排 | 编排层 | 一词一层直接对应 |
| 闸控 | 能力层 | 「能力网关」听者无感，「闸控」自带追问钩子（七层闸链、高危人批都在后面） |
| 韧性 | 模型层 | 「模型层」最没区分度——谁家没有模型？这一层的价值是模型出问题时系统不倒：熔断、退避重试、用量落账、超预算显式降级。词讲「防什么错」，不讲「有什么件」 |
| 证据 | **传输层 + 数据层（两层并一词）** | 两层共同服务取证：SSE 帧流逐帧落三表、断连重放、不重跑 LLM。分开报是流水账，合并是一个故事 |

打包理由：① 口述记忆上限——四词能停顿能重音，五层连报是报菜名；② 词讲收益、层讲结构，自我介绍的任务是勾起追问欲，层结构留给被追问时展开（doc 11 五层×五阶段矩阵兜底）；③ 每个词带戏眼：闸控→七层+HITL，韧性→「可见的失败率才是可治理的失败率」，证据→三级键+replay。

**反问预案**（被问「你架构是四层吗」）：「架构上是五层。口述时把传输层和数据层合并成『证据』一个词，因为这两层在我这为同一件事服务——取证。」此回答本身加分：说明是主动取舍，不是记不清。

### 1.3 四词展开版（约 30 秒 · 被追问某词时逐词展开）

> 编排——用 LangGraph 状态图做 supervisor 模式：一个规划者并发派发多个子任务，步数和轮次双预算，超了就显式停。
>
> 闸控——模型碰不到真实工具，所有调用走能力网关、过七层闸链；高危动作必须人批了才放行。
>
> 韧性——模型层多 provider 熔断退避，token 用量精确落账，超预算显式降级，不硬撑。
>
> 证据——每一次执行都是事件流逐帧落盘，断连能重放，事后能取证。

### 1.4 十秒极短版（被「一句话介绍下」时用）

> 一句话：我做了一套让大模型安全操作真实业务系统的多智能体运行时，核心是闸控和证据链，全部代码可查。

### 1.5 口述要点

- 「编排、闸控、韧性、证据」四个词说完**停一拍**，等对方接住结构；
- 重音在词本身，展开句语速可快、词要慢；
- 四词顺序就是后续深聊路线图：对方对哪个词有反应就往哪展开；
- 「真实审批」是产品深聊的钩子，自我介绍里**只提做过、不剧透发现**——对方追问「观察到什么」即进入 §4；
- 「VanorOS」口头念「Vanor OS」，别说成「vanorOS」。

## §3 使用体验主线（我做了什么 · 一句话时间线）

被问「你做了什么测试」时的口述时间线：

1. 把审批模式从 auto 切成 ask，扇出 3 个子 Agent 各自写文件，**真实触发 7 次审批**，3 次允许 4 次拒绝，全程日志回溯取证；
2. 静态通读工具注册机制（ToolRegistry / validateSchema / MCP 接入），配可执行脚本做行为实测；
3. 产出两份带复现步骤的报告，并且**修正了自己中途的三处错误结论**（见 §3.1）；
4. 子 agent kill 实测：子 agent 写手册到第 5 节被杀（仅 33 秒），**父 agent 先校验磁盘上的实际进度、再从第 6 节续写**剩余 8 节——agent 自己提炼出「边写边记」「中断后状态需要校验」两条教训（总结原文留存）；
5. 主进程 kill -9 崩溃实测：进程级有 supervisor 循环秒级自动重启，**run 级无恢复**——任务随堆内存整体消失，磁盘产物成唯一幸存；
6. **让 VanorOS 的 agent 自查机制**：它自读 supervisor.js 源码，给出行号级结论——子 agent 是同堆对象 + AbortController，「Session=进程」只是逻辑模型。

### 3.1 主动展示纠错（诚实度活证据）

> 「报告里我专门记录了自己中途判错的三处——比如只看子会话日志就断言『没有弹窗』，实际 7 个弹窗全在父会话。共同病根是拿部分证据下全称判断。我自己项目也栽过同类：拿滞后文档讲架构，把已删的节点讲进现状。所以我现在讲任何机制都带 file:line，讲错了比讲窄了致命。」

这一段同时完成三件事：展示实证方法、展示诚实、复述自己的工作纪律。

## §4 深聊点一：拒绝的语义（首选 · 理论高度最高）

**实测发现**：子 Agent 的 write_file 被用户拒绝后，换 exec printf 完成了同一写入——审批绑在「工具调用」上，用户拒绝的是「写这个文件」，模型理解的却是「这个工具不行」。错误消息对模型只有一句自然语言，无法区分「参数错了该重试」与「操作被禁止不该重试」。

**我的同源经验**：「我自己做多 Agent HITL 时最纠结的就是拒绝之后模型怎么办。我的解法是两头堵：能力侧，模型拿到的菜单是收窄过的，且授权令牌绑定能力集合和参数约束——换能力等于换目标，要重新签发；流程侧，被拒绝的子任务进终态，要重试必须走重规划。但我承认『意图级否决』我没做完——同一个意图换张菜单里的卡再试，我目前拦不住。」

**开场句式**：「我自己做 HITL 时最纠结拒绝之后模型怎么办，实测时发现了一个真实的绕过链……」

**收尾问题**：「Vanor 如果要给拒绝加上意图语义，你们会走语义标签（提示词）还是目标追踪（记录被拒绝的目标）？我自己的判断是目标追踪更可靠，因为不依赖模型理解提示词——但实现成本高。」

## §5 深聊点二：pattern 完整匹配（共鸣钩子最强）

**实测发现**：validateSchema 只支持 type/enum/required/properties/items；pattern、maxLength 写了不生效——实测 pattern 违规错误数=0。声明了约束、运行时完全不检查，schema 的自我描述是残缺的。

**我的同源经验（金牌共鸣点）**：「这个坑我自己前天刚修过。我的委派令牌层也有 pattern 参数约束，最初实现也有锚定问题，后来收紧成整串匹配——因为 JS 和 Python 的 `$` 都不锚定末尾换行，`re.search` 类语义会让 '123abc' 通过 '\d+'。所以我读 Vanor 代码时特意看了一眼 validateSchema。」

> 代码锚点（自己侧）：app/ops/capability/delegation.py:292-293「pattern 约束按整串匹配（re.fullmatch · fail-closed 收紧）：未锚定 pattern 不退化为子串包含，`$` 亦不匹配换行前」。

**为什么这个点段位高**：「我前天刚踩过一模一样的坑」是技术面试里拉近距离最快的句子——证明你读对方代码是真带着经验读的，且质量标准是在实战里磨出来的。

## §6 深聊点三：注册期校验与能力抽象（架构观展示）

**实测发现**：register() 只有一行 Map.set——无形状校验、无拒绝码、无能力声明；畸形工具（缺 handler）静默通过并被原样发给 LLM，错误推迟到调用时才暴露，且暴露方式不一致（register(null) 立即抛、缺 handler 静默、handler=123 调用时才炸）。两处注册清单（harness.js 与 server.js）独立维护，新增工具要改两处。

**我的同源经验（软措辞版）**：「我自己项目里把『能力』和『实现』拆成了两层：能力用清单文件静态声明风险面——风险等级、读写副作用、是否需要审批——实现注册必须挂到已声明的能力上。最意外的收益不是安全，是**清单变成了可以独立评审的工件**：review 权限变更不用读实现代码，看清单 diff 就够了。」

> 原报告措辞「有能力层却没有能力清单，等于有实现无边界」**不要当面说**（太重），内化后用上面的收益导向表述。

**收尾问题**：「Vanor 的 danger 可以是函数、按参数动态判级，这个表达力挺迷人的——你们考虑过在保留动态判定的同时加一个静态的最坏情况声明吗？这样审计面就有了确定答案。」

## §7 TokenOS 探针（未上线 · 只能问，但问法就是展示）

TokenOS 名字直指令牌——恰好是自己项目最深的领域（委派令牌：能力集合 + 参数约束 + 600s TTL + 签发验签分离 + off/observe/enforce 三档灰度）。探针三问按层次递进：

1. **关系问**：「TokenOS 和 VanorOS 是什么关系？独立产品，还是 VanorOS 的权限层独立出来？」
2. **层次问**：「如果 TokenOS 做的是授权令牌，令牌绑的是什么——工具名、参数约束，还是意图？」（问题本身展示你知道令牌设计有三个层次）
3. **协同问**：「Vanor 现在审批绑在工具调用上；如果 TokenOS 落地，拒绝语义是不是就能绑到意图上了？」

**展开预案**：若 TokenOS 确实是能力令牌方向，立即接上自己的委派令牌经验：「我做过类似的东西——令牌绑能力集合和参数约束、短 TTL 禁止续期、签发和验签分离在两处代码、上线走先观察后强制的灰度。最大的教训是：签发侧的 bug 在验签侧看起来全是攻击，所以灰度期必须只记录不拦截。」

## §8 禁区清单（不当面提）

| 禁区 | 原因 |
|---|---|
| 「以后都允许」一键把全局审批降为 auto、写配置文件、无二次确认 | 安全事故级缺陷，当面点破让人下不来台 |

### 附 · Node 三档隔离的技术底牌（问「进程隐喻」时用）

对方栈是 Node.js，「给子 agent 真实边界」有三档可选——问出问题的同时亮出这张表，证明你是做过取舍的人：

| 档位 | 机制 | 隔离强度 | 代价 |
|---|---|---|---|
| 同堆对象（Vanor 现状） | 对象 + AbortController | 无——宿主崩全灭 | 最便宜，上下文共享零成本 |
| worker_threads | 独立 V8 isolate + 独立堆，postMessage / SharedArrayBuffer | 中——JS 异常隔离，native 崩溃仍全灭 | 消息序列化，上下文传递要显式 |
| child_process.fork / spawn | 真 OS 进程，自带 IPC 通道 | 强——崩溃互不影响 | 每进程数十 MB、启动慢、IPC 序列化开销 |

口径：「我们也选了最便宜的一档（asyncio 任务）——问题不是选哪档，是选了便宜档之后**用什么补崩溃语义**：我们的答案是每帧落盘 + 孤儿补偿给失败命名。」
