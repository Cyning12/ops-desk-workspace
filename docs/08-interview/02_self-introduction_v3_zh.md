## 一、定调：11 年经验的自我介绍和校招差在哪

| 维度 | 校招/初级 | 你（11 年 / 架构师） |
|---|---|---|
| 起手 | 「我叫 X，20XX 年毕业于……」 | **先给一个判断，再问是否跑偏** |
| 主体 | 我做过 A、B、C（项目清单） | **我一直在解同一类问题**（一条主线） |
| 证据 | 「我参与了」「我负责了」 | **字段名、机制、失败模式、数字** |
| 态度 | 证明我能学会 | **证明我判断得准，并且知道自己不知道什么** |
| 结尾 | 「希望有机会加入」 | **反问 + 先给假设** |

**最关键的一条：资深面试的开场白，功能不是「介绍我」，是「定调」。** 你说的前三句话，决定了面试官接下来 20 分钟把你放在哪个层级上问。

**而「没有 JD」决定了第二个功能：套出对方是哪条业务线。** 所以结尾必须是一个**二选一**的问题。

## 二、主版（约 110 秒 / 约 480 字）

> 适用：一面开场，面试官说「你先介绍一下自己吧」。

面试官好，我是刘新宁，11 年研发，最近两年在百果园做 Agent 应用与工程效能负责人。

**根据猎头的初步了解，以及我自己看到的公开信息，我判断这次聊的重点会落在多 Agent 架构上。如果和你们实际关注的有偏差，请随时打断我。** 那我先给两句判断，请你们校准。

**第一句：多 Agent 平台真正难的不是编排，是「谁有权调什么」。** 编排框架现在满街都是，一周都能出 demo。但能力一上几十个、一有写操作，先崩的是授权模型，不是编排。所以我在百果园做的就是这一层：能力以注册表登记——`capability_id`、`kind`、`risk_level`、`side_effect`、启用状态；Gateway 做可见集裁剪和精确 id 分发，执行前落 Policy 硬闸。**模型能决定的是「在名单里点哪个」和「参数长什么样」，决定不了名单里有什么。**

**第二句：高危写操作不能只有「默认拒绝 + 配置放行」，得有单次人工确认。** 做法是：发起写请求时冻结一张快照——工具 id、参数哈希、发起人；管理员审的是**这张快照**；执行前再验一次，**参数一变、哈希对不上，旧审批直接作废**。聊天里说「用户已同意」不算，前端把布尔塞进请求体也不读。

**本体论这块我明确定位一下：它是我的学习方向，不是我的交付史。** 在职期间我没有做过本体工程，是离职之后参加技术沙龙才开始系统学；目前只有一个轻量落地——我自己开源库里的那份 `ontology.yaml`：类、带基数的类型化关系、公理独立命名空间，外面套一个 SHACL 语义子集的校验器，并且明确声明不声称标准合规。**所以这块我更想先听你们的期望落点，而不是先讲我的方案。**

边界我也直接交代 **[可省]**：**我没做过 OWL 那种重本体**；我那套能力注册表是进程内的，**放到多实例环境第一个破的就是它**，第二个是可见集求值——这两处我都有改法，但没在你们的量级上验证过。

最后想先确认一件事：**这个平台主要服务车内用户，还是内部员工？** 两边的对象和约束完全不同——前者是车、人、设备、服务，约束是安全；后者是组织、流程、系统、数据，约束是权限和审批。**你们更靠哪边，我后面的例子就往哪边调。**

> ⏱ **时间不够时的裁剪顺序**：① 边界段（标 [可省]）→ ② 第二句判断里的「聊天里说用户已同意」那半句 → ③ 第一句判断里的字段列举，只留 `capability_id` / `risk_level` / `side_effect`。**绝对不能砍**：定调句、两句判断的结论句、本体论的那句定位、结尾二选一。

## 三、精简版（约 40 秒 / 约 220 字）

> 适用：二面、交叉面、或面试官说「简单说说」。

我是刘新宁，11 年研发，最近两年在百果园做 Agent 应用与工程效能负责人，主线一句话——**让 Agent 在生产里可控**。

具体是两层：下层是能力注册与分发，能力以注册表登记，Gateway 做可见集裁剪和精确 id 分发，执行前落 Policy 硬闸；上层是 LangGraph 的 Supervisor 编排与自主规划，外面套一层 HITL 快照审批——高危写操作不走「配置放行」，走单次人工确认：冻结快照、管理员审快照、参数变了旧审批作废。

本体论这块我不多讲，因为它是我的学习方向不是交付史，只在个人开源库里做过一个轻量元模型。**想先问一句：这个平台服务的是车内用户，还是内部员工？**

## 四、本体论的准确口径（**这一节最重要，别讲错**）

> 风险点：JD 明确提了本体论，面试官一定会问；但**讲多了是吹，讲少了是空**。下面是"能说 / 不能说"的硬边界。

### 4.1 ✅ 可以说的（都是真的，且经得起追问）

`https://github.com/Cyning12/SpecWave/blob/main/assets/ontology.yaml`，公开可查：

- **类（classes）**：分了 `domain: Package` 与 `domain: Instance` 两层；`Track` 有 6 个子类（GraphTrack / WikiTrack / StandardsTrack / ProcessTrack / VerifyTrack / IDETrack）
- **类型化关系（relations）**：`embedsInto` / `blocks` / `governedBy` / `produces` / `hasGate`，**每条都带 subject、object 和 cardinality**
- **公理（axioms）独立命名空间**：用 `ONTO-` 前缀，**与代码层公理（graph axioms）显式分开**——这是本体工程里"分层"的正确做法
- **校验器**：`npx spec-wave graph ontology check`，profile 是 `spec-wave-shacl-subset/v1`，且**文件头明确写着"SHACL 语义子集不声称标准合规"**
- **人闸（human_gates）编码进本体**：`HG-TASK-DRAFT` / `HG-SPEC-SIGNOFF` / `HG-AUDIT-R1` / `HG-RELEASE`，每条都用 `blocks` 关系声明它阻断哪些 Hat
- **边界裁决（ONTO-OPEN）**：明确声明这是「**自用元模型 · 不提供自定义本体能力**」，并配了复议触发条件与走人闸的变更路径

### 4.2 ❌ 不能说的

- 不要说「我们一直在解本体要解的三个问题」——**这是 v2 的错误，已删**。在职期间没做过本体工程。
- 不要说「落地过企业级本体 / 知识图谱平台 / OWL 推理」。
- 不要把技术图谱（tech_graph）包装成本体——那是**代码模块依赖的机器真值**，是另一个东西，混着讲会被拆穿。
- 不要主动展开类层次设计、OWL 表达能力、推理机选型这类话题。

### 4.3 被直接问「你落地过本体论吗」怎么答

**直接承认，不要绕**：

> 「没有。企业级本体工程我没有做过。我做的是一个开源项目里的**轻量元模型**——类、带基数的关系、公理独立命名空间，加一个 SHACL 语义子集的校验器，以及和它配套的人闸。规模很小，但**它是被校验的、不是文档**。」

### 4.4 若对方继续追问本体论（**只用这一句，然后停**）

> 「我目前的一个不成熟判断是：本体在这类平台里应该落在**约束层**而不是检索层。我那份文件里其实就体现了这个——`human_gates` 和 `blocks` 关系是直接把『谁能阻断谁』写进本体的，不是写在文档里当建议。但这个判断我还没在有规模的系统上验证过。」

**说完就停，把话头交回去。** 这一句的价值在于证明你「想过方向」，而不在于证明你「做过」。

## 五、逐句设计意图

| 句子 | 意图 |
|---|---|
| 「11 年研发，最近两年专注让 Agent 在生产环境里可控」 | 立刻收敛焦点，避免被当成「什么都会一点」 |
| **「根据猎头初步了解 + 公开信息，我判断这次重点在多 Agent 架构；有偏差请随时打断」** | **定调句。** 同时做到三件事：承认信息不完整、给出判断、请对方校准。**比「我不铺履历了」自然得多，也不显得强势** |
| 判断①：难的不是编排，是「谁有权调什么」 | 打掉「你会用编排框架」这个低层次认知，把讨论拉到授权模型层 |
| 判断①的字段名（`capability_id` / `risk_level` / `side_effect`） | 字段级细节 = 只能来自真做过的人。同时预埋追问方向（引导往你厚的地方打） |
| 「模型决定不了名单里有什么」 | 一句话讲清**模型在场性**——这是你全部安全叙事的根 |
| 判断②：冻结快照 → 管理员审快照 → 参数变则作废 | **对口命中最强的一枪**。北汽福田原话「关键操作保留人工确认」 |
| **本体论只给「定位」不给「方案」** | **少讲是策略不是示弱。** 用「我更想先听你们的期望落点」把主动权拿回来——反而比硬讲更高级 |
| **主动交代边界** | 资深与初级的最大分水岭。先说出它会在哪破，面试官就没得扣分 |
| 结尾二选一：「车内用户还是内部员工」 | **无 JD 场景下的核心动作**。一句话定线，后面所有例子按线调 |

## 六、三种现场开局的应对

**开局 1：面试官说「你先自我介绍一下」** → 直接用主版，结尾抛出二选一。

**开局 2：面试官先讲岗位（说明他也在试探你）** → **不要打断，听完再讲**，但把主版顺序倒过来：先接住他讲的内容，再说判断。句式：
> 「你刚说的 XX，和我的判断是一致的 / 不太一样——我说一下我的两句判断，你看差在哪。」

（**先接住，再给观点**。资深面试最忌「没听完就开始讲自己」。）

**开局 3：面试官直接问「你了解我们吗」** → **不要背新闻**（公开数字有三个互相打架的口径，背错是硬伤）。用"业务线判断题"把球踢回去：
> 「公开能看到你们至少有两条完全不同的 Agent 线：一条在车上，走『1 中枢 + N 垂域』；另一条在企业内部，走流程和系统提效，比如工厂那套。**这两条的本体论落点差别很大**——所以我想先确认，这个岗位是在哪一条上？」

简历里有一行别人没有的：**2012.08–2015.05 中铁十六局 · 盾构机系统操作手**（本科计算机 → 现场三年 → 2015 回研发）。

**为什么对北汽特别值钱**：北汽福田那套工厂 Agent 的场景是「经营管理、生产协同、**安全巡查**、任务闭环」，还接了现场监控、排查「设备未断电」。这些是**工业现场**的事。一个在隧道掘进机上做过系统操作手、后来写代码的人，对「设备状态、安全规程、现场作业」有真实体感——这在车企面试里几乎独一份。

**怎么用**（**不要放进自我介绍**，放在被问到时）：
- 被问「你为什么想来制造/汽车行业」→ 这句就是答案，比任何情怀都实在
- 被问「你怎么理解工业现场的需求」→ 你有发言权
- 被问「非科班 / 转行」→ 反而是「科班毕业 → 去现场三年 → 回本行」，逻辑是顺的

**一句话版本**：
> 「我本科是计算机，毕业先去中铁十六局做了三年盾构机系统操作手，2015 年才回到研发。所以工厂现场、设备状态、安全规程这些东西，我不是从需求文档里认识的。」

**用不用你自己定。** 好处是差异化极强、和北汽福田那条线天然咬合；风险是可能被读成「履历不纯」。**我的建议：用，但只在被问到时用，且只用一句话。**

## 九、刻意不说的

1. **不按 2016–2024 时间线讲三阶段。** iOS 路由中间件、Uniapp 分包、B2B 小程序——只作为「工程底座」一句话背书，且只在被问时讲。

## 十、收口问题的备选（按场景挑）

**A. 定线用（无 JD 场景首选，就是主版结尾那句）**
> 「这个平台主要服务车内用户，还是内部员工？两边对象和约束完全不同，你们更靠哪边，我后面的例子就往哪边调。」

**B. 本体论向（若对方对本体论明显在意）**
> 「本体论这件事，你们期望它落在哪一层——是让模型更会选，还是让副作用边界更严？我个人倾向后者更早见效，但想先听你们的判断。」

**C. 治理向（适合已有存量 Agent 的团队）**
> 「我看公开报道，你们在生产上已经在跑不少 Agent 了。那**现在最难的是把它们收进同一条治理线，还是继续铺新的？** 如果是前者，我最想聊的是可见性和策略闸这两层。」

三句的共同点：**先给假设，再问结论。** 这比「请问你们平台怎么设计的」高一个层级——它证明你已经对着他们的场景想过一遍了。
