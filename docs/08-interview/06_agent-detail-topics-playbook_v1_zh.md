## 1. Checkpointer 与状态持久化

### 1.1 「高频 super-step 写入，DB 会不会爆？有没有 TTL？」✅/❌

**口述（60s）**

> 分两半答，因为**这两半在我这儿状态不一样**。
> 已经有的：checkpointer 只有一个真源开关——`LG_RAG_HTTP_CHECKPOINTER`，值等于 `postgres` 才用 PG，否则是进程内 saver。而且 HTTP 入口和 SSE 入口**必须走同一把闸**，否则会出现"invoke 落盘了、SSE 没落盘"，恢复时找不到挂起点。
> **没有的**：TTL、归档、大字段剥离、只保留最近 N 个——**一个都没有**。我第一期的量级小，DB 膨胀还没显形，所以我没做。如果现在要做，我的顺序是：**先定位"谁在膨胀"**（是 checkpoint 的 channel values 还是 writes），再做三件事：按 `thread_id` 归档 + 大字段外置（State 只留引用）+ 按时间 TTL。
> 但有一件**比清理更重要的事我已经做了**：**State 里不放本体**。检索证据本体不进 state，只进 `chain_meta` 这种质量信号子集——这是设计上的"不写入"，比事后剥离可靠。

**【落地参考】**

- 开关与 DSN 转换：`app/ops/lg_rag/checkpointer.py:25-43`（`CHECKPOINTER_ENV = "LG_RAG_HTTP_CHECKPOINTER"`；`postgresql+asyncpg://` → `postgresql://`，底层 psycopg v3）
- 每请求装配（`setup=True` 幂等建表）：`app/ops/lg_rag/router.py:177-180`
- 设计上不入 state：`app/ops/lg_rag/state.py:200-203`（注释原文"evidence 本体不进 state（黑盒原则）"）
- TTL/清理/归档：**全仓未发现**；checkpoint 表与业务表同库不同表仅见于 `checkpointer.py:14` 注释

### 1.2 「发版后新增/删除 State 字段，旧 checkpoint 恢复报错怎么办？」⚠️

**口述（75s）**

> 我没有迁移函数。我的做法是**"加字段必须能容忍老数据"**：State 的每个字段在 docstring 里都写清楚"老 checkpoint 没有这个键时怎么办"，代码里一律** `state.get(k) or 默认值`**。所以**新增字段天然兼容**。
> 但**跨大版本升级有一类是真的救不回来的**，这个我踩过，也是我认为这块最值钱的一条经验：**langgraph 0.2 → 1.2**，旧格式的 checkpoint 能读回 `values` 和 pending task，但 `task.interrupts` 是空的——新栈认不出"这里挂着一个 interrupt"。这时候硬喂 `Command(resume=...)`，会在框架内部炸一个 `TypeError: 'Interrupt' object is not subscriptable`。
> 我的处置不是"try 一下看运气"，而是**显式判死**：这种情况单独判成 `stranded_checkpoint`，返回 **409**，提示是"有未完成任务但没有 interrupt 元数据，**多半是升级前旧格式，无法恢复，只能作废重开**"。而且它和"这轮已经跑完了"（`not_interrupted`）**必须分开**——两者都返 409，但给人的下一步动作完全不同。
> 更重要的是一条**运维纪律**：升级前必须**排空在飞的审批**。我因此写了一个审计脚本，退出码是三态：0 = 没有在飞的审批（可安全升级）；1 = 还有没排空的；**2 = 审计本身做不了**。第三个最关键——"查不到 pending"和"压根没查成"必须分开，否则审计就变成了一盏假绿灯。

**【落地参考】**

```python
# app/ops/hitl/resume.py:236-248
if not [t for t in tasks if getattr(t, "interrupts", None)]:
    raise ResumeError(
        "stranded_checkpoint",
        f"thread {thread_id[:32]} 有未完成任务但没有 interrupt 元数据 —— "
        "多半是升级前旧版本格式的 checkpoint，无法恢复（只能作废重开）",
    )
```

- 状态码映射（409）：`app/ops/hitl/router.py:294`
- 字段级兼容口径：`app/ops/lg_rag/state.py:190-281`（逐字段写"老 checkpoint 无此键"的行为）
- 升级前审计：`scripts/acceptance/hitl_drain_audit.py:16-19`（退出码语义）、`:55-58`（`AuditUnavailable`）、`:71-83`（`resumable`/`stranded`/`finished`/`missing` 四态）、`:102-104`（用真图判，不猜）

### 1.3 「每个 super-step 都写 DB，高并发下 IO 打满怎么办？」❌

**口述（50s）**

> 我**没做过写入侧的性能优化**——checkpoint 是同步 await 写、没有批量提交、没有分区表、没有读写分离、也没有用 Redis 做热缓存。这是实话。
> 但同样是"写"，我有一个地方**故意做成异步的**，可以说明我的判断标准：**SSE 事件落盘是 fire-and-forget 的**。因为它是**旁路**——丢了不影响这次回答的正确性，只影响回放。而 checkpoint 是**主路**——它一丢，HITL 的挂起点就没了。所以我的规则是：**主路的写必须同步落定，旁路的写才允许 fire-and-forget**；反过来（为了吞吐把主路改成异步）是在拿可恢复性换延迟。
> 真要做到高并发，我会按"先旁路、后主路"的顺序做：旁路先批量化+分区表；主路只做一件事——**把 checkpoint 的存储挪到独立的库或实例**，先隔离故障域，再谈吞吐。

**【落地参考】**

- SSE 事件落盘异步：`app/ops/lg_rag/sse_stream.py:332-334`（`asyncio.create_task` + done_callback）；约束注释在 `:281-282`（"禁止 await persist 串在入队/yield 前，否则每 chunk 被 DB commit 卡节奏"）
- checkpoint 写入侧优化（批量/分区/缓存）：**未发现**

### 1.4 「要做时间旅行（回退到出错前）怎么办？」❌

**口述（50s）**

> **时间旅行我没做。** 全仓没有 `get_state_history` / `update_state`。

### 1.5 「多个并发 execute 同时写 State，reducer 冲突怎么解？」✅

**口述（75s）**

> 这个真踩过，而且**踩出来的结论是"不能只靠 reducer 的默认语义"**。
> 我那张 supervisor 图现在是**同批并发下发无依赖子任务**的。一旦并发，State 的合并就必须逐字段想清楚，否则会出现两类脏数据：**按到达顺序错位**（后返回的结果对到了别人的计划项）和**重复终态覆盖**。
> 我自定义的合并规则是这样的：`subtask_results` 的 reducer —— `None` **表示清空**（Critic 回环要重来时用），**带计划 id 集合时**：计划外的 id 直接丢、同一 id 已经有过终态的后到条**丢弃不覆盖**、既没 `output` 也没 `error` 的也丢。另外两个字段用最朴素的语义：步数计数器取 **max**（不能相加，否则并发时会虚高）、预算耗尽标志取 **or**（任一分支耗尽就是耗尽）。
> **收齐条件也一起改了**：不能拿"结果列表长度等于 N"当收齐——那正是错位的来源；必须是**"本轮计划里每个 id 都有一条终态"**。

**【落地参考】**

```python
# app/ops/lg_rag/state.py:259/279/280 —— reducer 挂在字段注解上
subtask_results: Annotated[list[dict], merge_subtask_results]
supervisor_step_count: Annotated[int, merge_supervisor_step_count]
supervisor_budget_exhausted: Annotated[bool, merge_budget_flag]
```

- `merge_subtask_results`：`state.py:143-187`（`None` → 清空；`replace` + `plan_ids` → 先裁剪；计划外 id 丢；已终态同 id 不覆盖；无终态丢弃）

## 2. 事件可靠性 / MQ / 回调

### 2.1 「MQ 消息重复消费怎么办？」❌（本仓没有 MQ）

**口述（60s）**

> 先说清楚：**我这边没有 MQ**——Kafka、RabbitMQ、Redis Stream 全仓零命中。我的事件链路是 **SSE + Postgres 事件表**，异步回调走**签名 HTTP**。
> 但"重复"这个问题我是**正面解决过**的，只是解在了另一个位置：**幂等层**。我的兜底不是"消费端去重表"，而是**写侧幂等键 + 租约**：键由 `(tenant, 能力, args)` 派生，状态机三态——没有记录就领走执行；`done` 就直接命中；`in_flight` 且租约没过期就**拒**（报 `duplicate_id`）。
> 两个设计要点值得说：**租约用数据库时钟判过期**，不用本机时钟，多实例才不会各自认为对方超时；失败**只在确知没有副作用时**才释放键，超时/连接错一律保持 `in_flight` 等租约自然过期——**宁可拒，也不冒重复执行的风险**。
> 如果换成 MQ，我会把同一套键搬过去当消费端幂等键：**重复消费的解法和重复提交的解法是同一个**——先给这次"业务动作"一个稳定的身份，再谈去重。

**【落地参考】**

- 幂等状态机与语义（"同一幂等键不在本层发两次请求"，不是回放原始响应）：`app/ops/capability/idempotency.py:3-24`、`:46-51`（DB 时钟判租约）
- 表与唯一约束 `(tenant_id, idempotency_key)`：`app/db/models.py:375-405`
- 释放纪律（fail-closed）：`app/ops/capability/adapters/http_generic.py:50-51`、`:592-593`；in-flight 拒：`:543`
- MQ：**全仓未发现**

### 2.2 「消息顺序性怎么保证？」✅（用 seq，不用分区）

**口述（60s）**

> 没有 MQ，所以没有分区键。我用的是**单调 seq**：每次 run 的所有帧共享一个自增计数器，**从 1 开始**，`delta` 帧和进度帧**共用同一个序列**——不能各算各的，否则回放时会漏帧或乱序。keepalive 是 SSE 注释，**不占 seq**。
> 游标就是 `{run_id}:{seq}`，回放是 `seq > after_seq` 严格递增过滤，带**归属校验**（别人的 run 查不到，404）。还有个细节：**HITL 中断恢复后接着编号**，取已有 max 再 +1——否则续跑那段会和前面的序号撞车，回放直接废掉。
> 如果迁到 MQ，顺序性的答案就是**按 thread/会话做分区键**，让同一线程的消息进同一分区；但底层我仍然会保留 seq ——**分区只保证投递顺序，seq 才保证消费端能自证"我没漏"**。

**【落地参考】**

- `seq` 从 1 起、emit 闭包单点自增、keepalive 不占号：`app/ops/lg_rag/sse_stream.py:279`、`:10`、`:358-359`
- cursor 定义与解析：`app/ops/lg_rag/sse_replay.py:12-14`、`:17-33`
- 回放（严格递增 + 归属校验）：`app/ops/lg_rag/event_store.py:98-128`；端点 `app/ops/lg_rag/router.py:308-349`（非法 cursor 422 / 跨用户 404）
- 唯一约束 `(run_id, seq)`：`app/db/models.py:261-280`、`:316-337`
- HITL 续跑接着编号：`app/ops/lg_rag/event_store.py:72-84`

### 2.3 「消息积压 / MQ 挂了 / 回调网关高可用怎么办？」❌

**口述（60s）**

> 这三条我**都没有生产级答案**，因为我没上 MQ，也**没有多副本无状态部署**——我这边是单实例自用的量级。
> 我能给的是**判断和顺序**：
> **积压**的第一反应不该是扩容消费者，而是先分开"**慢**"和"**卡**"——消费端处理慢可以水平扩容；但如果是下游同步阻塞（老 OA 大量这种接口），扩容只会把压力原样放大给下游。所以先做"**入队即返回 + 回执查询**"这条退化路径，再谈消费者数量。
> **MQ 本身挂了**这件事，正确的态度是**承认它是新的单点**：要么集群化，要么在**入口处留本地兜底**。我这边有一个可以类比的落盘：**审批决定先落本地、再发起回调**——注释写得很直白："回调失败也要留下'批过了'的证据"。
> **回调网关高可用**：我只有"无状态"这一半（无会话、可多副本），**没做多副本部署**。要补的第一件事不是扩容，是**把"决定已记录"和"回调已送达"拆成两个状态**——我这边就是这么做的：回调失败也返回 200，但带一个 `local_decision_recorded: true`，**绝不假装回调成功了**。

### 2.4 「第三方回调怎么保证不是伪造的？」✅

- 死信队列 / 定时补偿任务：**回调路径未发现**（无 apscheduler / `@Scheduled`）；但**向量影子写路径有真 DLQ**（`app/ops/rag/shadow_write.py:149-184`，表 `ops_qdrant_dlq`）——**别笼统说成"我们没有任何 DLQ"**
**口述（60s）**
  > **HMAC + 时间窗 + nonce**，三个一起上，缺一个都不行。
  > 签名是对 `"{ts}.{nonce}." + 原始 body` 做的 HMAC-SHA256，输出 `sha256=<hex>`。**对原始 body 签名**这一点很重要——如果你先反序列化再签名，字段顺序一变签名就不稳。时间窗是 ±300 秒，防重放靠 nonce 去重，nonce 集合有上界并做淘汰（否则它会变成一个无限增长的字典，那就是内存泄漏）。
  > 还有两条工程纪律：**空密钥直接抛异常，不允许"没配密钥就放行"**；以及**两侧必须是同一份实现**——所以我在 Java 侧和 Python 侧各写了一份、并且用**同一组测试向量**互相钉死。跨语言签名这种东西，"两边都跑得通"不等于"两边算的是同一个值"。

**【落地参考】**

- Java 侧：`ops-desk-mock-oa/src/main/java/com/cynaya/mock_oa/support/HmacSigner.java:33-47`（对 `"{ts}.{nonce}." + rawBody` 签名；空密钥抛）

### 4.3 「每次重试都带完整历史，Token 成本怎么控制？」✅

**口述（60s）**

### 4.4 「Pydantic 校验失败重试几次？会不会死循环？」✅

**口述（60s）**

> 上限是硬的：`max_retries` 默认 **3**，**总尝试次数 = max_retries + 1 = 4 次**，这是代码里写死的加法，不交给模型。纠偏提示会把失败原因喂回去，但**要求完整重生成，禁止只补那几个错字段**——因为局部打补丁会让整体结构越来越不一致，比重新生成更贵。
> 三个细节值得说：**原因截断到 400 字符**（否则纠偏提示自己变成违规内容）；**有一个** `no_retry=True` **的口子**，命中时连 reason 都不注入——用于"这条规则本身不能出现在 prompt 里"的场景；**失败时绝不返回半成功数据**，`ok=False` + `data=None`，宁可整条失败。
> 这条纪律我很在意：**半成功数据是 Agent 系统里最难查的一类 bug**——它看起来有值、下游照常消费，但缺的那部分没人知道。

**【落地参考】**

- 重试上限与总尝试次数：`app/ops/structured_output/complete.py:23`、`:110`、`:129`（`DEFAULT_MAX_RETRIES = 3`；`max_attempts = max_retries + 1`）

### 4.5 「怎么区分『用户参数错』和『系统故障』？」✅

**口述（60s）**

> 靠**结构化的失败成因**，不靠错误码、更不靠解析文案。
> 为什么不能再靠错误码：`upstream_error` 这一个码下面混着四种完全不同的东西——传输层不响应、5xx/429、**200 里嵌了业务失败码**、以及我们自己没配好 base_url。**只看 code，用户填错 5 次参数会把一个完全健康的能力熔断 60 秒**；只看错误文案，文案一改熔断就静默失效。所以我给每个失败附一个 cause（transport / http_status / business / local），熔断只认前两类。
> 重试策略也顺着这个分：**LLM 侧只对 408/429/5xx 标可重试**（4xx 不重试）；**工具侧 GET 最多 2 次、写操作绝不自动重试**。写不重试的理由是：**超时 ≠ 失败**，重发会建出第二张单。
> 最后一层是给模型看的：**错误码词表七个、不增**，而且**不外泄下游原文**——下游可能把内部细节写在错误里，模型拿到也做不了决策，只会继续瞎试。

**【落地参考】**

- cause 四分类与熔断只认环境类：`app/ops/capability/errors.py:50-93`（注释即"文案一改熔断就静默失效"）

### 5.1 「Prompt 怎么管理？改了效果变差能回滚吗？」⚠️

**口述（60s）**

> Prompt 在代码仓里，是**按 id 组织的模板字典，每条带** `version` **字段**；有少量 prompt 能用环境变量选版本（比如 grader 的 v1/v2）。

### 5.2 「LLM 调用超时怎么办？」✅

**口述（60s）**

> 超时是**显式的、按阶段分设**的，而且四个值不一样：连接 10 秒、**读取 180 秒**、写入 30 秒、连接池获取 5 秒。
> 为什么读取给到 180 秒这种"看起来很长"的值——因为**这是一个"生成式"调用，不是查询**：一次长回答的流式生成确实可能到分钟级。**把 read timeout 设成 10 秒，只会让长回答全部失败，而且失败得很随机。** 所以我宁可给足 read，把"防挂死"交给连接超时和整体墙钟预算。
> 也要说清楚我的短板：**LLM 这一层我没有通用重试、没有退避、没有抖动**——我只有一个"换模型重试"的链（按顺序换模型，但没有 sleep）。熔断也只做在工具层，LLM 层没有熔断。这些是我知道的缺口，不是我认为不必要。

**【落地参考】**

**口述（60s）**

### 6.5 「怎么防止重复提交？」✅

**口述（60s）**

> 三个能体现"真做过"的细节：
> 一是**幂等命中要重放上次的业务字段**，不能只回一句"重复了"。只回 `duplicated=True` 加一个回执 id，调用方第二次拿不到 `ticketId`，业务上这次调用等于白干——**防重保住了，可用性丢了**。

## 8. 安全与对抗

### 8.1 「怎么防 Agent 被当成跳板打内网？」⚠️

**口述（60s）**

> 我做对了一件、漏了一件。
> **做对的**：**出站默认不走任何环境代理**——因为我踩过一个特别隐蔽的坑：本机设了 `HTTP_PROXY` 时，客户端会把打给 `127.0.0.1` / 内网的请求送到出口代理，然后你拿到一个**看不懂的 502**，看起来像网络故障，实际是请求根本没到目标。所以我的出站 opener 默认是空 ProxyHandler，需要走代理必须显式配。**这条对任何设了 HTTP_PROXY 的企业环境都是必须的。**

> 补的顺序我会这样排：**先做白名单（按域名/网段）→ 再做协议限制（只允许 https、禁止跳到内网网段）→ 最后才考虑沙箱化执行**。因为前两者是配置级的、可审计的；沙箱是最后一道，不是第一道。

## 9. 成本与性能

### 9.1 「延迟怎么优化？」✅（有手段，无量化）

**口述（60s）**

> 四个手段，**但我要先说清楚：我没有 P95 这类量化基线**（没有压测、没有 SLO）。所以下面这些是"设计上的优化"，不是"实测的收益"。
> 一是**并发化**：无依赖子任务同批下发（上限 4），这一步的延迟收益是结构性的——从串行 N 次往返变成"最慢那条"。
> 二是**流式**：SSE 首帧尽早出，用户感知的延迟不是总时长，而是"多久看到第一个字"。还有 keepalive 帧（它不占 seq，纯保活）。
> 三是**旁路写入异步化**：事件落盘 fire-and-forget，不让每个 chunk 等一次 DB commit。
> 四是**减少 LLM 往返**：结构化输出失败时**完整重生成**而不是逐字段修补（少一轮交互）；只有"低质且重试次数未到"才触发改写，且改写有熔断封顶（避免自我复读式的重试）。

**【落地参考】**

- 并发下发：`app/ops/lg_rag/multi/graph.py:96-105`、`multi/nodes.py:63`
- 流式与 keepalive 不占 seq：`app/ops/lg_rag/sse_stream.py:10`、`:341-345`
- 旁路异步：`sse_stream.py:332-334`
- 改写熔断：`app/ops/lg_rag/graph.py:160`（`LG_RAG_MAX_RETRIES` 默认 2）

### 9.2 「怎么平衡准确率和成本？缓存怎么做？」⚠️

**口述（60s）**

> **权衡上我只有两种手段，没有"分层路由"**（没有"简单任务走小模型"这套）。我的两种是：
> **一是"换模型重试"链**——某个模型调不通时按序换下一个（不是熔断后降级，是链式换），而且**标了** `test_only` **的模型会被先过滤掉**，避免测试模型混进生产链路。
> **二是"不重试"的口子**——有些场景宁可失败也不重试（比如结构化输出里遇到不能进 prompt 的规则时，`no_retry` 连纠偏原因都不注入）。**"不花钱"也是一种成本策略。**
> **缓存**：我只有清单声明式的缓存降级（某个能力的降级动作是"回缓存值"），**没有语义缓存**。
> 关于语义缓存我想说一个风险：**它是"看起来最省"、实际最容易变成静默错误的优化**。命中语义缓存意味着你回了一个旧的答案，而用户以为它是新的——所以我如果要上，会要求缓存结果**必须带生成时间和来源标记**，和降级标记是同一套要求。**带标记的缓存是优化，不带的缓存是 bug 生成器。**

**【落地参考】**

- 模型 fallback 链与 `test_only` 过滤：`app/llm/providers/bailian.py:33-58`、`:70`；链定义 `app/llm/model_catalog.py:28-34`
- 降级动作里的缓存：`app/ops/capability/fallback.py`（action 取值含 cache，必须在清单声明）
- 降级必须带标记且进 output（红线 R13）：`evals/agent/redlines/capability_v1.yaml:136-160`
- 语义缓存 / 分层路由：**未发现**

### 9.3 「限流怎么做？」⚠️（**别把它说成限流**）

**口述（60s）**

> 我没有令牌桶、没有 QPS 限制，也没有 per-user 速率控制。我有的两道闸**性质不一样，不能叫限流**：
> **会话配额**（每会话调用数 64、写操作数 8）——它管的是**"一个会话总共能用多少"**，是总量上限，不是速率。它的价值在于兜住"幻觉在一个步里反复打同一个写能力"。
> 熄火开关——管的是**"这个能力还能不能用"**，是开关，不是限流。
> 这两个我都不叫限流，因为**限流的语义是"速率 + 排队/拒绝策略"**，我这边没有排队，只有拒绝。如果要真做限流，我会先说清楚一件事：**被限流之后的正确行为是什么？** 是排队（用户等更久）、还是失败（用户看错误）、还是降级（用户拿到次优结果）——这三个的产品含义完全不同，**先定这个，再选算法。**

**【落地参考】**

- 会话配额与 kill switch（性质区分）：`app/ops/capability/budget.py:38-49`、`:100-128`、`:154-190`
- 令牌桶 / 速率限制：**未发现**

## 10. 架构演进

### 10.1 「新增业务模块怎么扩展？图会越来越复杂。」✅

**口述（60s）**

> 我有一条**明确的扩展优先级：先加能力，其次加子图，最后才加条件边。**
> 理由：**加能力是"数据层"的变化，不动控制流**（清单加一条 + adapter 加一个函数），回归面最小；**加子图是"封装一层"，控制流仍然只有一条主线**；**加条件边是动主干**——它会让所有既有路径都要重新想一遍"这条边会不会被走到"。
> 所以我看到"图越来越复杂"的第一反应不是重构，而是问：**这件事能不能做成一个能力？** 能，就不要加节点。**能力层是这套系统里最便宜的扩展点，因为它的验证成本最低**——一个能力的正确性可以用单测钉死（形态、门序、错误码），一个节点的正确性要靠集成图和状态流转去验。
> 我在这条纪律上还加了一个约束：**能力的可见范围可以按域逐批放开**（第一期只读、按 kind/标签的基线），所以"上线一个新能力"不等于"全量放开一个能力"——**扩展和放开是两件事，必须能分开控制。**

**【落地参考】**

- 基线按 kind / 标签逐批放开：`app/ops/capability/baseline.py:33-44`
- 额外清单走显式环境变量（失败域隔离，不扫目录）：`app/ops/capability/manifest.py:59`、`:149-156`
- 单文件加载失败不影响其它文件：`app/ops/capability/manifest.py:196-199`

### 10.2 「怎么从单体 Agent 演进到多 Agent？」⚠️

**口述（60s）**

> 我的路径是**保留旧图当基线、新增一张图**，不是原地改造：`basic`（只一条 RAG）→ `router`（加了路由与质量评估）→ `supervisor`（多 Agent）。
> `basic` **我一直留着当对照基线**——不为"新的一定更好"做无基线的替换。换掉一个实现之前，我要有**同口径的旧数据**，否则"变好了"只是我的感觉。
> 多 Agent 这边我用的形态是**主从（supervisor + 工人子图）**，共享同一份状态与 checkpointer；工人的会话隔离靠 `thread_id = subtask_id`。
> **要诚实说的**：我没有做过 A2A / 跨进程工人 / 多 Agent 互相对话。我的"多 Agent"是**同一进程内、同一张图里的分工**，不是多个独立 Agent 之间的协议。这两件事的工程难度差一个量级——**前者是编排问题，后者是分布式系统问题。**

### 10.3 「多租户隔离怎么做？」✅

**口述（60s）**

> 三个维度，都落在**数据可见性**上，而不是落在"记得做过滤"上：
> **能力维**：`tenant_scoped` 的能力必须声明租户谓词怎么传给下游（加载期强校验），缺谓词直接拒。

> **会话维**：thread 按用户解析（`resolve_thread_for_user`），不是拿一个全局 thread id 到处用。
> 如果要往 SaaS 走，我会补的第一件事是**资源配额按租户**——现在我的配额是"每会话"，跨租户没有总量约束；第二件是**审计按租户可导出**。**多租户最难的不是隔离，是"证明隔离住了"**，所以我会优先做能自证的东西（审计导出、可见集差异报告）。

### 10.4 「怎么从 ReAct 演进到 Plan-and-Execute？」✅

**口述（60s）**

> 我这张图**两边都有**，而且是刻意分工的：
> **外层是 Plan-and-Execute**：意图识别 → 算可见能力集（白名单 ∩ 策略）→ **一次拆出 ≤4 个子任务** → 分派执行 → 汇聚 → critic 复核。
> **内层仍然留 ReAct**：某个子任务内部允许"观察—再行动"的轮次（默认 2 轮），到顶就收口。
> 为什么不全上 Plan：**计划越长，中途环境变化的概率越高**，而重规划的代价是"已执行部分可能白做"。所以我用"**小计划 + 局部 ReAct**"来平衡：**计划的每一步都小到"重来也不心疼"，环境变化留给子任务内部的 ReAct 去消化。**
> 还有一条硬纪律：**全局预算优先于局部回环**——否则"子任务重试环"和"critic 回环"会互相打架，max_steps 形同虚设。

**【落地参考】**

- 图拓扑与条件边（含 critic 的出边）：`app/ops/lg_rag/multi/graph.py:54-105`

- 全局预算优先于 critic 回环：`app/ops/strategy/critic.py:54-56`、`:80-81`

### 10.5 「怎么引入人工审核？」✅

**口述（75s）**

> 两个层次，**只有一种情况会叫人**。
> **能力层**：写操作与高危能力**必须在清单里声明"要人工确认"**，否则加载失败——这不是"运行时提示一下"，是**清单层面的硬要求**。方向也固定：**先声明，再上线**。
> **编排层**：唯一的叫人原因是——**要满足新计划，必须重跑一个已经执行过的、不可变前缀里的步骤**。因为改参数 = 换幂等键 = 一次新的写，**这会产生新的副作用**。除此之外的拦截（前驱失败、前驱输出缺字段）都**不需要人**，它们只是"这一步不执行"。
> **这就是我的设计取舍：审批是有成本的，到处挂 HITL 等于没有 HITL。** 我只在最贵、最不可逆的那个点上叫人 —— 会产生新副作用的时候。
> 机制上：申请落库、回调签名（HMAC + 时间窗 + nonce）、决定后再恢复图、事件编号接着排。

**【落地参考】**

- 清单层硬要求（写 / 高危必须 hitl）：`app/ops/capability/manifest.py:711-719`
- 编排层唯一的人闸原因：`app/ops/lg_rag/multi/step_contract.py:56-67`（`HITL_REASONS = frozenset({BLOCKED_PREFIX_TOUCH})`）

## 11. 统一话术：「项目里没做过」怎么说才不掉分

> 上面标 ❌ 的项加起来有二十多条。**被问到时的正确姿势是"三段式"，不是硬答。**
> 顺序不能变：**先认、再迁移、最后给最小可验证动作。**

### 模板

> **① 认（一句话，不解释）**
> 「这个我没做过。」
>
> **② 迁移（把它和我做过的最近似的东西挂上）**
> 「不过我做过最接近的是 X，它们的共同点是 Y，差别在 Z。」
>
> **③ 给动作（最小可验证的一步 + 怎么验证）**
> 「如果我来做，第一步不是搭全套，而是先做 A；验证方式是 B。」

### 六个高频 ❌ 的标准答案（可直接背）

| 被问 | ① 认 | ② 迁移锚点 | ③ 第一步 + 验证 |
|---|---|---|---|
| **MQ / 消息队列** | 我没上过 MQ | 但重复消费的解法我用过：**幂等键 + 租约 + 唯一约束**，和消费端去重是同一个问题 | 先给业务动作一个稳定身份（键由 tenant+能力+args 派生）；验证：同键并发调 100 次，对端只被请求 1 次 |
| **分布式锁** | 没有锁，只有幂等 | 幂等解决"重复"，锁解决"竞争"——我优先做了前者 | 先上乐观锁（版本号+CAS），冲突率本身就是观测信号；验证：并发改同一单，冲突必须显式报错而不是静默覆盖 |
| **Prompt 注入防护** | 我没做注入防护 | 我认同"提示词里的约束是行为建议、不是安全控制"，所以我的防线在执行层 | 第一层不动模型：把注入想达成的效果（越权调用）用可见集 + Policy + 人工确认堵住；验证：构造越权 prompt，断言下游零请求 |
| **Checkpoint TTL / 膨胀** | 没做清理 | 我做的是"设计上不写入"：证据本体不进 State，只进质量信号 | 先定位膨胀源（values 还是 writes）；验证：压测同一 thread 跑 N 轮，看表行数增长曲线再决定 TTL |
| **时间旅行** | 没做 | 我只有"从挂起点续跑"，没有"回到任意历史点" | 先保证每步有稳定执行 id（Host 签发 subtask_id）；验证：重放同一段计划，幂等键命中、不产生第二张单 |
| **多系统同步 / Saga** | 没做过 | 我能提供的是两块砖：回执（可对账）+ 幂等键（不重复） | 先接对方已有的状态机，不在 Agent 层再编一套；验证：人为制造部分失败，断言"失败的那步有回执、可被对账" |

### 三条纪律

1. **不要用"我们做了一些探索"这种模糊词**——它听起来像没做，而且会被追问到崩。**要么给 file:line，要么说"没做"。**
2. **说"没做"时给代价，不说借口**。句式：「没做，因为我们当时的量级还没到那个痛点」比「当时时间紧」可信得多——**前者是判断，后者是理由**。
3. **每说一个"没做"，后面必须跟一个"我会怎么排优先级"**。资深面试真正在考察的不是"你做过多少"，而是**"你知不知道自己缺什么、以及先补哪个"**。
