# 14 · 万佑智能（北京）后端岗面试作战手册 v2（诚实分层版）

> 面试：2026-10-27 下午 · 浙江万佑智能科技有限公司北京分公司 · 后端研发（初投全栈）。
> 情报源：公司介绍 PDF（2026-10-26）。初创（去年成立，25 人→年底 40-50），海淀西海国际中心 1 号楼 1709，9:30-18:30 双休。
> v2 变更：根据真实经历重新定位——ops-desk 主体为**离职后个人深度项目**（半年沉淀），企业内落地=LangChain RAG 工作流+般果管理台，LangGraph 企业内研究未落地（创新项目调整）。叙事主轴、自我介绍、口径全面重写。

## §1 诚实三层叙事框架（全场总纲）

| 层 | 内容 | 定性话术 |
|---|---|---|
| ① 企业内落地 | LangChain RAG 工作流 + 般果管理台研发 | 「这是我在生产环境真正交付的」 |
| ② 企业内研究未落地 | LangGraph（为创新项目预研，项目调整离职，未上线） | 「研究到一半项目被调整，这是遗憾也是伏笔」 |
| ③ 离职后自研（半年） | ops-desk supervisor 运行时全栈沉淀，小范围使用 | 「把没机会落地的想法做成完整系统自证」 |

**预期管理话术（开场后找自然时机主动给，约 30 秒）：**
> 「我先把背景说实，方便您校准：企业内我生产落地的是 LangChain RAG 工作流和管理台系统；LangGraph 是离职前为创新项目做的预研，项目调整没落地。离职后这半年我把它做成了一个完整的 supervisor 多智能体系统作为深度自研沉淀，目前是小范围使用。所以我的 agent 系统经验，请您定位为**深度个人项目+企业级工程纪律**，而不是生产大规模验证过的——但企业内的 RAG 和管理台是真实生产交付。」

为什么主动说：被动挖出来=诚信问题；主动分层=诚实+结构化思维+自驱，三件事一次展示。初创团队招的就是「没人要求也会把事做透」的人。

## §2 自我介绍（2min v2 · 主轴重排）

> 「您好，我是刘X，X 年后端/全栈经验。【按简历填：上一家 X 年，岗位】。
> 企业内我的主线有两条：一是**般果管理台的后端研发**【填：规模/用户/你负责的模块】；二是落地了一套 **LangChain RAG 工作流**【填：解决什么业务问题/数据规模/效果】。离职前我开始为创新项目预研 LangGraph 多智能体编排，项目调整后没有落地。
> 离职后半年，我把这个方向做成了完整的个人深度项目：一套 supervisor 多智能体运行时——编排层（LangGraph 状态图、并发子任务派发、预算轮次双上限）、能力网关（七层闸链、高危人工审批）、模型层（多 provider 熔断退避、token 用量精确落账）、传输层（SSE 帧流、断连重放）。全部代码、测试、设计文档可查，工程纪律按企业标准走：SPEC→评审→任务分支→PR。
> 了解到贵司智算云做聚合 API 和 Token 服务——用量计量、provider 高可用、配额治理正是我这半年钻得最深的内核；企业内的 RAG 落地经验也能直接复用。后端是我的主战场，全栈能力（iOS/Web 独立交付过）是增值项。」

⚠️ 口径词替换纪律：**「我们团队」→「我」；「线上/生产」→「个人项目/小范围使用」；「已上线」→「已实现并自测」**。红线项（委派令牌/LLM 预算/PG checkpointer/critic stub）=「已实现，按灰度纪律默认关闭」。

## §3 公司资产对位（沿用 v1，口径已校准）

| 他们的需求 | 你的资产 | 所在层 |

| 大模型应用落地 | LangChain RAG 工作流生产经验 | ①企业落地 |
| 聚合 API 高可用 | 熔断/退避/显式降级/degraded 标记 | ③自研 |

注意：①是压舱石（生产验证过），③是峰值（深度天花板）——**讲 ③ 时永远可以锚回 ①：「这个机制在企业 RAG 项目里我遇到过同类问题……」**。

## §4 技术深挖预判八题（骨架不变，口径已校准）

| # | 题 | 答题骨架 |
|---|---|---|
| 1 | 聚合 API 高可用 | 熔断+退避（写路径不参与半开探测）→显式降级 degraded 跟数据走→fallback 声明在清单→「熔断 open+降级率 0=用户硬吃错误，两指标必须一起看」 |
| 2 | Token 计费怎么准 | 只认末帧 usage/不落 0 假账/落表故障不挡主答但告警；幂等三层（声明强制+查重+下游透传） |
| 3 | RAG 工作流企业实战 | 【填：数据管线/切分策略/召回与重排/评估口径/线上问题】——**这题必须成为全场最长的回答之一** |
| 4 | agent 防失控 | 双维预算（32 图步+2 ReAct 轮）+4 子任务上限+高危能力对模型恒不可见+写操作人工审批 |
| 5 | agent 答案质量 | 诚实：过程完备性判定+上下文隔离聚合+规则闸；语义验收是已知缺口，骨架已留位，「只能否决不能放行」 |
| 6 | 故障排查 | 三平面：用户面帧+degraded / 证据面落盘+replay 不重跑 / 运维面 tracing+metrics；error 帧带 stage 定位 |
| 7 | 为什么离职后做这个 | 「创新项目被调整后不甘心——想法没机会验证，就自己把它做完。半年从零到完整系统，SPEC/测试/PR 流程全套按企业标准自约束」 |
| 8 | 个人项目和企业项目差异 | 主动认：「缺真实流量和多角色协作的摩擦——所以我格外重视把失败路径写成测试矩阵，用纪律对冲没有线上反馈的盲区」 |

## §5 企业内项目叙事补全（⚠️ 今晚必须填）

当前最大短板不是 ops-desk 深度，是 ①层的细节弹药。逐条回填：

### 5.1 般果管理台（已确认事实）
- 职责：**前端+移动端从 0 到 1 落地**；最初无 AI 内容。
- 口径已定：**后端不是我做的**——管理台只当「全栈 0→1 交付力」证据，**不做后端证据**；被问后端细节照实说「后端是同事负责，我负责前端+移动端」。
- 叙事位：0→1 交付证明（初创看重）+「后来我在 RAG 项目转到后端主战场」的演进线；别让它占超过 1/4 的叙述时间。

### 5.2 LangChain RAG 工作流（已确认事实+解法方向）
- 业务场景：**企业内文档查询，面向业务+管理员**；新人查询/交接/企业文件；**文档量 ~3k**。
- 链路（已确认）：
  - **切分 v1（企业内）**：滑动窗口 500~800 字 + 重叠 200，主要中文文档——简单可控、当时量级下够用。
  - **切分 v2（研发助手自演进）**：中英文混排/代码段/md 表格场景自研结构化切分——代码块保完整性优先；md 表格能整段保全则保全，跨段时每段重注列定义。**这是「踩过坑后的工程进化」，①→③ 的天然桥。**
  - **Embedding**：BGE-M3（中文友好）。加分点：M3 原生带 dense+sparse 多路——「今天会用它的 sparse 通道直接补 keyword 盲区」，把坑③和模型选型串起来。
  - **向量库**：PGVector——「3k 文档量级，PG 已在栈里，不引入新组件是最优解；选型标准是匹配量级不是追新潮」。务实判断，初创爱听。
  - **重排**：有，细节记不清——走 §5.5 口径；标准方向备着：cross-encoder 精排（bge-reranker 类），top-k 粗排后精排。
- 观测现状（诚实点）：**当时没有线上观测，问题靠使用者反馈**——这正是面试可以反转的点，见 §5.4。
- 三大坑（用户确认）+ 标准解法方向【⚠️ 解法细节用户记忆已淡，标「方向」；面试口径见 §5.5】：

| 坑 | 根因 | 标准解法方向 |
|---|---|---|
| ① 语义对应不上 | 用户口语 query 与文档书面表述错位（「请假怎么办」vs「考勤管理制度第 X 条」） | query rewrite/ HyDE（先改写或生成假想答案再检索）；同义词/术语表扩充；多 query 扩展召回 |
| ② 格式化内容（日志、版本号） | 日志语义稀薄被切分切碎；版本号/编号是精确符，embedding 对「v2.3.1 vs v2.3.2」几乎不敏感 | 按类型定制切分（日志保行/按时间窗）；版本号类走精确匹配+metadata 字段过滤，不进纯向量通道 |
| ③ 向量有结果、keyword 无结果 | keyword 对换说法零容错；反过来版本号类向量也抓瞎——**单路召回各有盲区** | **混合召回**：向量+BM25 双路 + RRF 融合；3k 文档量直接双路全量跑，成本可忽略 |

- 一条主线串三坑：**「3k 文档量不需要复杂架构，需要的是按内容类型分治+双路召回+把 badcase 攒成评测集」**。

### 5.3 LangGraph 预研（未落地）
- 创新项目原本要做什么：【填一句话】
- 为什么选 LangGraph（讲成有判断的选择）：RAG 工作流是**线性链**（LangChain 够用），多智能体需要**状态图**（循环/分支/挂起恢复/显式状态）——LangGraph 的 StateGraph+checkpointer 正好补这个；预研没落地，离职后自己把它做完了（自然过渡到 ③层）。

### 5.4 观测缺口的反转叙事（「当时没有」→「后来我补了」）

- 当时实况照实说：问题靠用户反馈，没有实时观测。
- 反转三段：①**今天我会怎么做**：trace 级 Langfuse（每次查询一条 trace：query→召回 chunk+分数→生成，badcase 可回放定位到是哪一段断的）+指标级监控（零召回率/低分召回率/负反馈率做告警——Langfuse 管案例回放，告警要靠指标层，两个都要）+用户负反馈→golden set 回归防再犯。②**我后来真做了**：自研项目里 tracing 就是按这个接的（OPS_CHAT_TRACER=langfuse，span 记动作不记内容，采样打分）。③金句：**「靠用户反馈发现问题等于把监控外包给用户——观测是召回质量的前置条件，不是事后挂件。」**

### 5.5 解法记不清的诚实话术

「坑我记得很清楚（三类各是什么、为什么发生），当时的具体解法细节淡了——但这个问题的标准解法今天是明确的：【5.2 表里的方向挑着说】。如果今天重做，我会按类型分治+双路召回+golden set 回归来做。」——**把「记不清」转成「设计题现场答」，安全且显功底；千万别硬编细节，被追问两层就穿。**

## §6 期望差距话术（全栈→后端 · 补「经验成色」版）

- 「你投的全栈」：「后端是主战场和职业重心；全栈（iOS/Web 独立交付）是增值——agent 产品的难点一半在后端一半在交互契约，我两头都定得清楚。」
- 「你后端经验主要在个人项目？」：「企业内后端是真实的：管理台+RAG 是生产交付。个人项目是我在 agent 基础设施方向的刻意加深——这个方向企业内没给我战场，我自己造了一个。」
