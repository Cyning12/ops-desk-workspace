## 1. 开场 · 定调与自我介绍（00:00–03:00）

### 1.1 定调句（第一句，必须说）

> 「根据猎头的初步了解和我看到的公开信息，我判断这次聊的重点会落在**多 Agent 的治理与可靠性**上，不只是编排出一个能跑的 Agent。如果和你们实际关注的有偏差，请随时打断我。」

作用：承认信息不完整 → 给出判断 → 请对方校准。比"我不铺履历了"自然，也比背诵公司新闻安全。

### 1.2 主版（约 110 秒）

> 面试官好，我是刘新宁，11 年研发，最近两年在百果园做 Agent 应用与AICoding提效。
>
> 今天我的重点内容是我根据猎头信息和贵司公开资料，判断这次聊的重点会落在多 Agent 的治理与可靠性上，而不只是编排出一个能跑的 Agent。
>
> 对此我根据自己实际经验落地有以下看法：
>
> 第一，多 Agent 真正难的不是编排，而是“谁有权调什么”。编排框架现在很多，一周能出演示；但能力一上几十个、一有写操作，先崩的往往是授权模型，不是编排。所以我做的那一层是：能力以注册表登记，登记表至少包含静态功能声明、执行语义、参数 schema、安全属性、运行时状态。网关做功能可见集裁剪、权限校验、精确能力标识分发，执行前再过一道策略硬闸。模型能决定的是“在名单里点哪个”和“参数长什么样”，决定不了名单里有什么。
>
> 第二，写操作和高危不能靠“配置放行”，得有确定性的刹车。我的做法是**三道递进的防线**，按调用生命周期分：
>
> **第一道，能力被 Agent 获取前——注册/加载期强制。** 写能力必须声明幂等键，必须明确安全策略：是 HITL_REQUIRED、PRE_AUTHORIZED、还是 HITL_EXEMPT。不声明，默认按 HITL_REQUIRED 处理。策略是 HITL_EXEMPT 的，必须安全域审批并写明理由。加载校验不过，能力根本进不了目录。这一步解决的是“坏能力从源头进不来”。
>
> **第二道，执行前——运行时落闸。** 每次调用前，Gateway 默认不自动放行，必须走显式授权路径。高危默认走人工确认；写操作默认需要显式授权——要么运行时 HITL 通过，要么在用户预授权范围内。放行键只有宿主能给，模型写在 plan 里的“已确认”不算数。这一步解决的是“模型不能自己给自己发通行证”。
>
> **第三道，执行失败或失控时——兜底熄火。** 按能力支持紧急停用；每个会话有调用数上限和写操作数上限；下游熔断优先于配额扣减；必要时降级到只读或规则引擎。这一步解决的是“出了事能刹住，不会无限扩散”。
>
> 这套目前是进程内注册表，跨进程和车控这个场景还没验证。不过我觉得它的治理思路对多 Agent 管理有可迁移性。具体怎么适配，得看贵司的业务落点。所以我想先听听贵司期待的方向，再判断哪些能复用、哪些要重做。
>
> 另外对于AI coding提效，落地方案是基于 SDD，先把需求写成可签收的 SPEC 与可验收的 task，再配技术图谱把系统结构、流程边界钉成单一事实来源。它要解决的是 AI 编码常见失控——范围漂移、凭聊天瞎改、实现与架构脱节。强调的HITL，关键节点无签收强制停止任务。  
> 这个纪律包在我离开团队后也在一直更新中。库名已经不是简历中的名字了，现在是SpecWave。
>
> 所以想先确认一件事：这个多 Agent 平台主要服务车内用户，还是内部员工？如果是车内用户，我理解核心挑战是多模态感知输入下的意图收敛和主动服务的安全边界；如果是内部员工，核心挑战可能更偏向跨系统 API 的安全编排。你们目前更侧重哪个方向？

### 1.3 精简版（40 秒，二面/交叉面用）

> 我是刘新宁，11 年研发，最近两年主线是"让 Agent 在生产里可控"。两层：下层是能力注册与分发——可见集裁剪 + 精确标识（id），执行前落策略（Policy）硬闸，写操作和高危还要人工确认；上层是 LangGraph 的多 Agent 编排，外面套人工确认（HITL）和预算收束。判断一句话：**能确定性判定的（形态、权限、副作用）绝不让模型判断；只能事后发现的（结果缺失）靠契约和对账；只能收敛的（幻觉）靠预算、审批、幂等把最贵的后果锁死。**

### 1.4 三种开场的接法

## 2. 叙事主线（03:00–37:00）

> 三段都是**陈述**，不是答题。每段走完「结论 → 取舍 → 一个失败或一个数字」。

### 段一（约 12 min）· 难的不是编排，是"谁有权调什么"

**90 秒开场稿**

> 我先把结论说了：**我把"能力"和"执行"分开了。能被模型看见的才叫能力；看不见的东西，它就算再想调也调不到。**
>
> 具体三层。最外层是**可见性**：不该被调用的能力，在拼上下文之前就不进目录。我第一期的基线是 deny_write + deny_high_risk——写能力和高危能力连被看见的资格都没有，模型看不见，它就写不出那个标识（id）。
>
> 中间层是**策略闸**：`invoke` 之前串一道。`capability_id` 查表 → 是否启用 → 策略（Policy） → 下游熔断 → 配额与熄火开关 → 参数形态。**顺序是有意义的**：熔断优先于配额，因为下游都挂了还消耗配额是浪费；被闸门拦下的调用**不计入配额**，否则"反复尝试但都被拒"会把配额打满，反而误伤一次正常调用。
>
> 最内层是**清单的形状完整性**：`kind=http` 的能力必须有 http 块；模板用到的变量必须先在模式（schema）里声明；接外部系统的能力必须显式声明可见范围——**没有"默认全员可见"这种兜底**。这几点全在加载期判，判不过这个能力就根本进不了目录。
>
> 还有一类**不在清单里、但必须随时查得到**：**运行时状态**——启用没有、熔断了没有、这个会话已经用了几次、上次降级是什么时候。它**不进清单**，因为配置是静态的、而放行是单次事件；**把运行时状态写进清单，正是"靠配置放行"这个错误的根源。**

**展开要点（每点 1–2 句，按顺序讲）**

1. **清单加载期就强校验**：写操作必须有幂等键、必须声明要人工确认；高危也必须人工确认；接外部系统的能力必须显式声明可见范围（没有"默认全员可见"这种兜底）。**加载失败，坏能力根本进不了注册表**——这是"事后补"和"事前挡"的分水岭。
2. **两个维度不能互相代理**：`risk_level`（危险程度）和 `side_effect`（有没有副作用）是两件事。`medium + write` 这种"普通提交"，在只看风险等级（risk_level）的实现里会被完全放行。**写闸挂在副作用（side_effect）上，不挂在风险等级（risk_level）上。**
3. **策略键只有宿主（Host）能给**：五个仅宿主（Host-only）键（allow_high_risk / allow_sandbox / allow_cli / allow_write / policy_override）。它们只从**进程环境变量**或宿主（Host）构造的 `ctx["_host_policy"]` 读。模型写在计划（plan）顶层的同名键**不进这条读取路径**——不是"检查了再拒绝"，是"根本读不到"。
4. **七个错误码，不增**：`unknown_id` / `disabled` / `policy_blocked` / `args_schema_invalid` / `duplicate_id` / `upstream_error` / `permission_denied`。下游是「五十度灰」式的错误（Fifty Shades of Error）：有一家 OA 的业务码就有几十种，**必须在适配器（adapter）层归一化**，否则模型面对一堆无法决策的字符串只会继续瞎试。新失败落既有码 + 详情（detail）区分。
5. **失败还得再分类一次**：同一个 `upstream_error` 里混着三种东西——传输层故障（该熔断）、429/5xx（该熔断）、200 里嵌了业务失败码（下游活着且回答了，**不该熔**）、本地没配好（我们自己的锅）。所以错误码（code）之外还带一个**结构化**的成因（cause），熔断只看这一项，**不解析错误文案**——文案一改，熔断就静默失效。
6. **登记表要装五类，缺一类就会在某个时刻失明**：静态声明（这是什么、谁维护）/ 执行语义（从哪个门出去、同步还是异步）/ 参数模式（schema）/ 安全属性（危险程度 · 副作用 · 要不要人批 · 可见范围）/ **运行时状态**（启用 · 熔断 · 会话用量 · 降级痕迹）。前四类在清单里，**变更走 Git + 合并请求（PR） + 人闸**；第五类是进程内实时态，**只能查、不能配**——它是观测对象，不是声明对象。

**🎣 本段预埋钩子**（说出这些词，就是在邀请他追问）：`side_effect` 与 `risk_level` 分列 · 七个错误码 · 仅宿主（Host-only）策略键 · 清单加载即拒 · 成因（cause）结构化 · **登记表五类与"运行时状态不进清单"**。

### 段二（约 12 min）· 把 Agent 的失败分成四类（**全场引擎**）

> 这一段是这场面试的核心。讲完之后，面试官大概率会顺着某一类追下去——**那就是 Q1–Q8 的入口**。

**90 秒开场稿**

> 大家聊 Agent 可靠性，习惯一条一条列问题：工具选错怎么办、结果错了怎么办、超时怎么办。我踩过一圈之后的结论是：**这八类失败不能用一种机制解决，它们分属四类，每类的"正确武器"不一样。**
>
> - **A 类 · 选择错**：该调 A 调了 B、参数格式错、漏必填。这一类**能确定性判定**，所以一分都不该让模型背——形态校验 + 候选集裁剪，模型不参与。
> - **B 类 · 结果错**：工具返回缺字段、列表为空、类型变了，Agent 当成正确结果继续规划。这一类**只能事后对账**，武器是**输出契约**：这一次调用的成功长什么样，必须先声明出来。
> - **C 类 · 环境错**：超时、限流、下游挂。可判定但**要策略**，而且**横向策略**和**纵向策略**必须分开——熔断回答"还打得通吗"，降级回答"打不通时给什么"。
> - **D 类 · 失控**：幻觉、循环、乱规划。这类**没有根治方法**，只能收敛，并把最贵的后果锁死。
>
> 一句话：**能确定性判定的，绝不让模型判断；只能事后发现的，靠契约和对账；只能收敛的，靠预算、审批、幂等把重复写这个最贵的后果按住。**

**展开要点**

1. **B 类是最容易被忽略、但污染面最大的一类。** 没有输出契约的时候，工具返回缺字段、字段类型变了、列表为空，**一律成功（ok=True）**——"查到 0 条"和"被限流返回空"在系统里长得一模一样。这是**唯一一处"错了还报成功"的口子**，而且没有任何环节会报错。**把它补上之后我才明白：前面那些闸都在防"错误的输入"，没有人防"错误的输出"。**
2. **契约必须显式声明，系统不替你猜。** 没声明输出契约（output_schema）的能力，不校验、不拦截——否则"能用"会变成"随机不可用"。这条是反向的那一半，**缺了它整件事会写成空真**。
3. **C 类的分工要说清楚**：熔断和降级是两件事。**框架能替业务定的是"何时降级"**（传输层（transport） / 5xx / 429 / 熔断打开（circuit_open），全是结构化判定）；**框架绝不能替业务定"降级成什么"**——框架猜出来的降级结果是静默错误：把三小时前的缓存当实时数据回答，它长得完全像一次成功。所以：**降级值写进清单，走 Git + 合并请求（PR） + 人闸。**
4. **降级必须带标记，而且标记必须跟着数据走。** 打在元信息（meta）上等于没打——模型只看工具输出，看不到元信息（meta）。**标记要进输出（output）**，否则兜底值会被当成真实结果写进答复，语气还很确定。
5. **写操作是 C 类的特例，纪律要反过来**：① 超时**不重发**（超时 ≠ 失败，重发会建出第二张单据）；② **写能力永不降级**（单据没建就是没建，不存在"降级成建了一半"）；③ 写能力**不参与半开探测**（探测代价不对等）。
6. **D 类的三个抓手**：一个是会话维度的**调用数 / 写操作数**配额——注意预算管的是"用了多少次"，不能拿"模型走了几步"冒充，"幻觉在一个步里连打十次写"是典型形态；一个是**熄火开关**（按能力 / 通配 / `write:*`）；再一个是**幂等 + 回执**——把最贵的那个后果（重复写）变成"最多发生一次"。
7. **配额分桶有个假门**：不能按子任务（subtask）分桶。子任务是 `run_id:seq`，一个子任务基本只打一次工具，按它分桶每个桶最多 1 次，**配额永远打不满——那是一道看起来有闸的假门，比没有更危险**。必须按会话（run）维度。

**🎣 本段预埋钩子**：输出契约 · 错了还报成功 · 熔断 对比（vs） 降级 · 标记必须跟着数据走 · 写操作三条反向纪律 · 按子任务（subtask）分桶的假门。

### 段三（约 11 min）· 怎么证明它没退步

**90 秒开场稿**

> 前面讲的都是"我加了哪些闸"。但这些闸有个共同的风险：**声明了不等于被调用**。我有过一次教训——模块里写着一个 V7 校验，代码里没有任何一处调它，跑了三个月没人发现。所以我现在的所有防御，验收只看一件事：**它在不在调用路径上。**
>
> 我把它做成三层：第一层是**红线（否决项）**——每条红线必须是"正向断言 + 反向对照"两条；只做正向会得到假通过，因为"一律拒绝"天然满足"该拦的拦住了"。第二层让**清单和实现互相盯着**（清单里有、测试里没有 → 失败（fail）；反过来也失败（fail）），这条对齐本身也是一条红线。第三层是**九层验收一条命令**，含真进程、真 HTTP、真数据库、真桩服务。

**展开要点**

1. **红线的"反向对照"是全部要点**：比如"无写放行时写能力必须被拒"这条，反向那半句是"给了放行必须真的执行成功"。再比如配额那条红线把"被闸门拦下的调用不计入配额"单独写死——因为它最容易被写反，`budget_exhausted` 报出来的时候你可能正在误伤一次正常调用。
2. **做完要变异检验**：把行为改坏一次，确认红线真的会失败（fail）。不然可能是一句空真。
3. **确定性判分、不自评**：规划侧的出口用题集 + 确定性判分器（grader）判——路由有没有命中、可见白名单有没有算对、计划结构有没有对上，全是**字段级比对**，不用大模型（LLM）当裁判给自己打分。而且**负样本是双审的**：词面零命中 + 语义零命中两条同时对上才算负样本，否则"答不上来"会被误当成"正确地拒答"。
4. **黑盒题集 + 基线差异比对（diff）**：`acc.route_match` / `acc.strategy.allowlist_match` / `acc.plan_match` 是三个与代码无关的出口指标；出口产出有基线快照，改完自动做差异比对（diff）——**模型换了、提示词改了，漂移一眼可见**，不用靠人回忆"以前好像不是这样"。
5. **三个"不许假装没发生"的细节**：① 幂等状态机的租约判定交给**数据库时钟**而不是本机时钟，多实例才不会各自认为对方已经超时；② 回调走 HMAC 签名 + ±300s 时间窗 + 一次性随机数（nonce）防重放，第三方不能伪造审批结果；③ 进程内的配额字典有 512 条上界、按插入顺序淘汰，并且**把淘汰计数报进运行时快照**——内存有界这件事不能靠人记住。
6. **Java 侧不是 PPT**：为了让"能力层真的发得出去"，我另起了一个 Java 的本地 OA 桩服务（Spring Boot 4），带凭证校验、租户谓词校验、幂等去重、故障注入。它存在的唯一理由是：**FakeTransport 能证明逻辑对，证明不了真的发得出去。** 现在是 26/26 全过，其中最关键的一条是"写操作超时后，桩服务侧该幂等键只被请求了 1 次"。
7. **真进程人工确认（HITL）回路**：还有一个跨两个真进程的审批回路脚本（Python 侧 + Java 侧），一次抓出两个单测抓不到的缺陷（bug）——一个是 JDK HTTP 客户端默认带 h2c 升级头，对面直接不读请求体，报 422 却完全不提示原因；另一个是两套存储的语义分叉（内存版无守卫覆盖写、数据库（DB）版有 `WHERE status='pending'` 守卫），**联调放行、生产拒绝**。

**🎣 本段预埋钩子**：声明了但没被调用 · 反向对照 · 变异检验 · 确定性判分 · FakeTransport 证明不了 · 26/26 · h2c。

### 轮 5 · 「工具返回的结果本身是错的，Agent 当成对的往下跑，你怎么发现？」（= Q2）

### 轮 6 · 「下游超时了、限流了、挂了，是直接失败还是有降级？」（= Q3）

**口述（90s）**

> 有，但**熔断和降级是两件事，必须分开装**：  
> **熔断是横向的**——只回答"这个下游还打得通吗"，不需要任何业务知识，连续五次"环境类失败"就打开，打开（open）期间零出网，60 秒后放行一次探测。  
> 这里有个很容易写错的地方：**必须只统计"环境类失败"**。如果一个 `upstream_error` 里既可能有传输层故障，也可能有 200 里嵌的业务失败码、也可能有我们自己没配好服务地址（base_url）——只看错误码（code）的话，"用户填错五次参数"会把一个完全健康的能力停 60 秒。所以我在错误上带一个**结构化的成因（cause）**，只认传输层（transport） / 5xx / 429，且**不解析错误文案**。  
> **降级是纵向的**——回答"打不通时给什么"，每个能力不一样，**框架绝不能替业务猜**。框架只做四件事：什么时候降级、怎么标记、链条多深、怎么观测。"降级成什么"必须写进清单、走合并请求（PR）。  
> 因为框架猜出来的降级结果是**静默错误**：返回上一次的结果，会把三小时前的数据当实时数据回答，而它长得完全像一次成功。所以降级结果**必须带标记**，而且**标记要跟着数据走、进输出（output）**——打在元信息（meta）上等于没打，模型只看工具输出。  
> 最后一条：**写能力永不降级，也不参与半开探测。** 单据没建就是没建，不存在"降级成建了一半"。

### 轮 7 · 「多步串联，中间某一步错了，后面步步错，你怎么提前拦？」（= Q4）

**口述（90s）**

> 这里有两个实证缺陷，我是读代码读出来的，讲出来比讲方案更有说服力：  
> **第一个**：归并的时候，`done` 里同时收了输出（output）和错误（error）两种终态——**前驱失败也被当成"已完成"**，依赖它的后继照常下发。这就是"中间某步错、后面步步错"的字面形态。  
> **第二个**：工人拿到的是计划里**写死**的输入（input），前驱的产出从来没被注入。`depends_on` 只表达顺序、不表达数据流——**伪串联**，模型以为串上了其实没有。  
> 所以我加了步骤契约：每步声明 `consumes` / `produces`，编排层在**喂入前**校验；前驱失败或缺少本步声明的消费字段（consumes） → **不下发、下游零请求**。  
> 两条纪律：**未声明的不校验**（否则"一步都不派"就满足所有断言，是空真）；**契约命中后必须真的注入**（平掉规划器（planner）写死的占位值），否则看着有链式推理、实际是并行 + 空引用。

### 轮 8 · 「执行到一半发现要加个工具、改个参数，是全量重规划还是增量修？」（= Q8）

**口述（90s）**

> 增量修，而且**不是"规范上有约束"，是结构上把它锁死**：计划表示成**不可变前缀 + 可变后缀**。已成功步骤进前缀，重规划**只动后缀**；前缀在提示里以只读形态出现，模型输出的东西只当后缀。  
> 为什么不用"写完再验它有没有改前缀"？因为大模型（LLM）复述前缀时换个说法就算改了，比对松了又等于没锁。**正确做法是收回写权限，不是事后检查。**  
> 这里和幂等有一个很漂亮的咬合点：写能力的幂等键由 `(tenant, 能力, args)` 派生，而前缀锁的正是 `(tool, args)` ⇒ 即便被重放，派生的键和首次相同 ⇒ 命中回执 ⇒ **重放而不是重做**。  
> 反过来说明为什么"改前缀"必须人工：**改参数（args）就是换键，就是一次新的写。** 所以我只在一种拦截原因上挂人工确认——`prefix_touch_required`：本步需要重跑已执行的前缀步骤才能满足。

## 5. 八问（Q1–Q8）· 架构答法

> **用法约定**：面试现场**不要逐条背"我们有 X"**。先给下面的"四类总纲"，再挑他追的那一条展开。  
> 每问的结构固定为：**结论一句 → 架构分层 → 迁移到新环境的最小实现 → 最容易写错的一点 → 【落地参考】**。

### 总纲（**这段必须背下来，它是八问的答案框架**）

| 类                                | 八问里哪几条      | 性质          | 正确武器                            |
| -------------------------------- | ----------- | ----------- | ------------------------------- |
| **A · 选择错**（调错工具 / 参数格式错 / 漏必填）  | Q1          | **可确定性判定**  | 候选集裁剪 + 形态校验 + 稳定错误码。模型不参与判定    |

### Q1 · 大模型对工具描述理解有歧义，该调 A 却调了 B，或参数传错格式、漏传必填，接口报错怎么兜底？

**结论**：这一类**不该让模型背**，因为它全部可确定性判定。三层：加载期挡坏工具 → 运行时缩候选集 → 出门前验形态。

**架构分层**

1. **加载期**：能力清单必须有面向模型的 `when_to_use`（这是模型选工具的唯一依据，空则加载失败）、必须有 `args_schema`、模板变量必须声明、密钥形字段只允许写**名字**。**坏能力进不了目录。**
2. **可见性**：静默裁剪在拼上下文之前发生——写/高危在基线里就被拒绝（deny）；再叠一层身份维（部门/角色/项目/密级），匿名主体一律失败即关闭（fail-closed）。
3. **运行期（形态层）**：JSON 模式（JSON Schema）子集校验必填（required） / 类型（type） / 额外字段（additionalProperties），失败返回 `args_schema_invalid: 缺必填字段: x`，**请求不出门**。**注意这一层只判形态、不判值域**——`enum` / 区间（minimum / maximum）当前**都没实现**，所以"温度填 999"是过得去的。被追问到值域，用 §7.5 的三类分法（形态 / 包络 / 业务规则）。
4. **错误归一**：真到了下游才报错，由适配器（adapter）把厂商各异的业务码映射成七个稳定码，**并且不外泄下游原文**（一是数据边界，二是模型拿着一堆无法决策的字符串只会继续瞎试）。

**迁移到新环境的最小实现**：先做 3（形态校验）+ 4（错误归一），成本最低、收益最高；1、2 跟着第一批能力一起补。**顺序不能倒**——没有 `args_schema` 就先谈"让模型自己修参数"，等于先把验收标准删掉再谈质量。

**最容易写错的一点**：**参数形态 ≠ 参数语义**。`subject` 传成了 `id` 这种只有下游能判，别指望模式（schema）。所以要有"补救路径"：`args_schema_invalid` 的详情（detail）回喂模型**重试一次**，而**读可重试、写不可重试**（写重试会建第二张单——这是 R5 的同一条纪律）。

还有一条更隐蔽的：**值域不校验会让错误码语义翻转**——越界参数在域侧被拦会被归一化成 `upstream_error`（**可重试**），在网关（Gateway）侧被拦才是 `args_schema_invalid`（**可修正**）。同一个"参数不合法"，前者会诱导模型去重试一个永远不可能成功的调用。

### Q2 · 工具返回结果本身有错、有缺失，Agent 当成正确结果继续规划，整条链路全错，你怎么发现？

**结论**：加**输出契约**。这是**唯一一处"错了还报成功"的口子**，必须先声明"这次调用的成功长什么样"，否则没有任何环节会报错。

**架构分层**

1. **声明三件事**：必填路径（存在且非空值（null））、列表最小条数、空是否可疑（`empty_is_suspicious`）。
2. **命中即判失败**，落到既有错误码的详情（detail）上，**不新造码**（词表七个是硬约束，否则错误码会指数膨胀，模型又会回到"面对一堆字符串"）。
3. **空必须是显式状态**：默认不把空判失败（会误伤正常查无），但必须打 `result_empty` 标记，让编排层区分"确实没有"和"可疑的空"。
4. **反向那半句同等重要**：未声明契约的能力**不校验、不拦截**。契约是显式声明出来的，系统不替你猜——否则"能用"会变成"随机不可用"，而且你会在测试里得到假通过。

**迁移到新环境的最小实现**：给前 10 个（top-10）高频能力先声明 `output_schema`（只写必填（required）就够了），跑一周看命中率；再对所有**写**能力强制。

**最容易写错的一点**：把失败判据写成"非空就行"。**类型变了比缺字段更常见**（下游把列表（list）改成了字典（dict）），所以判据里必须有"不是列表"这一类。

**【落地参考】** `result_contract.py:77-155` · 契约定义位置 `types.py` 的 `output_schema` · 红线 **R10** · 该红线的依据（rationale）直接写着"八问 Q2/Q4 的根因"

### Q3 · 工具调用超时、限流、接口挂了，Agent 卡在那反复重试，是直接失败还是有降级和备选工具？

**结论**：有策略，但**必须横向能力和纵向能力分开装**——**熔断回答"还打得通吗"，降级回答"打不通时给什么"。**

**架构分层**

1. **超时与重试**：声明式 `timeout_ms`，超时判失败不挂起。重试策略显式分化：**读可重试，写永远不自动重试**（`attempts = 2 if GET else 1`）。理由是超时 ≠ 失败，写重发会建出第二张单据。
2. **写超时后怎么办**：不重发、不自动查询，保持 `in_flight` + 租约（120s），租约过期可被接管并记录 `took_over_stale_lease`。另外给运维一个**只发现、不自动重试**的排障视图。
3. **熔断（横向）**：连续 N 次**环境类**失败打开，打开（open）期零出网，60s 后放行一次探测。**只统计环境类失败**（传输层（transport） / 5xx / 429），业务码失败和本地装配问题**不计入**——否则五个用户填错参数就把一个健康能力停 60 秒。**判据必须结构化，不能解析错误文案。**
4. **降级（纵向）**：框架只做"何时降级 / 怎么标记 / 链条多深 / 怎么观测"；**"降级成什么"必须由业务在清单里声明**，走 Git + 合并请求（PR） + 人闸。框架猜出来的降级是静默错误。
5. **标记必须跟着数据走**：元信息（meta）上的降级标记等于没打——模型只看工具输出。**标记要进输出（output）**，进不去必须报进观测，不能假装没发生。

**迁移到新环境的最小实现**：先装 1 + 3（这两件不需要业务知识），降级放到最后——因为它需要每个能力负责人（owner）来回答"退到哪一步"。

**最容易写错的一点**：**给写能力降级或参与半开探测**。单据没建就是没建，"降级成建了一半"会造成最坏结果：用户以为提交了。

**【落地参考】** `fallback.py:1-40`（分工表 + B1–B4）· `circuit.py:63-66, 200-214` · `errors.py:50-85`（成因（cause）分类）· `idempotency.py` 租约 · 红线 **R5 / R12 / R13**

### Q4 · 连续多步调用，前一步输出是后一步输入，中间某步错了，后面步步错，怎么提前拦截？

**结论**：加**步骤契约**，并且**校验点在喂入前**。事后校验只能"发现错了"，挡不住"已经在错的数据上继续跑"。

**架构分层**

1. 每步声明 `consumes`（要前驱的哪些字段）/ `produces`（承诺产出什么）。
2. 编排层在**喂入前**校验：前驱是失败终态 → 后继不执行；前驱输出缺 `consumes` 声明的字段 → 后继不执行。**两者都是下游零请求。**
3. **必须真的注入**：覆盖规划器（planner）写死的占位值。只做"声明 + 校验"不做绑定 = 空门（看着有链式推理，实际是并行 + 空引用）。
4. **未声明的不拦截**：否则"一步都不派"就满足所有断言，是另一种空真。
5. 给足背景预算上界：单步字段数、单值截断、整块预算都要有闸，防止一堆字段把提示词（prompt）撑爆。

**迁移到新环境的最小实现**：先在最贵、最长、最容易错的那条链路上加 `consumes`，别全量铺。

**最容易写错的一点**：把"列表顺序"或提示词里的"按执行顺序排列"当成依赖。**顺序不是依赖，不能被当成调度依据**——需要显式字段。

**【落地参考】** `app/ops/lg_rag/multi/step_contract.py:1-30, 56-67` · `docs/tasks/active/task_supervisor_parallel_join.md`（R2/R4：新增 `depends_on`，收齐按计划标识（id）终态集而非列表长度）· 红线 **R14**

### Q5 · 有没有考虑过不靠大模型自己判断的方案？

**结论**：有，而且这是我的默认立场——**大模型（LLM）不可替代的只有"在不完全信息下做选择"这一件事。**

**架构分层（全部是机制，不是提示词）**

- **白名单 + Git + 合并请求（PR） + 人闸**：能力清单是代码；`risk_level` 降级等价拆闸，不能靠改库生效。
- **禁止热加载**：变更必须重启或显式重载（reload）；包内连 `APIRouter` 都不许出现（有测试守）。
- **可见集裁剪**：模型看不见就调不到——这是最便宜也最有效的一道。
- **策略（Policy）硬闸**：高危 / 写 / 沙箱 / CLI 默认拒；租户谓词强制下推，缺就拒。
- **形态校验 + 稳定错误码 + 输出契约**：把"能不能调用（invoke）"、"这次成功了吗"变成确定性判定。
- **幂等 + 租约 + 回执**：把最贵的后果（重复写）锁成"最多一次"，且事后可对账。
- **确定性判分 + 题集 + 基线差异比对（diff）**：不靠大模型当裁判（LLM-as-judge）给自己打分。
- **预算与循环上限**：步数、写操作数、重写（rewrite）熔断（重写后与原查询（query）相同即终止）。

**迁移到新环境的最小实现**：先做最基础的三件——可见集裁剪、形态校验、稳定错误码。它们是后面所有机制的承重墙。

**最容易写错的一点**：以为"用大模型（LLM）判断大模型（LLM）的输出"也算一道闸。**自评不算闸。**

### Q6 · 大模型幻觉、乱规划、乱调用，整个 Agent 失控，单点风险怎么解？

**结论**：**幻觉治不了，但可以收敛，并把最贵的后果定义为"不发生"。**

**架构分层**

1. **不给机会**：候选集裁剪 + 默认拒 + 参数形态校验。
2. **给上限，且量纲要选对**：分层的预算——编排步数（32，耗尽走汇聚而不是报错，保证**任何情况下都有终态回答**）、每会话调用数（64）、**每会话写操作数**（8）。注意各个上限之间还有个"谁优先"的问题（预算耗尽 对比（vs） 评审器（critic）回环）：**全局预算优先于局部回环**，否则两个回环互相打架，最大步数（max_steps）反而失效。
3. **熄火开关**：按能力 / 通配 / `write:*`，一键停；并且**与正常变更通道分开**（正常变更走合并请求（PR），紧急停用是另一条审计线索）。
4. **最贵的后果只发生一次**：幂等键 + 租约 + 回执。
5. **被闸门拦下的调用不计入配额**——这条单独钉成红线，因为它最容易被写反，而且写反之后在正常流量下完全测不出来。

**迁移到新环境的最小实现**：先上"每会话写操作数"这一个数字。它是投入产出比最高的一个闸，因为它直接对准最贵的失败。

**最容易写错的一点**：**预算分桶用错维度就是假门**。按子任务/按步分桶，看起来有闸，实际每个桶最多一次、永远打不满。必须是会话（run）维度。

**【落地参考】** `budget.py:38-190`（含"假门"注释原文）· `app/ops/lg_rag/multi/budget.py:18-33` · `strategy/critic.py:54-56`（全局优先）· `app/ops/lg_rag/multi/nodes.py:859-860`（耗尽 → observe → settle）· 红线 **R11**

### Q7 · 任务复杂，动态选择十几个工具，模型漏工具、跳步骤、循环调用，怎么优化？

**结论**：三件事——**压缩候选、给检查单、换更准的循环判据**。

**架构分层**

1. **压缩候选**：① 可见集裁剪按身份维；② `when_to_use` 做语义召回前 k 个（top-k，5–8）再交给模型选，**不要全量喂**。工具到几十个时全量喂会退化成选择困难 + 漏选。
2. **检查单（required_capabilities）**：这类任务**必须**调用哪些能力，由任务模板声明，编排层校验，缺了就是"跳步骤"，直接失败——不靠自觉。
3. **循环判据换指纹**：`(capability_id, args)` 出现第二次即判循环。这比"步数上限"**更早、更准**——步数上限是兜底，不该是第一道。
4. **规模化之后的归并纪律**：子任务标识（id）由宿主（Host）签发（`run_id:seq`），模型给的那串 `t1` 只当别名，**不当关联键**；收齐条件是"每个计划标识（id）都有一条终态"，**不能拿结果列表长度凑**（并发返回时按长度取下标会错配到别人的结果）。

**迁移到新环境的最小实现**：先从 4 做起（它最容易出错且最贵），再做 1 的语义召回，最后才是检查单（它需要业务负责人（owner）配合定义模板）。

**最容易写错的一点**：把提示词里的"按执行顺序排列"当成依赖关系。**它不可测，且在并行化后会直接崩。**

**【落地参考】** `multi/nodes.py:63`（`MAX_SUBTASKS = 4`）· `docs/tasks/active/task_supervisor_parallel_join.md` 的「10 钉死契约」与失败路径（宿主（Host）签发关联键、模型标识（id）只当别名、按计划标识（id）收齐、会话标识（run_id）缺失不许退化成 `t1`）· `strategy/builder.py:38-59`（候选 ∩ 可见集，记 `stripped`）

### Q8 · 动态场景：执行中发现要新增工具、调整参数，原计划被打乱，全量重规划还是增量修正？怎么保证不影响已执行步骤？

**结论**：**增量修正，且用"收回写权限"而不是"事后检查"来保证前缀不变。**

**架构分层**


1. 计划表示成**不可变前缀 + 可变后缀**：已成功步骤进前缀；重规划时前缀以**只读**形态出现在提示里，模型输出的东西只作后缀。理由：大模型（LLM）复述前缀时换个说法就算改了，比对松了又等于没锁——**事后校验这条路先天不可靠**。
2. **与幂等咬合**：写能力的幂等键由 `(tenant, 能力, args)` 派生 ⇒ 前缀被重放时键不变 ⇒ 命中回执 ⇒ **重放而非重做**。这是幂等真正的价值，不只是"防重复提交"。
3. **改前缀必须人工**：改参数（args） = 换键 = 一次新的写。所以只保留一种需要人批的拦截原因：`prefix_touch_required`。所以我没有做"到处挂人工确认（HITL）"，只在会产生**新的副作用**时才叫人——审批是有成本的，到处挂等于没有。
4. **失败终态不进前缀**：没有副作用、没有可取结果，留着只会让整条链卡死（无法被重写）。
5. **回环时不能把结果整批清空**：评审器（critic）回环时必须保留前缀结果，只清后缀——否则"断点续跑"根本无从谈起。

**迁移到新环境的最小实现**：先把 `subtask_id` 交给宿主（Host）签发并落进回执，然后才有资格谈"可恢复点"。**没有稳定的执行标识（id），就没有恢复点。**

**最容易写错的一点**：评审器（critic）回环时把结果整批清空，已跑过的步骤被再打一遍。**这会让前缀锁定的所有努力归零。**

**【落地参考】** 红线 **R15**（`capability_v1.yaml:184-203`，含上述最易错处）· `step_contract.py:66-67`（`HITL_REASONS`）· `http_generic.py:779-789`（键派生）· `multi/nodes.py:1286-1300`（申请行）· `hitl/signature.py`（回调 HMAC + 时间窗 + 一次性随机数（nonce））

### 7.4 「委派降权没做」是空真——改说"执行路径不认识调用者"

早期稿里那句反复出现的"委派降权没做"**不要再说**。它是**空真**：当前是单图多步（子任务，subtask），根本没有跨 Agent 委派，对一个不存在的对象做否定陈述 = 零信息量；而且旧稿"现在靠父层先裁剪、子层再看一遍"这句**描述了一个不存在的机制**（代码里没有子层）。

**换成这个真边界**：

> 「**执行路径不认识调用者**——可见性校验只在规划期做（`list_capabilities`），`invoke` 时不查"谁在调"。单 Agent 下够用；一旦引入 1+N 的委派，这就是硬伤。委派降权的前提不是那个取交集的算法（十几行），是"每次调用都带主体"这个基础设施——**我缺的是前提，不是算法。**」

---

### 7.5 参数校验只判形态、不判值域——被追到"空调填 999 度"时用这个

**现状**：`schema_validate.py` 只做 `type` / `required` / `properties` / `additionalProperties`——**连 `enum` 都没实现**。所以"温度填 999"和"单位填华氏度"今天**都过**。

**关键是把三类分开，别混为一谈**：

| 类别          | 例子                             | 谁声明      | 谁执行          |
| ----------- | ------------------------------ | -------- | ------------ |
| 形态          | temperature 是 number           | 车控域写进清单  | 网关（Gateway）  |
| **包络**      | **16–30（物理 / 安全边界，与调用者无关、全域恒定）** | **车控域写进清单** | **网关（Gateway）** |
| 业务规则        | 这个人能批多少钱                       | 域服务      | 域服务 / 策略（Policy） |

**16–30 不是业务规则，是包络。** 我早期把它一刀切归进"业务不变量不进 schema"那条纪律（P-16），那是分类错误——P-16 举的"涨跌幅"确实是业务规则，但它不该顺手把包络也吞掉。

**为什么必须在网关侧拦**（不是"晚不晚"，是四条硬的）：

1. **出门之后可逆性不由我决定**——999 度可能被下游截断（clamp）成 30，等于**静默改了用户意图**，比报错更坏；
2. **错误码语义会翻转**——域侧拦会被归一化成 `upstream_error`（**可重试**），网关侧拦才是 `args_schema_invalid`（**可修正**）。**同一个"参数不合法"，前者诱导模型重试一个永远不可能成功的调用**；
3. **配额记账位置**——参数校验在 `_prepare_call` 里、`budget_count` 在它之后，所以越界被拦**不计入配额**；挪到域侧就白吃一次额度；
4. **指标分类错**——拦不下就从"被拦下的写"掉进"调用失败"那一桶。

**落地口径**：**写能力强制包络，读能力推荐**。999 度去查询返回空，无害，没必要为每个读能力都配值域。

### 7.6 「这套升级成多 Agent，网关在哪一层起作用？」——照这张表说，别虚

**先给结论**：我画的七层里，**当前有代码的只有 ①②⑥⑦，④⑤ 一行没有**；而**真正的"闸"只有第 ⑥ 层一处**（`gateway._prepare_call` 六道闸）。其余各层都是"过滤 / 注入 / 规划"，**拦不住东西**。

| 层                  | 当前落点                                                                                            | 是闸吗                     | 代码                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------- |
| ① 策略 Builder      | 有。`get_policy_visible_catalog()` = `list_capabilities(filter=BUILDER_CAP_FILTER)`                    | **不是**（只产出，不拦截）           | `app/ops/strategy/builder.py:25-29`                                    |
| ② 可见集注入           | 有。写 `allowed_capability_ids` 进 state，被剥掉的部分只进 span                                                  | 不是（**过滤**，不是闸）            | `builder.py:38-59, 74-121`                                             |
| ③ 主 Agent 规划       | 有。supervisor 出 ≤4 子任务 + S1-d 校验（工具 id 非法 → 整份计划判 None）                                             | 是**弱闸**（拦"规划出来的"，不拦"直接吐的"） | `app/ops/lg_rag/multi/nodes.py:720-857`；`_subtasks_have_valid_tool_ids` |
| ④ 委派网关 A2A        | **完全没有**                                                                                          | —                       | 无                                                                      |
| ⑤ 垂类子 Agent       | **无**（主 Agent 代做，子任务共享主状态，没有独立主体）                                                                     | —                       | 无                                                                      |
| ⑥ **执行网关 A2G**    | **有，且是唯一真闸**。六道：lookup → enabled → Policy → 熔断 → 配额/熄火 → args_schema                                | **是**                   | `app/ops/capability/gateway.py:258-385`                                |
| ⑦ 能力提供方            | 有（local_fn / http 两种形态，`ALLOWED_KINDS` 只认这两个）                                                       | 不是                      | `manifest.py:62`                                                       |

**三个必须主动说出来的硬事实**（都是对我不利的，先说反而加分）：

1. **Builder 不是闸。** `allowed_capability_ids` 只写 state，`_prepare_call` 里**没有任何一道白名单闸**——模型绕过 supervisor 直接吐一个不在允许集（allowlist）里的 id，第 ⑥ 层照放。所以"可见集"目前是**提示词（prompt）层面的引导**，不是强制。
2. **可见集是三层取交集，但身份维是空的。** `CapabilityFilter`（场景维：kind/risk/写/deny_*）∩ `visibility`（身份维：部门/角色/项目/密级）——**身份维在生产上没人传主体（principal）**，`principal_or_principal()` 走匿名失败即关闭（fail-closed），等于这一维恒等于"全放行或全不放行"，没真正生效。
3. **④⑤ 不在，⑥ 就答不了"谁在调"。** `tool_exec_node` 构造的 `cap_ctx` 只有 `{tenant_id, subtask_id, run_id}`（`nodes.py:1095-1102`），**没有主体、没有授予集（granted）、没有委派深度**。这就是 §7.4 那句"执行路径不认识调用者"的代码级出处。

**升级时三条不能踩**（被追问"那你怎么补 ④⑤"时用）：

- **委派令牌绝不能进 state。** state 是会被重规划（replan）、会被持久化的；令牌必须像 `_host_policy` 一样**按次调用走 ctx**，随调用生、随调用灭。
- **A2G 必须补第 7 道闸：`cid ∈ ctx["allowed_ids"]`。** 否则 A2A 的签名是废纸——模型直接打 ⑥ 就绕过去了。**现成的反例就在代码里**：`_degrade`（`gateway.py:783-795`）内部派发到 `fallback.capability_id`，走 Policy/熔断/配额/schema，但**不查可见集、不查允许集**——这就是一道已经存在的"旁路"。
- **Builder 剥掉的那些（`stripped`）要变成一手证据。** 今天它只进 span（观测用），应该升级成 A2A 拒签的依据，并回传给规划器让它知道"不是没这个工具，是你没权用"。

**一句话收口**：「**我不是有一个多 Agent 网关，我是有一个执行闸 + 一条过滤链。** ④⑤ 那两层现在没有，但第六层的位置是对的——它在最靠近真实副作用的地方。补④⑤ 的时候，第六层不用动，只需要多收一个参数。」
