## 【0:00–1:00】开场：一条链路，五层空间

我用一句话概括这套系统：**一条五阶段的链路，叠在五层空间上**。

空间上分五层：编排层管任务分解，能力层管工具闸控，模型层管 LLM 供给韧性，数据层管状态与证据，传输层管 SSE 生命周期——每层防一类错。但空间分层只能报菜名，看不出设计判断。所以我按时间线讲：一次请求的生命周期要走**五个阶段**——收窄、规划、派发、聚合、落地。每个阶段都可能失败，而每个阶段的失败都是显式的——系统报错时，error 帧的 stage 字段就是按阶段定位的。这条主线讲到尾。

---

## 【1:00–6:00】五阶段时间线（每阶段约 1min）

### 第一阶段 · 收窄

请求进来，第一站不是大模型，是一个没有 LLM 的 Builder。它做三件事：第一，把候选能力清单和注册表、策略基线取交集，裁成一份白名单——模型根本看不到工具全集，连幻觉出高危工具的机会都没有；第二，把对话历史压成 6+2 窗口：6 轮原文，更早的每 2 轮压成一组合摘要；第三，从这里开始计 32 步总预算。

注意收窄的默认值：交集求不出来就是空集，不是全开。收窄成空白名单也不报错——显式降级成单 rag 并打标记。**fail-closed 从入口第一阶段就开始了**。

[看点] 给模型的不是全部工具，是交集后的白名单。
[若被追问·不主动讲] 为什么不放行未知 key？——只裁剪防不住幻觉 id，可见裁剪和执行拦截双管。

### 第二阶段 · 规划

supervisor 上场，只做一次结构化调用，把问题拆成不超过 4 个子任务，带依赖关系。

这一阶段最关键的设计判断：**首次规划失败，默认直接停图**。发一帧带 stage 的 error 帧——就这一帧，就是终态，后面没有 done。失败对用户显式可见、可重试。我们宁可显式失败，也不静默退化成通用回答、造成任务完成的假象。当然留了灾备开关：显式配置后可以降级单 rag，但全程带 degraded 标记——降级必须可统计、用户必须知情。

两个数字分清楚：32 步是 supervisor 总步预算，2 轮是 ReAct 收口次数——**步数和轮数是两个维度**。

[看点] 首次规划失败 = 一帧 error 即终态，绝不静默冒充成功。
[若被追问] 为什么不自动重试 LLM？——同 prompt 重试大概率同结果，把重试决策交给用户更诚实；且重试烧的是 32 步预算。

### 第三阶段 · 派发

规划出来不是直接执行。join 节点是派发前的最后一道闸，做三件事：先校验**步骤契约**——上一步承诺的字段齐了没有，缺字段不喂坏数据，写成带原因码的 blocked 终态；要改历史步骤的产出，**交人批**；校验过了，才逐个子任务**签发委派令牌**——TTL 600 秒、禁续期、重发重签发、nonce 一次性，拒绝分六类原因码。

工人执行时，每次工具调用还要过**七层闸链**：验签、查找、启用、策略、熔断、配额、参数校验。注意一个顺序：熔断排在配额前面——**先谈别打了，再谈打几次**。

还有一个口径：blocked 不是 error。blocked 是业务判定，带原因码、能转人工；error 帧只留给技术异常。

[看点] join 是派发前最后一道闸：缺字段不喂坏数据、改历史交人批。
[红线] 委派令牌模式**默认关**（三档灰度：off 短路 / observe 只记不拦 / enforce 真拦）——口径是「先量后闸」，不是「已全面强制」。
[若被追问] 令牌为什么禁续期？——续期就是变相扩大授权窗口，重发即重签发。

### 第四阶段 · 聚合

工人全部回来后，observe 节点先做收口判定——用的是**确定性信号**：还有没有待发步骤、有没有失败、有没有挂着的人工审批。这里有个关键区分：**没有待发步骤，不等于满足了问题**。判不满足就走重规划，最多 2 轮。

然后 aggregator——独立节点，不是主 agent 顺手做——把子任务结果综合成分节答案，token 流式推给用户。最后是 critic：**它现在是规则 stub，不是 LLM**。为什么不用 LLM？收尾判定要确定性、可测试、可重现——LLM 评委引入不可重现性，这是设计如此。

额度上：局部有 1+1 的回环（一次内部重试 + 一次重绑定），但**全局 32 步预算优先**——局部额度永远不能突破全局上限。

[看点] 两个收口分开做：observe 判「活干完没」，critic 判「答案行不行」。
[红线] critic 是规则 stub——必须说「设计如此」，不能被当成「还没做」。

### 第五阶段 · 落地

最后是传输和落地。核心判断一句话：**执行与传输解耦**。SSE 只是只读订阅者——断连就是退订，worker 照跑。

每一帧都落数据库，run_id 加 seq 唯一；事后 replay 原样回放取证，**不重跑 LLM**。进程崩了有孤儿补偿：300 秒没有终帧，补一帧 disconnected——失败语义显式，不是挂着没人管。审批挂起有 3600 秒 TTL；恢复是**异步受理**秒回——因为同步实测要两三分钟，会超前端 30 秒超时。

[看点] 断连只是退订：执行与 HTTP 订阅解耦，每帧落盘可 replay 取证。
[红线] 两条照实说：① run 单飞是进程内字典，**多副本 DB 租约已知未做**；② 落盘是「登录路径全量 + 后台尽力」，不说「每帧必落」。
[若被追问] 多副本怎么办？——照实承认边界，租约机制在路线图上。

## 【6:00–8:30】两个取舍（各约 75s）

### 取舍一 · 显式失败 vs 静默兜底

只能讲一个取舍就讲这个。规划失败其实有另一条路：静默降级成单 rag——用户总能拿到一个回答，体验平滑。但那是假象：他要的是多步任务，得到的是一次检索，**任务完成的假象比失败本身更危险**。

我们选显式失败：error 帧带 stage、retryable，可见、可重试、可统计。代价是失败率数字变难看了——但我们认为，**可见的失败率才是可治理的失败率**。灾备开关保留逃生通道，degraded 标记让每次降级都可统计、跟数据走进最终答案，用户有权知道这是兜底结果。

### 取舍二 · 执行与传输解耦

第二个取舍：SSE 连接和 run 的生命周期**不绑定**。绑定的实现简单——断连即 cancel，省资源。但 agent 任务动辄几分钟，移动端切后台、网络抖动是常态；一断就杀任务，用户代价远高于服务端省下的那点资源。

所以 worker 有独立生命周期、帧逐帧落盘、replay 断点续看。代价是服务端要为「没人在看的 run」负责——孤儿补偿、单飞去重、落盘一致性，这些机制全都是这个取舍开出的账单，我们认账。

[备选取舍·可替换] critic 规则化 vs LLM 评委（确定性 vs 表达能力）；可见裁剪+执行拦截双轴（为什么不能只做一道）。

## 【8:30–10:00】失败场景 + 收尾

### 失败场景 · 规划失败全链路（约 60s）

讲一个真实链路。supervisor 首次规划，LLM 返回了非法 JSON。parse 失败，且没有 locked 前缀——说明还没有任何战果——直接抛错停图。发出一帧 error 帧，stage 是 supervisor_plan、retryable 为 true，这帧就是终态，落库。

之后呢？前端看到 retryable 可以重试；我事后按 event_type 等于 error 一条 SQL 捞出全部规划失败；tracing 里有专门的 span 标记。从头到尾：**错误有专属帧、专属 stage、专属落盘位置、专属指标——没有一处静默**。

### 收尾（约 30s）

这套系统只能记一句话的话，是**失败显式化**：五个阶段每个都可能失败，每种失败都有专属帧、专属落盘、专属指标。还有第二句：**高危默认关**——委派令牌、PG 持久化、输入隔离，全是显式开关，先观察、后强制。

做完这套系统我最大的体会是：**agent 的权限边界比能力本身难得多**。这也是我这段时间认真读 VanorOS 源码、并且实际跑了几轮测试的原因——有些发现想跟你们聊聊。

[情境] 末段转向句面向 Vanor 场景（用法见 doc 14 §2：若自我介绍阶段对方已接住「真实审批」钩子，可跳过转向句直接进深聊点）；通用场景收尾改为「这两句合起来，就是我们对『agent 系统怎么才算生产级』的回答」。
