## 0. 先给结论

### 0.1 你列的五块，不是完整地图

你列的：**LLM 管理工程 · 能力注册表 · 记忆管理 · Prompt 管理 · 编排管理**。
这五块都对，但它们缺了**三块最能拉开差距的**——而且那三块恰好是你仓库里最强的部分。

| 你列的 | 本仓成熟度 | 是否该重点讲 |
|---|---|---|
| 能力注册表 | ★★★★★ | 已经是主叙事 |
| 编排管理 | ★★★★☆ | 已经是主叙事 |
| LLM 管理工程 | ★★★☆☆ | 有骨架（provider 抽象 + 结构化输出），缺路由/重试/熔断 |

| 你**没**列、但真正拉开差距的 | 本仓成熟度 | 为什么它是差异化武器 |
|---|---|---|
| **评测与红线层** | ★★★★★ | 大多数人只能讲"我做了什么"，讲不了**"我怎么证明它没退步"**。你有 R0–R15 十六条红线 + 九层验收 + 确定性 grader |
| **契约层**（形态/结果/步骤三套） | ★★★★★ | 它把"模型的不确定性"挡在**系统边界外**——这是"工程化"和"调 prompt"的分水岭 |
| **人闸与幂等层** | ★★★★☆ | 它让**写操作变得可逆、可对账**。企业场景里这是"能不能上线"的开关 |

> **一句话**：你列的五个是"Agent 长什么样"；漏掉的三个是"**凭什么敢让它上生产**"。面试官在北汽这种场景下，真正压的是后者。

### 0.2 为什么记忆 / Prompt 必须专门准备

三个理由，都很实际：

1. **它们是"看起来最像有、一问细节就露"的两块。** 候选人一说"我们有记忆管理"，面试官立刻问三连：*什么该记住？记错了怎么纠正？怎么忘掉？*——答不上来，前面所有可信度一起崩。
2. **多 Agent 方向天然会问到。** Agent 一多，必然引出"Agent 之间怎么共享上下文"、"长任务怎么不丢信息"、"跨会话怎么延续"。这是 JD 的必答题，不是加分题。
3. **你这两块都有"名不副实"的风险点**（见 §1.2.2 和 §2.1.1）——**必须提前改口径**，否则现场被追问细节会发现说的是另一回事。

> 准备方式不是"补知识"，而是**把"缺什么 + 为什么缺 + 怎么补"讲清楚**。这是这三册材料一以贯之的姿势。

## 1. 记忆管理（Memory）

### 1.1 第一步：把"记忆"这个词拆开，否则必答错

面试官说"记忆"，可能指**四件完全不同的事**。它们的存储、生命周期、设计难点都不一样：

| 类型 | 是什么 | 存哪 | 生命周期 | 本仓状态 |
|---|---|---|---|---|
| **工作记忆** | 当前 run 的执行状态（计划、中间结果、预算） | Checkpointer | 一次 run | ✅ 有 |
| **会话记忆** | 多轮对话历史 | `ops_runs` + 窗口压缩 | 一个会话 | ⚠️ **有，但只是截断** |
| **长期语义记忆** | 跨会话的经验 / 事实（可语义召回） | 向量库 | 长期 | ❌ 语义层没有（**但基础设施已就位**） |
| **画像记忆** | 用户偏好 / 习惯 / 常用对象 | KV | 长期 | ❌ 没有 |

> **被问到时的第一个动作**：不要直接答，先把它拆开——
> 「记忆我分四层看：工作记忆、会话记忆、长期语义记忆、画像记忆。**您想聊哪一层？** 如果是工作记忆和会话记忆，我这边是落地的；如果是长期记忆，**我只有基础设施，没有记忆语义层**——我可以讲清楚差什么。」
> 这不是耍花招。这四层的**写入策略、冲突处理、遗忘机制完全不同**，混着答必然出错；而且**主动分层本身就是资深信号**。

### 1.2 本仓逐层真实状态

#### 1.2.1 工作记忆 ✅（这块很强，直接讲）

- State 里有计划、子任务结果、预算计数、意图/策略等结构；证据本体**不进 State**（黑盒原则）。
- 持久化靠 checkpointer，开关是 `LG_RAG_HTTP_CHECKPOINTER`（值 = `postgres` 才走 PG，否则进程内 saver）。
- **HTTP 入口与 SSE 入口必须走同一把闸**——否则会出现"invoke 落盘了、SSE 没落盘"，恢复时找不到挂起点。

**关键纠正（很重要）**：`LG_RAG_HTTP_CHECKPOINTER` 不是 `true/false` 布尔开关，而是**取值等于 `postgres` 才启用**——说成"我们开了个开关"就不精确了。

**【落地参考】**
- 开关与 DSN：`app/ops/lg_rag/checkpointer.py:25-43`
- 每请求装配（`setup=True` 幂等建表）：`app/ops/lg_rag/router.py:177-180`
- 证据不入 State：`app/ops/lg_rag/state.py:200-203`（注释原文"evidence 本体不进 state（黑盒原则）"）

#### 1.2.2 会话记忆 ⚠️ —— **本篇最需要改口径的一处**

**真实实现**：`compress_window` 保留最近 6 轮全量，更早的轮次**替换成一个占位标记**。占位符的实际内容是：

```
"[历史摘要 · 2 轮 · roles=assistant,user]"
```

**它里面没有内容，只有轮数和角色。**

所以它**不是摘要**，它是**"截断 + 标记"**：

| 它保住了什么 | 它没保住什么 |
|---|---|
| 窗口有界（token 可控） | **语义连续**——模型不知道前面说了什么 |
| 不静默丢弃（留下痕迹，模型知道"这里曾经有对话"） | 不能防"前后矛盾/重复提问" |
| 实现极简（纯函数、无 DB、无额外模型调用） | 摘要能力（那需要额外一次模型调用） |

> **主动说的价值**（强烈建议这么说）：
> 「这里我要说得很准，因为它容易被说成另一回事——**我的窗口压缩是"截断 + 占位标记"，不是"摘要"**。标记里只有轮数和角色，不含内容，所以模型只知道"这里曾经有 2 轮对话"，不知道说了什么。
> **它保住了窗口有界和不静默丢弃，没有保住语义连续**——也就是说，它挡不住"前后矛盾"。真正的摘要要让更早的轮次过一遍模型生成，要多花一次调用，**我没做，这是我明确知道自己缺的一环**。
> 我为什么不直接做摘要？因为**摘要会引入一个新的失败面**：摘错了就是凭空造了个错误前提，而且是静默的。所以我要做的话会先给它配一个"可回退到原文"的路径。」
>
> **这段是本篇里性价比最高的一段**——它把一个"名不副实"变成了一次**设计判断的展示**。面试官听到"我知道它保住了什么、没保住什么"，比听到"我们做了摘要"信任度高得多。

**【落地参考】**
- 窗口压缩：`app/ops/lg_rag/continuity.py:10-45`（`max_full_turns=6`、`group_size=2`；占位符构造在 `:33-40`）
- LC 消息装配（压缩后转 `HumanMessage` / `AIMessage` / `SystemMessage`）：`app/ops/lg_rag/continuity.py:48-75`
- **请求路径入口**：`app/ops/lg_rag/graph.py:27`（`from ...continuity import assemble_graph_messages`）
- 历史来源：`app/ops/session/history.py:12-45`（`load_session_turns(session_id, limit=20)`，从 `ops_runs` 表按会话取最近 20 条 run）
- ⚠️ **存在一份重复实现**：`app/ops/session/continuity.py`（与 `lg_rag/continuity.py` 逻辑相同，但**只被测试引用**）。两份实现有漂移风险，是已知的整理项——**被问到代码组织时可以主动说**，这属于"我知道自己的债"。

#### 1.2.3 长期语义记忆 ❌ —— **但基础设施已经就位 ✅（本篇最有价值的一条）**

这一块**看起来是缺口，实际是资产**。因为做长期记忆需要的底层能力，你在**知识检索**这条线上已经全部做过了：

| 做记忆需要的能力 | 你已有的实现 | 位置 |
|---|---|---|
| 向量存储 + 相似检索 | **Qdrant / pgvector 双后端**，`RAG_VECTOR_BACKEND` 切换（默认 qdrant） | `app/ops/rag/backend.py:19-45` |
| 后端失败时降级 | 即时回退 pgvector（**并且明确禁止"跨进程 fail_streak 当唯一熔断"**） | `app/ops/rag/backend.py:1-4` |
| 双写与迁移 | **影子写**：PG commit 后非阻塞入队；失败进 **DLQ**（`ops_qdrant_dlq`） | `app/ops/rag/shadow_write.py:1`、`:149-184` |
| 迁移前的门禁 | `fio` 磁盘 IO 门禁 + RSS 内存基准 + 迁移**对账**报告 | `reports/qdrant_migrate/fio_gate_*.yaml`、`reconcile_p1_20260813.yaml`、`expand_rss*.json` |

| 规模验证 | 100k / 800k 两档基准（含内存与标量量化变体） | `reports/qdrant_bench_100k.yaml` 等 4 份 |

> **所以正确的口径是**：
> 「**长期记忆我这一期没做**，但我要说清楚一件事——**做记忆需要的基础设施我是现成的**：向量存储（Qdrant，带 800k 规模基准和 p95 实测）、双写与迁移（影子写 + DLQ + 对账）、切分与重排（chunker / reranker）都在跑，只是**现在服务的是"知识检索"，不是"经验记忆"**。
> 这两件事用的**是同一套基础设施，但语义完全不同**：知识是"外部文档，只读、可重建"；记忆是"agent 自己的经历，可写、会冲突、要遗忘"。**所以缺的不是那套技术，是记忆的写入策略、冲突消解和遗忘机制这三件事。**」
>
> **这比说"我们做了向量记忆"强得多**——因为面试官接着问"记忆怎么写入、怎么更新、怎么忘掉"，你有答案框架；而如果你说"做了向量记忆"，这三个问题一个都答不上来。

#### 1.2.4 画像记忆 ❌

完全没有。没有用户偏好表、没有常用对象缓存、没有个性化配置。

> 被问到时：**认 + 说明为什么现在不做**——「画像记忆的前提是"有稳定的长期用户"，我们这一期是任务型单会话，所以没做。要做的话我会先做**事实型画像**（比如"该用户主要负责的项目/仓库"）而不是**偏好型画像**——因为事实型画像**可验证**（能对着数据源核对），偏好型画像只能靠推断，错了没法发现。」

### 1.3 面试必答的四问（缺记忆层时一定会被追到这里）

**这四问是"记忆管理"的真正考点**，不是"你用了什么向量库"。

| 问题 | 为什么难 | 答法要点 |
|---|---|---|
| **什么该记住？** | 无差别全存 = 噪声淹没检索 | 写入要有**准入判据**：① 可复用（不是一次性的）② 稳定（不是会变的快照）③ 与主体相关（不是通用知识——那是 RAG 的活）。**判据要在写入时判，不能等检索时筛**——写入时你有上下文，检索时你只有 query |
| **新旧冲突怎么办？** | 用户换了偏好，旧记忆还在，两条都召回 | ① 每条记忆带**时间戳 + 来源**；② 显式 **supersede**（新记忆声明它取代哪条旧记忆），而不是靠"取最新的"；③ 冲突时**优先信可验证的来源**（用户明确说的 > 系统推断的）。**别指望向量相似度解决时效性——它只懂"像不像"，不懂"新不新"** |
| **记错了怎么纠正？** | 错误记忆一旦写入，会持续污染后续所有决策 | ① 记忆**必须可溯源到原始事件**（哪次对话、哪个回执产生的）；② 必须支持**按源头批量撤销**；③ 纠正动作本身要审计。**没有溯源能力的记忆系统，出错了只能全量重建** |
| **怎么遗忘？** | 只增不减 = 又慢又贵，且合规上过不去 | 三层：**TTL**（时间）、**热度淘汰**（没人召回的自然衰减）、**合规删除权**（按 user 物理删除）。**遗忘必须是显式设计的功能，不是"没做清理"** |

> **一个能收尾的判断**：
> 「我认为这四问里**最难的是第一个（什么该记住）**，因为后三个都是机制问题，第一个是**判断问题**。而判断问题一旦出错，机制再好也救不回来——**你会把噪声记得很牢、把关键信息漏掉。** 所以我要做的话会先做最小的一件事：**只记"事实"，不记"对话"**——事实可以被验证、可以被枚举、可以删，而对话摘要只能靠模型再生成一次，**错了你都不知道。**

### 1.4 记忆管理口述稿（90 秒，可直接用）

> 「记忆我分四层看，而且**这一期我只做了一层半**，我说清楚是哪一层半。
> **工作记忆是落地的**——State + checkpointer，证据本体不进 State。
> **会话记忆做了一半**：窗口压缩保留最近 6 轮，更早的替换成占位标记。这里我要说准——**它是"截断 + 标记"，不是"摘要"**：标记里只有轮数和角色，没有内容。所以它保住了窗口有界，**没保住语义连续**。真正的摘要要额外一次模型调用，我没做，那是我明确知道缺的一环。
> **长期记忆和画像记忆没有做。**
> 但有一条我想主动说：**做记忆需要的基础设施我是现成的**——Qdrant 向量存储、影子双写、DLQ、迁移对账、p95 基准，这些在知识检索那条线上都在跑，只是**现在服务的是"知识"不是"经验"**。这两者共用同一套技术，但语义完全不同：**知识只读、可重建；记忆可写、会冲突、要遗忘**。所以缺的不是那套技术，是**写入策略、冲突消解、遗忘机制**这三件事。
> 如果我来补，顺序是：**先做事实型记忆（可验证、可枚举、可删），再做语义记忆；先解决"什么该记住"，再解决"怎么召回"**——因为第一问错了，后面全是白做。」


### 1.5 被问「那你会怎么补」：记忆语义层的最小方案

§1.3 的四问给出的是**判断框架**，这一节把它落成**一张可以照着开工的表**——每条机制都带"最小第一步 + 怎么自证"，姿势和附录 B 完全一致（**不能自证的机制，等于没装**）。

先给存储 schema（一张表就够，不引入新组件——复用 §1.2.3 已有的向量基础设施 + PG）：

```
ops_memory_facts
  id            uuid
  tenant_id     text        -- 与 Principal 同源，代码构造
  user_id       text
  key           text        -- 规范化事实键，如 "project.primary_repo"
  value         jsonb
  kind          text        -- fact | preference（一期只做 fact）
  source_run_id text        -- 溯源：哪次 run 产生的
  source_turn   int
  supersedes    uuid null   -- 显式取代哪条旧事实
  status        text        -- active | superseded | revoked
  expires_at    timestamptz null
  embedding     vector      -- 走 RAG_VECTOR_BACKEND 同一套
```

| 机制 | 最小第一步 | 怎么自证（一条断言） |
|---|---|---|
| **写入准入** | 一个纯函数 `should_write(candidate) -> bool`，三条判据（可复用 / 稳定 / 与主体相关）全部落在写入路径上，**不在检索时筛** | 喂 10 个候选（5 应存 5 不应存），断言拒绝的 5 条**根本没落库**——不是"存了但没召回" |
| **冲突消解** | 同 `(tenant_id, user_id, key)` 新值写入时**显式置旧值 `status=superseded`**（逻辑失效，不物理删，保审计） | 写新值后召回，断言旧值**不出现**；且旧值在表里**还能查到**（对账用） |
| **纠错撤销** | 按 `source_run_id` 批量置 `revoked` | 造一次"错误事实从某 run 写入"，撤销该 run 全部产出，断言后续召回**零命中** |
| **遗忘** | `expires_at` + 定期任务；删除走 `status` 状态机而非裸 DELETE（合规删除权时才物理删） | 写入一条 TTL=1s 的事实，过期后断言**检索路径查不到**（不是"查到了但过滤掉"） |
| **召回注入** | 召回 = 向量相似 × 时间衰减 × 来源权重（用户明说 > 系统推断）；注入位置在**系统消息尾部独立块**，带 token 预算上限 | 预算超限时断言**截断的是低分条目**，不是随机截断 |

> **口述要点**：
> 「补记忆我会先落**一张事实表 + 一个写入闸函数**，不先碰向量——因为四问里最难的是"什么该记住"，那是**判断问题**，而判断问题用一张表加一个纯函数就能开始验证。向量召回是第二问的事，而且那一问我基础设施是现成的（§1.2.3），接入成本最低。
> 每一条机制我都先写它的**否定性断言**：拒绝的没落库、superseded 的不出现、撤销的零命中、过期的查不到。**先把"坏了能发现"装上，再让功能上线**——这跟我在红线上做的变异检验是同一个思路。」

### 1.6 多 Agent 场景：Agent 之间怎么共享记忆（JD 必答题）

多 Agent 一面到"记忆"，问的几乎一定是**"Agent 之间怎么共享上下文"**。答案要先**按共享范围分三层**——不分层混答，必崩：

| 共享范围 | 载体 | 本仓状态 | 关键设计 |
|---|---|---|---|
| **同一 run 内**（supervisor ↔ 子 Agent / 步骤间） | State + 步骤契约（`produces` / `consumes` / `depends_on`） | ✅ 有 | **共享"结论与引用"，不共享"过程与证据本体"** |
| **同会话跨 run** | `ops_runs` 历史 + 窗口压缩 | ⚠️ 截断+占位 | 见 §1.2.2，保窗口有界、不保语义连续 |
| **跨会话跨 Agent** | 长期记忆（§1.5 事实表） | ❌ 没做 | 按 `tenant_id` 隔离，**可见集仍走 L1 准入闸**——记忆不能成为越权通道 |

**第一层的两条纪律是本仓已有的设计，被问到直接讲**：

1. **证据本体不进 State**（黑盒原则）：子 Agent 的原始检索结果不进全局 State，State 里只放**结论 + 引用**（哪一步产的、去哪取）。否则 State 随步骤数线性膨胀，checkpointer 落盘成本失控——而且**大部分中间证据下游根本不看**。
2. **下游消费靠步骤契约校验**，不靠"上一个 Agent 记得传给我"：`consumes` 不满足就**不调度**，这是代码判断，不是模型自觉。

> **口述要点**：
> 「多 Agent 共享记忆我先按范围分三层。**run 内这一层我是落地的，而且有一条纪律我很坚持：Agent 之间共享"结论与引用"，不共享"过程"**——证据本体不进 State，这不是省 token 的优化，是**边界设计**：每个 Agent 的输入应该由契约声明出来，而不是"碰巧在共享黑板里看到了"。
> 共享黑板模式我不用的原因很具体：**它把"谁依赖谁"从显式契约变成了隐式约定**——改一个 Agent 的输出格式，你不知道会砸到谁。这和我在能力层"未声明契约不得推测性拦截"是同一条纪律。
> 跨会话那一层我还没做，但有一条红线是提前定好的：**记忆召回必须过同一个准入闸**——不能因为"它记得"就让一个 Agent 看到它本来看不到的数据，**记忆系统不能成为绕过可见集裁剪的后门**。」

**【落地参考】**
- 证据不入 State：`app/ops/lg_rag/state.py:200-203`
- 步骤契约 `produces` / `consumes` / `depends_on` 与双阈值截断：`app/ops/lg_rag/multi/step_contract.py`
- 可见集裁剪（fail-closed）：`app/ops/capability/visibility.py:56-72`

### 1.7 长任务不丢信息 / 跨会话怎么延续

这两问常被当成记忆问题问出来，**其实第一问是状态层问题，第二问才是记忆问题**——拆开答本身就是加分点。

| 问题 | 真正归属 | 本仓答法 |
|---|---|---|
| **长任务跑一半，怎么不丢？** | L6 状态与数据，不是 L4 | checkpointer 外置（`LG_RAG_HTTP_CHECKPOINTER=postgres`）+ 事件表 `(run_id, seq)` 唯一约束 + cursor 续传。**恢复 = 从挂起点继续，不重跑模型**；`stranded_checkpoint` 判死给终态 |
| **跨会话怎么延续？** | L4 记忆 | 现状：同会话靠 `ops_runs` 最近 20 条 + 截断占位；跨会话**没有**。要延续的不是"对话"，是**目标与结论**——这正是 §1.5 事实型记忆要接的活 |

> **口述要点**：
> 「长任务不丢信息这件事，我的答案是**不靠记忆，靠状态外置**——checkpointer 落 PG，服务重启后从挂起点恢复，事件按 cursor 回放，**回放不重跑模型**。记忆解决的是另一个问题：**这次会话结束了，下次它还应该知道什么**。
> 这两件事混着设计会两头出错：把长任务状态塞进记忆，记忆会被一次性快照淹没（违反"稳定"判据）；把跨会话延续指望在历史回放，成本随会话长度线性涨。**状态管"一次任务内不丢"，记忆管"跨任务还记得"，边界就在"这个 run 结束没有"。**」

### 1.8 记忆系统怎么评测（和 §3.3 红线层同一套打法）

记忆层一旦上线，**最难回答的问题会从"怎么存"变成"怎么证明它没把系统带坏"**。答案直接复用本仓评测层的三招：

1. **否定性红线**（不是"召回率高就是好"）：
   - 已删除 / 已过期的事实**不得再被召回**；
   - 被 supersede 的旧值**不得出现在召回结果里**；
   - 无任何记忆时，模型**不得幻觉出用户偏好**（这是最容易漏的一条——记忆系统的引入本身会提高"编偏好"的先验）。
2. **变异检验**：故意写入一条错误事实 → 断言它**确实污染了**回答（证明记忆通路是通的，不是空规则）→ 撤销 → 断言污染**消失**。不做第一步，后面的"撤销成功"可能是假通过。
3. **金样集**：构造"新值替换旧值"、"多用户相邻事实"、"事实与当前指令冲突"三类用例进离线评测，**热路径上不加 LLM-as-judge**（和 Prompt 层同一条纪律）。

> **口述要点**：「记忆系统的评测我只信否定性断言——"该忘的还在不在"、"旧值出没出现"、"没记忆时编不编"。正向指标（召回率、命中率）我会看，但它证明不了安全，**一个把所有东西都记住的系统召回率是满分，也是最坏的系统。**」

### 1.9 反模式清单（被追问细节时的避雷表）

| 反模式 | 为什么坏 | 正确做法 |
|---|---|---|
| 全量对话存向量库 | 一次性内容淹没检索，违反"可复用"判据；又贵又慢 | 写入闸在写入时判，只记事实 |
| 用向量相似度判时效 | 相似度只懂"像不像"，不懂"新不新" | 时间戳 + 显式 supersede |
| 静默覆盖，无旧值留存 | 覆盖错了无法对账、无法回退 | 逻辑 supersede + 审计，旧值可查 |
| 摘要不可回退 | 摘错 = 静默造了个错误前提 | 摘要必须能回退到原文（这也是我**现在不做摘要**的原因，§1.2.2） |
| 记忆无 TTL / 无删除权 | 只增不减 = 慢、贵、合规过不去 | TTL + 热度淘汰 + 按 user 物理删除 |
| 记忆召回绕过准入闸 | 记忆成了越权后门 | 召回结果仍过可见集裁剪（§1.6） |
| 在线 LLM 判记忆质量 | 热路径延迟翻倍，还引入新的不确定性 | 判分离线，热路径只留确定性断言 |
| 记忆直接写进 system prompt 正文 | 与指令混杂，无法单独截断 / 审计 | 独立块注入，带预算上限（§1.5） |

## 2. Prompt 管理

### 2.1 本仓真实状态（先看清楚边界，再说方向）

**有的**：

| 能力 | 实现 |
|---|---|
| 命名模板 registry | `TEMPLATES: dict[str, dict[str, str]]`，**以 id 为键的静态字典，写在代码里** |
| 每个模板带版本字段 | `PromptTemplate(template_id, version, body)`，version 取值 `v1` / `v2` |
| 渲染 + 变量校验 | `render(template_id, variables)`；缺变量**抛 `KeyError` 并报出缺哪个**（早失败） |
| 插槽注入 | `slots={"skill": ...}` → 追加 `<!-- slot:skill -->` 块，供 Skill 提供内容 |
| 部分 prompt 可切版本 | 走环境变量，全局单值（如 `RAG_GRADER_PROMPT` = `v1`/`v2`，**未知值回退 v1 并打警告**） |

**没有的**（重要，别含糊）：

- ❌ **A/B 测试、灰度分流**（按 user / thread 打标）
- ❌ **DB 化 / 运营后台**（改 prompt 要发版）
- ❌ **变更审计**（谁在什么时候改了哪句、为什么）
- ❌ **一键回滚**（回滚 = 改代码 + 发版）
- ❌ **效果归因**（不知道这次变好/变差是不是 prompt 造成的）
- ❌ **注入防护**（见 06 篇 §5.3：只有 system prompt 里的软约束）

**一个必须知道的规模事实**：registry 里**只有 3 个模板**——`lg_rag.intent.system`、`lg_rag.supervisor.system`、`lg_rag.supervisor.suffix.system`（编排侧的系统提示）。**其余 prompt 是硬编码在各个模块里的字符串**，只有少量能用 env 切版本。

> 这个事实要说出来，而且**说了反而加分**：
> 「我的 prompt registry 目前只覆盖了 3 个——**编排侧的系统提示**。其他 prompt 还散在各个模块里，只有一部分能用环境变量切版本。**这是我知道的不一致**：因为当时优先做的是"让最常改、最容易改坏的那几个先有版本"，也就是 planner 那几条。**剩下没进 registry 的，恰好是改动频率低的**——所以这个取舍是有意的，不是我忘了。」

#### 2.1.1 一个真实的工程痛点：模板引擎和 JSON 语法打架

prompt 里有大量 JSON 示例（意图分类、子任务拆解都要输出 JSON），而模板是用 `str.format(**vars)` 渲染的。结果就是：**JSON 里的每个花括号都必须双写**：

```python
'{{"subtasks": [{{"id": "t1", "type": "rag|extract|tool", "input": "..."}}]}}'
```

这不是小问题，它带来三个后果：

1. **手写极易漏**，漏一个就 `KeyError`（好在是启动/渲染期就炸，不是线上炸）。
2. **prompt 的可读性下降**——写 prompt 的人要同时想"文案对不对"和"转义对不对"。
3. **它把"改 prompt"变成了一件需要工程能力的事**——业务同学改不了，必须找开发。

> **这是个很值钱的素材**，因为它证明你真的动手改过 prompt，而不是只在架构图上画过一个框：
> 「我踩过一个具体的坑：**模板引擎用 `str.format`，而我的 prompt 里全是 JSON**——意味着每个花括号都要双写。结果是**改 prompt 变成了一件必须由开发做的事**，业务同学碰不了。
> 如果要解，我会换成**不做转义的模板方式**（比如 `string.Template` 的 `$var`，或者干脆把变量以独立块拼进去，正文完全字符串化）。**这不是个技术难题，但它决定了 prompt 能不能交给非开发同学维护**——这一点比"有没有版本号"更影响实际迭代速度。」

**【落地参考】**
- registry 与 3 个模板 id：`app/ops/prompts/templates.py:5` 起
- 模板对象与版本字段：`app/ops/prompts/render.py:11-17`
- 取模板（未知 id 抛 `PromptTemplateNotFoundError`）：`app/ops/prompts/render.py:24-32`
- 渲染 + 缺变量早失败 + slots 注入：`app/ops/prompts/render.py:35-53`
- env 切版本（全局单值 + 未知值回退告警）：`app/ops/rag/grader.py:144`（`RAG_GRADER_PROMPT`）、`app/ops/prompts/packs.py:34`（`PACK_VERSION = "v1"`）
- **JSON 花括号双写实例**：`app/ops/prompts/templates.py` 的 `lg_rag.supervisor.system` body

### 2.2 面试必答的四问

| 问题 | 答法要点 |
|---|---|
| **改了 prompt 效果变差，怎么回滚？** | 先分清"回滚"要回滚到什么粒度：**整体回退**（env 够用，改配置 + 重启）vs **按人群回退**（需要分流层）。**我现在只有整体回退**。判断标准：只要改动是"整体的、可回退的"，env 就够；一旦要"新用户用新 prompt、老用户保持旧的"，**需要的不是 prompt 版本表，而是分流层**（按 user/thread 打标 + 记录命中版本） |
| **怎么知道改好了？** | **不用感觉判断**。两层：**确定性 grader**（路由/白名单/计划结构的字段比对）+ **离线金样集**（含负样本）。而且**热路径上禁 LLM-as-judge**——在请求路径上加一次模型调用，延迟成本翻倍，还把"可观测"变成"新的不确定性来源"。**判分放离线，不放请求路径** |
| **多版本怎么共存？** | 版本要加在**模型看得见的那一层**。对 prompt 是 `template_id` 上带 version；对能力是 `capability_id` 上带 version（如 `oa.doc.search.v2`）。**理由**：日志里必须能看出"这次命中的是哪一版"，否则效果变差你连归因都做不了。旧版本保留并标 deprecated，**不删除**——跟旧接口给 410 但保留代码是同一个道理 |
| **Prompt 注入怎么防？** | **不在 prompt 层防。** 提示词里的约束是**行为建议，不是安全控制**——你这道护栏也是模型，它就能被同一类手法绕过。所以顺序是：**① 执行层堵死**（注入想达成的效果无非是越权调用 / 读不该读的数据 → 可见集裁剪 + Policy + 写操作人工确认已经在执行层堵住了）；**② 输入结构隔离**（用户内容只能进被声明的槽位，不参与指令拼装）；**③ 最后才轮到检测**（规则 + 抽样 judge）。**顺序不能倒——检测是最不可靠的一层，不能让它当第一道闸** |

> 注意第四问：**这一问你要主动认"我没做注入防护"**，然后给出上面这个顺序。因为"我认为提示词里的约束不是安全控制"这句话本身就是很强的观点——**它把"没做"讲成了"我不信这个做法"**，比硬说"我们做了多层护栏"安全得多。

### 2.3 Prompt 管理口述稿（90 秒）

> 「Prompt 我按**资产**来管，但现在只做到最基础的一档，我说清楚边界。
> **有的**：以 id 为键的模板 registry，每个模板带 `version` 字段；渲染层缺变量会**早失败并报出缺哪个**；有插槽注入点给 Skill 用；少数 prompt 能用环境变量切版本。
> **没有的**：A/B 和灰度分流、DB 化、变更审计、一键回滚、效果归因。
> 还有两个具体的诚实点：**第一，registry 只覆盖了 3 个模板**——编排侧的系统提示，其余 prompt 还散在各模块里。这是有意的取舍：**先让最常改、最容易改坏的 planner 那几条有版本**。**第二，我的模板用 `str.format` 渲染，而 prompt 里全是 JSON，所以每个花括号都要双写**——结果就是**改 prompt 必须找开发，业务同学碰不了**。这不是技术难题，但它直接决定了 prompt 的迭代速度。
> 如果要往前走，我的顺序是：**先解决"改得动"（去掉转义、把 prompt 从代码里拿出来），再解决"看得见"（变更审计 + 命中的是哪一版），最后才解决"分得开"（分流层）**。**分流层我放在最后**，因为一旦上了它，所有 prompt 相关的排查都要先问"他命中的哪一版"——那是复杂度，不是能力。」

### 2.4 Prompt 的落地路径（分三阶段，答"怎么补"时用）

| 阶段 | 目标 | 做什么 | 判断到位没有 |
|---|---|---|---|
| 一 | **改得动** | 去掉 `str.format` 转义；prompt 从代码搬到数据（DB / 配置中心）；加变更审计 | 非开发同学能改一句文案并上线 |
| 二 | **看得见** | 每次调用记录：template_id + version + 渲染后 hash；效果指标按 version 聚合 | 改动后能回答"是哪个版本、变好还是变差" |
| 三 | **分得开** | 按 user / thread 分流；灰度比例；A/B 对照 | 能"新用户试新 prompt，老用户不动"，且能一键回退到具体人群 |

> **一句话判断**：`第一阶段是"能不能迭代"，第二阶段是"改动可不可归因"，第三阶段才是"A/B 测试"。绝大多数团队跳过了第一阶段直接想做第三阶段——**结果是分流层建好了，但还是没人能安全地改一句 prompt。**

## 3. 成熟企业 Agent 的完整模块地图

### 3.1 十层地图（总表）

先给结论：**一个能上生产的企业 Agent，模块不是 5 个，是 10 层。** 其中 7 层是功能层，3 层是**横切层**（每层都要用，单独拿出来看才不丢）。

| # | 层 | 一句话职责 | 不做的代价 | 本仓 |
|---|---|---|---|---|
| L0 | **接入与身份** | 谁在调、代表哪个租户、能进到哪 | 越权、串租户 | ⚠️ 有，单实例 |
| L1 | **决策与准入** | 模型能看见什么、能做什么、能做多少 | 模型可调任意工具 | ★★★★★ |
| L2 | **编排** | 怎么拆、怎么并发、怎么收、什么时候叫人 | 长任务失控 / 无终态 | ★★★★☆ |
| L3 | **能力（工具）** | 注册、门序、幂等、熔断、降级、回执 | 写操作重复 / 静默失败 | ★★★★★ |
| L4 | **上下文与记忆** | 窗口里放什么、跨会话记得什么 | 又贵又忘事 | ★★☆☆☆ |
| L5 | **模型层** | 选哪个模型、输出怎么保证是结构化的 | 解析失败 / 成本失控 | ★★★☆☆ |
| L6 | **状态与数据** | 状态存哪、事件能不能回放 | 挂了就丢 / 没法定位 | ★★★★☆ |
| L7 | **安全与合规**（横切） | 注入、沙箱、脱敏、删除权 | 事故 / 合规过不去 | ★★☆☆☆ |
| L8 | **可观测与评测**（横切） | 出事能定位、改动能证明没退步 | 不敢改、改坏了不知道 | ★★★★★ |
| L9 | **交付与运维**（横切） | 灰度、容量、灾备、开关 | 上不了生产 | ★☆☆☆☆ |

### 3.2 逐层说明（职责 + 关键一问 + 本仓状态）

#### L0 接入与身份
- **职责**：网关、鉴权、**主体/租户识别**，把"调用者是谁"变成一个**代码构造的可信对象**。
- **关键一问**：*身份从哪来？* —— 必须是代码从会话构造，**不能取模型产出**。本仓 `Principal` 的注释写得很直白："必须由代码从会话构造"。
- **本仓**：`app/ops/auth.py`、`security.py`、`tenant_context.py`、`deps.py`；Java 侧有 `ops-desk-api-java-gateway`（Spring Cloud Gateway）+ `ops-desk-eureka-server`。⚠️ **单实例，多副本未验证**——这条是边界，别说成"我们已经做了服务发现与多副本"。
- **落地参考**：`app/ops/capability/visibility.py:56-72`（Principal 从 ctx 构造，注释明确"不取自模型产出"）

#### L1 决策与准入（**你很可能把它合进了"能力注册表"，但它其实是独立的一层**）
- **职责**：在模型**看见之前**决定它看见什么（可见集裁剪），在调用**发出之前**决定放不放行（Policy 门）。
- **关键一问**：*模型能不能"自己决定"用哪个工具？* —— 不能。**它只能在被裁剪过的名单里选**。名单由代码算（注册表 ∩ 策略 ∩ 身份）。
- **本仓**：`app/ops/strategy/`（builder / critic / intent）+ `capability/policy.py`、`baseline.py`、`visibility.py`、`budget.py`。**这一层是本仓最强的一块，值得单独讲。**
- **为什么它是独立层**：因为"注册表里有什么"和"这次这个用户能看见什么"是两个问题。**注册表是全局的，可见集是每次请求算出来的**——混成一层，你就没法回答"为什么他这次看不到这个工具"。

#### L2 编排
- **职责**：拆解、调度、依赖、并发归并、**收敛（预算）**、以及什么时候叫人。
- **关键一问**：*任务跑不完怎么办？* —— 必须有**上限 + 终态**：上限（步数/子任务/墙钟），且**每个计划项都必须有终态**（含错误终态），**绝不允许"悬挂但不告警"**。
- **本仓**：`app/ops/lg_rag/graph.py`（basic / router）、`lg_rag/multi/graph.py`（supervisor）、`lg_rag/multi/step_contract.py`、`hitl/`。★ 保留 `basic` 当对照基线是加分项。

#### L3 能力（工具）层
- **职责**：注册、加载期不变式、门序、幂等、熔断、降级、回执。
- **关键一问**：*写操作失败了会怎样？* —— **必须能回答"要么一张单，要么没有"**，而不是"我不知道发出去没有"。
- **本仓**：`app/ops/capability/` 全模块。**主叙事。**

#### L4 上下文与记忆
- **职责**：窗口预算、压缩、检索（RAG）、长期记忆。
- **关键一问**：*上下文超了怎么裁？* —— 判断依据是**"丢了之后模型会不会编"**。见 §1。
- **本仓**：`session/` + `lg_rag/continuity.py`（截断+占位）+ `multi/step_contract.py`（双阈值：单值 200 / 整块 800）+ `rag/`（Qdrant/pgvector）。❌ 长期/画像记忆。

#### L5 模型层
- **职责**：provider 抽象、模型选择/路由、**结构化输出保证**、超时/重试/熔断、成本。
- **关键一问**：*模型返回的不是合法 JSON 怎么办？* —— 必须有**修复 + 校验 + 有限重试**，并且**失败时绝不返回半成功数据**。
- **本仓**：`app/llm/`（provider 字典 + 超时 + fallback 链）+ `app/ops/structured_output/`（parse → repair → validate → complete）。⚠️ 缺通用重试退避、缺熔断、缺路由与成本归集。

#### L6 状态与数据
- **职责**：checkpointer、事件存储与回放、回执、审计。
- **关键一问**：*服务重启，一个跑到一半的任务还在吗？* —— 状态必须外置，且**回放不能依赖重跑模型**。
- **本仓**：`lg_rag/checkpointer.py`、`event_store.py`（`(run_id, seq)` 唯一约束 + cursor 续传）、`db/models.py`。

#### L7 安全与合规（**横切**）
- **职责**：注入防护、输出合规、沙箱、脱敏、数据删除权。
- **关键一问**：*假设防线被突破，损失可控吗？* —— 判断标准是**"可逆性"**：写操作人工确认 + 幂等 + 回执，让损失可界定。
- **本仓**：凭据只走 env（`OPS_CAP_CRED_`）、密钥形键拒绝入清单、args 摘要脱敏、sandbox/cli/MCP 默认关、出站不走环境代理。❌ 注入防护、PII 识别、出口脱敏、真沙箱（adapter 是 Mock）、删除权。

#### L8 可观测与评测（**横切，也是本仓的差异化武器**）
- **职责**：出事能定位（trace/metrics/audit）+ **改动能证明没退步**（eval / 红线 / 回归）。
- **关键一问**：*你怎么证明这次改动没让系统变差？* —— 这是**绝大多数候选人答不上来的问题**。见 §3.3。
- **本仓**：`app/ops/tracing.py`（Langfuse + span 字段）、`app/ops/admin/capability.py`（`/runtime`、`/metrics`、`/receipts`、`/hitl/runtime`）、`evals/` + `evals/agent/redlines/capability_v1.yaml`（R0–R15）、`scripts/acceptance/`。

#### L9 交付与运维（**横切**）
- **职责**：配置与灰度、发布、容量规划、灾备、运行时开关。
- **关键一问**：*怎么在不发版的情况下关掉一个出问题的能力？* —— 需要**运行时开关**，而且**它必须和正常变更走两条不同的审计线**。
- **本仓**：有**熄火开关**（`capability/budget.py:131-158`，支持 `oa.*` / `write:*` / `*` 通配）与 `hitl_drain_audit.py`（升级前排空审计）。❌ 灰度、压测、灾备、删除权全无。

### 3.3 你漏掉的三块，恰好是最能拉开差距的

#### ① 评测与红线层 —— **"我怎么证明它没退步"**

大多数人能讲"我做了什么"，**讲不了"我怎么证明它现在还是对的"**。这是最大的分水岭。

本仓有：
- **红线清单**：`evals/agent/redlines/capability_v1.yaml`，**R0–R15 十六条**，每条都有**正向断言 + 反向对照**（只做正向会得到假通过——"一律拒绝"天然满足"该拦的拦住了"）。
- **变异检验**：新加红线后**把行为改坏一次，确认红线真的会 fail**，否则可能是空真。
- **确定性 grader**：路由命中 / 白名单匹配 / 计划结构匹配，**不靠 LLM-as-judge 自评**。
- **基线 diff**：改动会不会让规划飘移是**可测的**。
- **九层验收** + 真进程联调脚本（`scripts/acceptance/hitl_approval_loop.sh` → `hitl_approval_loop.py:93-231`，**9 个主步骤 + 2 个对照子步，共 17 项断言**（PG 模式 16 项））。

> **口述要点**：「我的验收不是"跑通就算过"，是**"任一条红线被突破就不算通过"**——它是**否定性的**，不是总分制的。而且每条红线都有**反向对照**，因为只做正向断言会得到假通过。新加一条红线之后我还要**把行为改坏一次**，确认它真的会 fail——**不做这步，你可能加了条永远为真的空规则。**」

#### ② 契约层 —— **把"模型的不确定性"挡在系统边界外**

这是"工程化"和"调 prompt"的分界。**三套契约，各管一段**：

| 契约 | 管什么 | 位置 |
|---|---|---|
| **参数契约**（`args_schema`） | 出门前校验参数**形态** | 清单声明 + 加载期强校验 |
| **结果契约**（`output_schema` / `result_contract`） | 拿到结果后校验**业务完整性**（缺必填 / 条数不足 / 空且可疑就判失败） | `app/ops/capability/result_contract.py` |
| **步骤契约**（`produces` / `consumes` / `depends_on`） | 上一步产出**能不能满足**下一步输入 | `app/ops/lg_rag/multi/step_contract.py` |

> **口述要点**：「契约的作用不是"让模型更准"，是**"让模型的错在边界上被挡住"**。而且有一条纪律我特别在意：**只对显式声明了契约的能力做校验**——**未声明契约的能力不得被推测性拦截**。因为契约是显式声明出来的，**系统不替你猜**。猜出来的契约会变成一种隐形的硬编码，改起来没人敢动。」

#### ③ 人闸与幂等层 —— **让写操作可逆、可对账**

企业场景里这是"能不能上线"的开关，因为**只有它能让"做错了"变成"能挽回"**。

本仓有：
- **清单层硬要求**：写操作必须声明幂等键、必须声明人工确认；高危必须人工确认——**否则加载失败**（不是运行时提示）。
- **编排层唯一的人闸原因**：`HITL_REASONS = {prefix_touch_required}`——**只有"要改不可变前缀"才叫人**，因为改参数 = 换幂等键 = 一次新的写 = 新的副作用。其余拦截（前驱失败、缺字段）都**不需要人**。
- **幂等**：键由 `(tenant, 能力, args)` 派生 → 唯一约束 → 租约状态机 → **命中重放上次业务结果**。
- **回执**：12 字段可对账（含 `subtask_id` / `tenant_id` / `idempotency_key` / `write_confirmed`）。

> **口述要点**：「**审批是有成本的，到处挂 HITL 等于没有 HITL。** 我只在最贵、最不可逆的那个点叫人——**会产生新副作用的时候。** 这就是为什么我的人闸只有一条原因：要改不可变前缀。」

### 3.4 讲这张地图的正确姿势（60 秒口述稿）

> **不要平铺十层**——面试官记不住，而且听起来像背的。要说成**三类**：

> 「我把 Agent 的模块分三类，**分类依据是"缺了会造成什么"**：
>
> **第一类是承重墙——缺了会出不可逆的错。** 四块：能力与准入、契约、状态外置、人闸与幂等。这四块缺任何一个，我都会明确说"这个不能上线"——因为它们的失效方式是**静默的**：能力没闸是"悄悄越权"，契约没校验是"带错数据往下走"，状态没外置是"重启就丢"，幂等没有是"重复建单"。**静默失效是最贵的失效。**
>
> **第二类是放大器——缺了只是不好用。** 可观测、记忆、Prompt 资产、模型路由。它们决定的是**迭代速度**，不是**正确性**。所以我把它们排在承重墙后面：先保证不出事，再保证改得快。
>
> **第三类是成熟度标志——缺了说明还没上生产。** 灰度、容量规划、灾备、合规删除权。这一类的共同前提是**"有真实流量、多实例、有合规要求"**——**量级没到之前做它，是在给一个还不存在的问题写方案。**
>
> 这个分类对我有用的地方是：**别人问"你下一步做什么"，我不用凭感觉答**——先看承重墙有没有缺角，缺了就先补；承重墙齐了，再看放大器哪个最卡迭代。」

## 4. 一页速答

| 问题关键词 | 一句话答案 |
|---|---|
| **记忆分几层** | 四层：工作记忆（State+checkpointer ✅）/ 会话记忆（截断+占位 ⚠️）/ 长期语义记忆（❌ 语义层，✅ 基础设施）/ 画像记忆（❌）。**被问先分层，再答** |
| **记忆什么该记住** | 三条准入判据：可复用、稳定、与主体相关。**判据在写入时判，不能等检索时筛**——写入时有上下文，检索时只有 query |
| **记忆冲突** | 时间戳 + 来源 + 显式 supersede。**别指望向量相似度解决时效——它只懂"像不像"，不懂"新不新"** |
| **记忆纠错** | 必须可溯源到原始事件 + 按源头批量撤销。**没有溯源的记忆系统，出错了只能全量重建** |
| **记忆遗忘** | 三层：TTL（时间）/ 热度淘汰 / 合规删除权。**遗忘是显式设计的功能，不是"没做清理"** |
| **会话窗口压缩** | 保留最近 6 轮全量，更早替换为**占位标记**（只带轮数+角色）。**是"截断+标记"，不是"摘要"**——保住窗口有界，**没保住语义连续** |
| **向量基础设施** | ✅ 有：Qdrant/pgvector 双后端（`RAG_VECTOR_BACKEND`，默认 qdrant，失败即时回退）、影子写 + DLQ、迁移 fio 门禁 + 对账、p95 实测（pgvector 2.56ms / Qdrant 14.6ms，预算 150ms） |
| **知识 vs 记忆** | **共用同一套技术，语义完全不同**：知识只读、可重建；记忆可写、会冲突、要遗忘。缺的不是技术，是**写入策略 / 冲突消解 / 遗忘机制** |
| **记忆怎么补（最小方案）** | 一张事实表（key/value/source/supersedes/status/expires_at）+ 写入闸纯函数。**先解决"什么该记住"，再碰向量召回**；每条机制配一条否定性断言（§1.5） |
| **多Agent共享记忆** | 按范围分三层：run 内靠步骤契约（**共享结论与引用，不共享过程**）、同会话靠 `ops_runs`+占位、跨会话需事实型记忆。**记忆召回必须仍过准入闸，不能成越权后门**（§1.6） |
| **长任务不丢 vs 跨会话延续** | 前者是状态层问题：checkpointer + 事件回放，**恢复不重跑模型**；后者才是记忆问题，延续的是**目标与结论**不是对话（§1.7） |
| **记忆怎么评测** | 否定性红线：已删/过期不得召回、superseded 旧值不得出现、无记忆不得幻觉偏好。**写入→污染→撤销→消失 全链路变异检验**（§1.8） |
| **Prompt registry** | 静态字典 + `version` 字段 + 渲染层缺变量早失败 + slots 注入。**只覆盖 3 个模板**（编排侧系统提示），其余散在各模块 |
| **Prompt 回滚** | 只有**整体回退**（env 单值，改配置+重启）。**按人群回退需要分流层，我没有** |
| **Prompt 怎么知道改好了** | 确定性 grader（路由/白名单/计划结构）+ 离线金样集含负样本。**热路径禁 LLM-as-judge** |
| **Prompt 多版本共存** | 版本加在**模型看得见的那一层**（prompt 是 template_id 上带 version，能力是 capability_id 上带 version）。旧版本标 deprecated **不删除** |
| **Prompt 注入防护** | **没做**。立场：提示词里的约束是行为建议、不是安全控制。顺序：①执行层堵死 ②输入结构隔离 ③最后才检测——**顺序不能倒** |
| **Prompt 真痛点** | 模板用 `str.format`，prompt 里全是 JSON ⇒ **每个花括号必须双写** ⇒ 改 prompt 必须找开发。**它决定迭代速度，比"有没有版本号"更实际** |
| **模块几层** | **10 层**：7 功能层（接入身份/决策准入/编排/能力/上下文记忆/模型/状态数据）+ 3 横切层（安全合规/可观测评测/交付运维） |
| **决策准入为何独立** | 「注册表里有什么」是全局的，「这次这个用户能看见什么」是每请求算的。**混成一层就答不出"为什么他这次看不到"** |
| **最拉开差距的三块** | ① 评测与红线 ② 契约（参数/结果/步骤三套）③ 人闸与幂等。**它们回答的是"凭什么敢上生产"** |
| **讲地图的姿势** | 分三类：**承重墙**（缺了静默出错）/ **放大器**（缺了只是不好迭代）/ **成熟度标志**（缺了说明还没上生产）。依据：**缺了会不会造成不可逆的错或看不见的错** |
| **下一步做什么** | 先看承重墙有没有缺角 → 再看放大器哪个最卡迭代 → 成熟度标志等量级到了再做 |

## 附录 B · 面试官说「这些我们都没有，你会怎么补」

> **不要罗列**。给一个**排序原则 + 每项的第一步 + 验证方式**。这里最容易被追问"为什么是这个顺序"，所以顺序本身要有依据。

### B.1 排序原则（先背这句）

> 「我按**"缺了会不会造成不可逆的、或者看不见的错"**排。会造成这两类的先补，其他往后放。
> 因为**可逆的错误可以事后修，看得见的错误可以事后查**——**而不可逆 + 静默的错误，你连'出过事'都不知道。**」

### B.2 按这个原则得出的顺序

| 序 | 补什么 | 为什么排这 | 第一步（最小可验证动作） | 怎么验证 |
|---|---|---|---|---|
| 1 | **契约**（参数/结果/步骤） | 缺了会**带错数据往下走**，且静默 | 先只给**写操作**声明结果契约（读的错了下游还能发现） | 构造"结果缺必填字段"的桩，断言它**判失败**而不是当成功 |
| 2 | **幂等 + 人工确认** | 缺了会**重复产生副作用**，不可逆 | 先给最贵的那个写操作做幂等键 + 唯一约束 | 同键并发调 100 次，对端**只被请求 1 次**；再改一个参数，断言**是新的一次写** |
| 3 | **状态外置 + 事件回放** | 缺了**重启就丢**，且没法定位 | 先落事件表（`run_id`+`seq` 唯一约束） | 断线重连按 cursor 续传，**不重跑模型**；跨用户查别人的 run 必须 404 |
| 4 | **准入闸（可见集 + Policy）** | 缺了模型可调**任意工具** | 先把**写与高危**从默认可见集里拿掉 | 构造越权 prompt，断言**下游零请求**（不是"被拒绝了"，是**没发出去**） |
| 5 | **契约化的评测与红线** | 缺了**不敢改**，且改坏了不知道 | 先写 3 条**否定性**红线（任一条破就不算过） | 每条红线做**变异检验**：把行为改坏，确认它真的 fail |
| 6 | **记忆（事实型优先）** | 缺了只是不好用，但**做错了会长期污染** | 只记**事实**不记对话——事实可验证、可枚举、可删 | 删一条事实，断言它不再被召回；改一条，断言旧值不再出现 |
| 7 | **Prompt 资产化** | 决定**迭代速度** | 先去掉 `str.format` 转义 + 记录"命中的哪一版" | 非开发同学能安全改一句文案并上线 |
| 8 | **灰度 / 容量 / 灾备 / 合规删除** | 前提是**有真实流量和多实例** | **先不做**——说清楚"等量级到了从哪接进来" | — |

### B.3 三条纪律（收尾用）

1. **先做"能自证"的那一件。** 排在前面的每一项，验证方式都是**一条可执行的断言**，不是"应该没问题"。**不能自证的机制，等于没装。**
2. **每说一个"没做"，后面必须跟一个"我会怎么排优先级"。** 资深面真正在看的不是"你做过多少"，而是**"你知不知道自己缺什么、先补哪个"**。
3. **别把"没做"说成"我们做了一些探索"。** 模糊词听起来像没做，而且会被追问到崩。**要么给 file:line，要么说"没做"。**
