# 企业 Agent（OA + 智能体）· 背景梳理与需求点全景

> 用途：面试前把「企业 Agent」这条线的产业背景、对标、北汽现状、需求点全景梳理清楚
> 前提：猎头推荐岗，判断对方是**企业 Agent 方向**（与简历最贴合）
> 全部外部来源在文末列出，可查

---

## 一、结论先行：企业 Agent 的第一站在哪

**行业已经形成共识：企业 AI 的第一站落在「内部服务台 + 审批流」，早于对外窗口。**

FastGPT 在 2026-08 公开的一批企业内落地项目（IT 报障、财务审单、供应商初筛、考勤报销、制度查询）总结出的三条特征，是整条线的纲领：

1. **这些工作有三个共同特征：高频、重复、有明确依据可循**——正好落在 AI 能承接的区间里。
2. **企业对内部场景的容错要求反而更清晰：查询可以先放开，写入与审批必须留住人。**
3. **这让内部服务台成为验证 AI 治理规则的合适起点。**

> 第 2 条是整个方向的战略核心。**它意味着「先做只读，再碰写入」不是保守，是行业验证过的最优路径。** 你后面所有方案的分期，都可以挂在这一句上。

**为什么是 OA 而不是业务系统？** 因为 OA 是唯一一个「全员每天用、流程清晰、制度有明文、单据有结构」的入口。业务系统各有各的边界，OA 是横向的。

## 二、产业结构：谁在做、做成什么样

### 2.1 三种形态

| 形态 | 代表 | 特征 | 对你意味着 |
|---|---|---|---|
| **老 OA 厂商加 AI** | 致远互联 AI-COP、泛微、蓝凌 | 有流程引擎和权限底座，但 AI 是新增层；卖点是「**把组织与流程模型化为可操作对象**」 | 存量系统的改造者。他们的图是「AI 是加出来的」 |
| **协同平台自带智能体** | 飞书 aily / 多维表格、钉钉 AI 助理 | 开箱即用，员工自助搭；**门槛低但治理弱** | **北汽现在大概率在这条路上**（福田就是飞书 + OpenClaw） |
| **AI 原生平台** | FastGPT 一类开源企业 AI 平台 | 从 AI 出发，反接企业系统；强在 RAG 和编排，弱在流程与权限 | 你做的事和这类最像，但你有流程侧的机制积累 |

### 2.2 汽车行业直接对标：延锋国际（上汽集团旗下）——**最重要的一条**

他们把 AI 接进了 **IT、财务、采购** 三条线：

| 场景 | 做法 | 结果 |
|---|---|---|
| **iSAP IT 运维机器人** | SAP 运维手册 + FAQ 建知识库 → 对话式识别故障意图 → **集成企业微信一键提交工单** | **70% 重复咨询自动化**，响应从小时级→秒级 |
| **财务 AI 智能审单** | 财务制度与审核规则入库 → AI 提取票据信息做合规校验 → **嵌入 BPM 审批流程** | 年单据量 **52 万张**；单据秒级初审；**异常单据仍由人工复核并反向优化模型** |
| **供应商智能推荐** | 对接企业数据仓，多维匹配绩效/资质/产能 → 输出推荐清单并**标注风险厂商** | 初筛从**数天→几分钟** |

**这一条为什么对你极其重要**：
- **同行业**（汽车零部件），说明车企的思路和方法是可以直接类比的
- **「异常单据仍由人工复核」= 你讲的 HITL**，而且是行业标准做法，不是你的个人偏好
- **「企业微信一键提交工单」** = 你讲的「Agent 出口在 Host，不在模型」
- **「嵌入 BPM 审批流程」** = 你讲的「把闸放在链路上，不是放在提示词里」

### 2.3 另外两个可引用的对标

- **大型医药制造企业**：三个内部智能体分别放在**管理层、厂区员工、OA 入口**——
  - 人才数据决策智能体：**通过 MCP 工具对接人力、销售与项目数据库**，报告效率 +90%
  - 厂区员工自助问答：专属制度知识库嵌入**企业公众号**，员工在微信里问考勤、工卡补办、通勤班车、报销流程
  - **OA 智能助手：自然语言发起流程（「下周三请假 1 天」→ 提取信息预填表单 → 实时查审批进度），流程发起从 3–5 分钟缩到 30 秒以内**
- **上海邮电设计咨询研究院**：**权限隔离做在知识库这一层**——700+ 份企业制度**分单位隔离存储**，员工只能检索**本单位权限内**的文件

> 最后这条就是「可见集裁剪」的企业版：**不是回答时才过滤，是存储时就隔离。**

## 三、北汽的现状与缺口（基于第八、九节的公开信息）

### 3.1 已有的基础

- **协同底座**：飞书（多维表格、aily）；北汽新能源已有 33 个部门 / 44 名数智化专员
- **已落地的内部 Agent 样例**：AI 机器人做用户调研、积压与呆滞预防处置、生产订单变更数据自动测算、财务 RPA 审核（20 分钟→2 分钟）、智能体工作流辅助品牌营销、**数字员工「胡一一」**、AI 直播与视频剪辑
- **福田「长超小福」**：飞书多维表格 + OpenClaw 框架；**先全员禁用 Excel，搭全生产流程数据底座**；**打通 ERP、MES**；**「正测试让 AI 直接操作工业系统，关键操作保留人工确认」**
- **组织动作**：研究总院群组制改革；北汽新能源成立「AI+数智化委员会」（一把手挂帅），推动**「组织、流程、系统、数据」统一**

### 3.2 缺口（也就是 JD 里「做一个多 Agent 平台」要填的）

| 缺口 | 表现 | 你能对上什么 |
|---|---|---|
| **缺纳管层** | 现在是用飞书 / OpenClaw 这类外部框架一个个拼，**每个 Agent 各自接系统、各自持凭证** | Capability Host：注册表 + 可见集裁剪 + 精确 id 分发 |
| **缺写操作闸** | 「关键操作保留人工确认」目前是**逐场景手写的**，没有统一机制 | per-request HITL：冻快照 → 管理员审批 → 参数变则作废 |
| **缺对象模型** | 「组织、流程、系统、数据」还是四个名词，**没有被模型化为可操作对象** | 类型化对象 + 类型化关系 + 可验证锚点 |
| **缺审计可重建** | Agent 做过什么、以谁的名义做的、依据是什么 | side_effect_receipts + run_events 回放 |
| **缺评测口径** | 内部 Agent 的效果目前多半靠满意度/节省时间讲故事 | 分层评测、含负样本的金样集、不以单一分数冒充总分 |

## 四、需求点全景（**本节的扩充是重点**）

按「风险梯度」分六层。**从只读到主动，风险逐层升高。**

### A 类 · 找得到 + 答得准（只读，低风险）

| 编号 | 需求点 | 关键难点 |
|---|---|---|
| A1 | **制度问答**：考勤、年假、差旅住宿标准、报销要求、用章流程、加班调休 | 制度有**版本**（2024 版 vs 2026 版）、有**适用范围**（事业部/职级/地区）、有**例外条款**。答错代价高 |
| A2 | **文档定位**（不是问答，是找到并给出链接）：「二期项目的验收报告」「去年那份供应链框架协议」 | **权限校验**：我有没有权看这份？→ 可见集裁剪的企业版 |
| A3 | **找人 / 找关系**：「这个项目谁负责」「这个流程该找谁批」「XX 部门对接人是谁」 | 组织架构 + 职责关系 + 兼岗与代管 |
| A4 | **查我的**：「我还有几个待办」「我上个月报销到哪了」「我年假还剩几天」「我那个工单谁在处理」 | **强隔离**：个人数据不能串。这是**对象级授权**的最典型场景 |
| A5 | **历史工单检索与复用**：「上次打印机坏了是怎么解决的」「这个报障以前谁处理过」 | 沉淀——把个人经验变成组织资产 |
| A6 | **跨库知识聚合**：制度在 OA、技术文档在 Wiki、项目资料在网盘、关键结论还散在邮件和群里 | 多源 + 去重 + 冲突时以谁为准 |

### B 类 · 帮填 + 起草（半写，中风险）

| 编号 | 需求点 | 关键难点 |
|---|---|---|
| B1 | **自然语言发起流程**：「下周三请假 1 天」→ 提取信息 → **预填表单** → 员工确认后提交 | 时间/人的实体抽取；**多轮澄清**（哪天？请哪种假？） |
| B2 | **IT 报障工单草拟**：「三楼打印机坏了」→ 自动分类、定级、判定所属部门、附上历史解法 | 分类准确性；误定级会导致派错人 |
| B3 | **报销单据整理**：发票识别 → 科目匹配 → 预算科目对齐 → 生成报销单草稿 | 财务规则复杂；**必须留人工复核**（对标延锋） |
| B4 | **采购 / 供应商需求单草拟**：输入规格、成本、交期 → 生成需求单 → 可附风险提示 | 数据来源跨系统 |
| B5 | **会议纪要 → 待办拆分**：纪要里的 action item 抽成工单草稿，带上责任人和时间 | 责任人与时间的歧义 |
| B6 | **汇报材料起草**：周报、月报、专项汇报（从待办/工单/数据里汇总） | **最容易做成「AI 写废话」**，要设质量门 |
| B7 | **公文 / 合同初稿 + 合规预检** | 国企公文格式要求严；合同条款风险识别 |
| B8 | **格式规范化 / 润色 / 翻译** | 低风险、见效快，适合当第一个「甜点」场景 |

### C 类 · 真写入 + 推进（高风险，**必须有闸**）

| 编号 | 需求点 | 风险等级 | 该有什么闸 |
|---|---|---|---|
| C1 | **真正提交工单 / 发起流程** | 中 | **单次人工确认**（用户点确认才提交） |
| C2 | **催办 / 转办 / 改派审批人** | 中高（影响他人） | 确认 + 留痕 + 谁授权的 |
| C3 | **流程加签 / 退回 / 撤销** | 高 | 确认 + 审批链记录 |
| C4 | **知识库 / 制度库更新** | **高（影响全员）** | **管理员审批**，不能由 Agent 直写 |
| C5 | **权限与账号申请执行** | **最高** | 用户只能**发起请求**，**实际管理员审批**，且**参数变了旧审批作废** |
| C6 | **批量通知 / 批量操作** | 高 | 幂等 + 单飞锁 + 影响范围预估 |
| C7 | **归档 / 销毁** | 最高（不可逆） | 双人确认 + 延迟执行 |

> **C5 是你简历上那套快照审批最精准的用武之地。** 而且它天然需要：发起人身份、工具 id、参数哈希、审批记录、执行前二次校验——**五个要素你全有。**

### D 类 · 跨系统联动（**纳管命题的核心**）

| 编号 | 需求点 |
|---|---|
| D1 | OA ↔ **ERP**：工单关联采购单、应付单；生产订单变更（福田已在做） |
| D2 | OA ↔ **财务**：发票验真、对账、预算占用与释放 |
| D3 | OA ↔ **HR**：入转调离联动、编制校验、考勤汇算 |
| D4 | OA ↔ **MES / 生产**：生产异常单、设备报修（北汽福田场景） |
| D5 | OA ↔ **合同 / 法务**：用印、归档、到期提醒 |
| D6 | OA ↔ **网盘 / 文档中心 / 邮件**：知识来源与归档去向 |
| D7 | **老系统无 API** → 需要 RPA / 浏览器自动化兜底 | ← **这是最脏的活，但也是最能体现工程能力的地方** |

> D 类是「能力注册表 + 可见集裁剪 + Policy 闸」真正的用武之地。**每多接一个系统，就多一份凭证、多一组权限、多一片审计盲区。** 手工拼接在 3 个系统时还行，到 10 个必然失控。

### E 类 · 主动式服务（央企国企的「管理提升」叙事，容易出彩）

| 编号 | 需求点 | 注意 |
|---|---|---|
| E1 | **流程超时预警 + 主动催办**：「这个单子在你那压了 5 天了」 | 主动性 = 越权风险，必须限定在**用户自己的授权范围**内 |
| E2 | **合同 / 证照 / 资质到期预警** | 数据准确性要求高，误报比不报更糟 |
| E3 | **制度更新后的受影响人群告知** | 需要「制度 ↔ 适用人群」的关系模型（**这就是对象建模的落点**） |
| E4 | **待办聚合与日程编排**：「你明天有三件事冲突」 | 跨系统读 |
| E5 | **风险提示**：单据异常、合规风险、供应商风险（对标延锋「标注风险厂商」） | 提示不等于决策，不要越界 |
| E6 | **新员工入职引导**：首周任务流、常用制度、对接人 | 低频但体验好，适合当样板 |

### F 类 · 平台与治理（**这是「做一个多 Agent 平台」的正题**）

| 编号 | 需求点 | 说明 |
|---|---|---|
| F1 | **能力注册与纳管** | 谁的 Agent、能调哪些能力、风险等级、启用状态——**统一登记，不许各接各的** |
| F2 | **可见集裁剪** | 按部门 / 角色 / 密级 / 项目裁剪。**不是回答时过滤，是给到模型之前就裁剪** |
| F3 | **策略闸** | 写操作默认拒；高危能力需显式放行 |
| F4 | **单次人工确认** | 冻快照 → 管理员审批 → 执行前二次校验 → 参数变则作废 |
| F5 | **身份与代表关系** | 「谁发起、Agent 代表谁、能访问什么、权限持续多久」——**行业公认的四个问题** |
| F6 | **审计可重建** | 能回答「以谁的名义、依据什么、做了什么、产生了什么副作用」 |
| F7 | **评测口径** | 不是「答得像不像」，是「**单填错没填错**」——工单类场景要用任务完成度评 |
| F8 | **模型可插拔** | 豆包 / 星辰 / DeepSeek 都在接，出口不能绑在模型上 |
| F9 | **长流程多轮状态** | **工单是长流程，不是一次问答**——审批到哪一步、等谁、能否撤回，都要能续 |
| F10 | **知识库运营** | 高频问题回流，反哺知识库结构和制度本身 |

## 五、分期建议（面试可以直接讲这个）

**核心原则来自行业原话：查询先放开，写入与审批留住人。**

| 期 | 做什么 | 为什么这么排 |
|---|---|---|
| **第一期（1–2 月）** | A1 / A2 / A4 / A5 + B1 / B2 —— **只读 + 草稿，一律不真写** | 见效快、风险低、能立刻拿到使用数据；同时**用真实流量把可见集和审计跑起来** |
| **第二期** | **C1 单点突破**：选一个高频低危流程（请假 / IT 报障），带**单次人工确认** | 验证写操作闸；一个流程跑通再复制 |
| **第三期** | D 跨系统：从 ERP / HR 各接一个真实链路 | 这时纳管层的价值才显性化 |
| **第四期** | E 主动式 + C4 / C5 高危 | 需要前面积累的授权模型和审计底子 |

### ⚠️ 一个必须主动讲的判断

**F（平台治理）不能放到最后做。** 如果第一期不做可见集和审计，第二期一加写操作就得推倒重来——因为**「谁有权调什么」这件事必须在能力第一次被注册时就定义好，事后补是补不上的**。

> 这句话是你整个方案里最有分量的一句。它同时说明了**为什么需要你**（多数团队会先做场景后补治理，然后返工），也说明了**你的经验从哪来**（你就是返工过一次的人）。

## 六、治理维度：行业数据（**你的差异化**）

### 6.1 行业现状（可引用的硬数据）

| 事实 | 数据 | 来源 |
|---|---|---|
| 已授予权限在 90 天内被使用的比例 | **只有 4%**（即 96% 从未使用） | CSA Labs |
| 用户正常行使自己权限的比例 | **17%** | CSA Labs |
| 怀疑自家 AI Agent 已访问超范围数据的企业 | **三分之二** | Akeyless 2026 |
| 承认 AI Agent 已超出预期范围行动的组织 | **80%** | SailPoint |
| 能追踪和审计 Agent 访问数据的组织 | **只有 52%** | SailPoint |
| 被攻陷 Agent 的平均检测时间 | **14 小时** | Akeyless 2026 |
| 企业内部 AI 应用对 IT 可见的比例 | **只有 11%** | UpGuard |

> **「96% 已授予权限从未被使用」这一条，是「可见集裁剪」最有力的论据。** 你要论证的不是「权限应该收紧」这种正确的废话，而是「**给出去的权限里 96% 是纯风险敞口**」。

### 6.2 行业给出的四层架构（**和你的做法完全一致**）

企业级 AI Agent 权限管控的目标架构是 **四层分离：身份层 / 策略层 / 执行层 / 审计层**。

而治理逻辑上，**最小权限原则要升级为「以任务为中心的动态最小授权」：默认拒绝、按需授予、即时生效、自动回收**。

对照你的实现：

| 行业要求 | 你的对应 |
|---|---|
| 默认拒绝、按需授予 | Policy 硬闸：高危默认拒，Host 显式放行 |
| 以任务为中心 | per-request HITL：**只对这一次调用放行**（快照绑定） |
| 即时生效、自动回收 | 快照有过期时间；参数变则作废 |
| 身份层 | 租户由**代码**放进 `ctx`，来源是登录会话，不是模型写的 `tenant_id` |
| 策略层 | 可见集裁剪 + Policy 闸（**名单由代码定，模型只选**） |
| 审计层 | `side_effect_receipts` + run_events 回放 |

### 6.3 一句最有力的行业原话

> **"Prompt-level restrictions are behavioral suggestions, not security controls."**
> （提示词层面的限制是行为建议，不是安全控制。）

**这就是你「模型改不了的闸」的权威英文表述。** 你在 Q6 被批过的「作用域下推靠自觉」，行业标准的说法是**「不要用提示词做安全控制」**——你现在有了行业背书的说法。

## 十、老 OA 接入 Agent 的架构选型（三个判断）

> 原始判断：① 先走「OA+AI」而不是「AI+OA」；② Agent 与老 OA 交互，**给 Agent 直接发 API 请求最快**；③ **旧 API 包装成 MCP 的前提是「API 不能满足 Agent 调用」**。
> **我的结论：① 同意，但要加一个关键限定；② 一半对；③ 判断反了。**

### 10.1 判断①「先 OA+AI」——同意，但有一个关键限定

**同意的五个理由**（按重要性排）：

1. **权限底座是现成的**。老 OA 有完整的组织架构、角色、密级、流程权限模型。AI 原生重做一套身份和权限，等于把最难的活重做一遍。**这是最大的理由。**
2. **流程引擎是现成的**。审批链、会签、条件路由、留痕、归档——AI 从外面接是补不上的。
3. **可回退**。AI 层挂了 OA 照常跑。国企场景里这一条权重极高。
4. **不改变用户习惯**。国企里改变工作习惯比技术难得多。
5. **存量数据不迁移。**

**但必须加的限定（这是陷阱）**：

> **交付形态可以是「OA + AI 层」，但治理形态必须是「一层能力层 + 多个场景」，不能变成「N 个 AI 插件」。**

因为如果每个场景各写一个插件（工单助手、制度问答、报销助手），它们的**能力清单、权限判断、审计口径各写一套**——那就退化成了福田现在的问题（用飞书/OpenClaw 一个个拼）。**致远互联自己就是这么说的：「不是给老 OA 外挂一个 AI 插件」。**

**另一个补充：入口应该是双的，不是二选一。**
- **OA 内嵌**（原有用户不动，零学习成本）
- **侧边对话**（愿意用新方式的直接对话即操作）

只做前者，AI 永远是个功能点；只做后者，用户习惯过不去。

### 10.2 判断②「Agent 直接发 API 请求最快」——一半对

**对的那一半**：**L1 接口可调用性**确实是成本最低的起步方式——一个 HTTP client + 令牌管理 + 网络可达，今天就能通。

**错的那一半**：**L2 能力语义描述层一分都省不掉。**

老 OA 的 API 长这样：`POST /api/flow/submit`，`flowId=1024`。**问题不是能不能调，是模型根本不知道 1024 是什么。** API 文档是给程序员看的（字段、类型、必填），不是给模型看的（**这个能力解决什么问题、什么时候该用、用户那句话怎么映射成参数、它有没有副作用**）。

所以哪怕 API 完全够用，你仍然必须补：**能力 id、面向模型的描述、args_schema、何时使用、风险等级、是否写操作**。

**省掉 L2 的代价是滞后的、但必然爆发的**：
- 没有能力清单 → 后面加可见集，要改所有调用点
- 没有 args_schema → 后面加参数校验，要改所有调用点
- 没有风险等级 → 后面加策略闸，要重新盘一遍每个接口

**这就是"事后补"，而且是补不上那种。**

### 10.3 判断③「API 不能满足才做 MCP」——**这个判断反了**

**MCP 解决的从来不是「能不能调」，而是「能不能被模型选中 + 被动态发现 + 不绑框架」。**

| MCP 的真实价值 | 说明 |
|---|---|
| **自描述** | 工具名、参数 schema、描述 → **模型能选中** |
| **可发现** | 一个 server 声明一组工具，客户端动态拿到清单 → **这就是可见集的天然载体** |
| **传输解耦** | stdio / HTTP，本地或远程 |

**所以 MCP 不是"稀缺品"，是"标准品"**——只要你要让能力被 Agent 使用，**这层描述就是必需的**，跟 API 够不够用没关系。

**真正"不够用时才做"的是更重的两件事**：

1. **业务级编排封装**——当 API 粒度 < 业务动作时。例：「创建请假单」在老 OA 里可能是：查请假类型字典 → 查剩余年假 → 查审批人 → 提交单据 → 触发流程。**API 是 CRUD 级的，业务动作是编排级的。** 让 Agent 直接调 CRUD，等于让模型去写业务逻辑——就是"业务不变式写在模型里"的老毛病。
2. **无 API 时的兜底**——老系统可能只有页面（RPA / 浏览器自动化），或只有 SOAP / 私有协议。

**那对老 OA，要不要现在上 MCP？我的判断：先不上，后置。**

- **目标是"快"** → 先做 L1 + L2，用**进程内的能力注册表**（就是现有的 Capability Host）。MCP 是 L2 的一种传输标准，**换了传输层，L2 的内容不用重写**，所以后置不亏。
- **MCP 什么时候值得上**：① 能力要被**多个不同的 Agent 宿主**消费（比如飞书里也要用、自研平台也要用）② 能力由**外部厂商**提供（ERP / 财务厂商自己出 MCP server）③ 要免部署地接第三方工具生态。
- **北汽的具体判断**：他们已经在用飞书（aily / 多维表格）。**如果将来希望同一批能力在飞书里也能用，MCP 就有价值；否则先做内部注册表更划算。**

### 10.4 老 OA 的五个技术坑（附你的对应资产）

| 坑 | 表现 | 你的对应 |
|---|---|---|
| **会话态 API** | 老 OA 大量依赖 session / cookie，不是无状态 token；cookie 会过期 | 令牌与凭证管理；**租户由代码放进 ctx，不取自模型** |
| **非幂等** | 提交类接口重复调用产生多张单据 | **幂等键 + 单飞锁** |
| **同步阻塞** | 有些接口同步跑完整条流程，超时 | **回执（side_effect_receipts）+ 状态查询** |
| **SOAP / 私有协议** | 甚至只有页面 | 适配层 / RPA 兜底 |
| **错误码不稳定** | 200 里嵌业务失败码 | **稳定错误码枚举**（unknown_id / disabled / policy_blocked / args_schema_invalid / duplicate_id） |

> **最后一条是你的强项**：不管底层 API 返回什么，**对模型看到的永远是同一套错误码**。这就把老系统的不稳定语义挡在了能力层外面——**而且这套枚举已经有跨语言一致性测试在守。**

### 10.5 最快落地路径（五步）

1. **盘接口**：把 OA 里高频、重复、有明确依据的接口拉一张表（从 A/B 类需求反推）
2. **补 L2 描述**：每个接口补能力 id + 面向模型的描述 + args_schema + 风险等级 + 是否写操作。**哪怕先写在 YAML 里，也要先有结构。**
3. **搭最小纳管层**：注册表 + 可见集裁剪（按部门/角色）+ 只读审计。**这一层第一期就要有。**
4. **上只读 + 草稿场景**：A1/A2/A4 + B1/B2，一律不真写
5. **再开写操作**：选一个高频低危流程（请假 / IT 报障），走**单次人工确认**

**第 3 步的顺序是全部的关键**：如果第 5 步之前没做第 3 步，写操作一开就要返工。

### 10.6 面试怎么讲这一段（口语版）

> 「我同意先走 OA+AI，因为权限底座和流程引擎都是现成的，AI 原生重做一遍是最贵的路。**但有个前提**——交付上可以是给 OA 加一层，治理上必须是**一层能力层托多个场景**，不能变成 N 个 AI 插件各管各的，否则半年后又得回来收拾。
>
> 接口对接上，直接调 API 起步最快，**但省掉的从来不是「能不能调」，是「模型能不能选中」**。老 OA 的接口是 `flowId=1024` 这种形态，模型不知道那是什么，**所以能力描述这一层一分都省不掉**——省了就等着返工。
>
> 至于 MCP，我的判断是**它不是「API 不够用时才做」**，它解决的是能力的描述、发现和传输解耦，是标准品不是稀缺品。**但对你们现在这个阶段，我更建议先做内部的能力注册表，MCP 后置**——因为换了传输层，能力描述不用重写。**除非你们希望同一批能力在飞书里也能直接用，那就值得早上。**」
