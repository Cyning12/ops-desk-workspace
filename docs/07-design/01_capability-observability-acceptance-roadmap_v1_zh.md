# Capability 层 · 可观测与模块化验收路线

> **状态**：待走查（v1 草案）
> **范围**：`ops-desk-api/app/ops/capability/` 及其对外的管理面
> **由来**：H4/W2/W3/W5/W6 把机制建起来了，但**它们对人不可见、也没法自己验**。
> 本文回答的是「**如何让人来观测并验收**」，而不是再加机制。
> **关联**：`00_capability-registry-design_v1_zh.md`（设计与实施记录）

---

## 1. 起点：现状盘点（有什么 / 缺什么）

### 1.1 观测

| 层次 | 回答什么问题 | 现状 |
|---|---|---|
| 调用级（trace） | 这一次调用发生了什么？ | ✅ span 里有 `capability_id`/`side_effect`/`receipt_id`/`policy`/错误码<br>⚠️ **没开 tracing 就什么都没有**；且只有翻 trace 才看得到 |
| 聚合级（指标） | 整体健康吗？谁在出错？拦截率？ | ❌ 完全没有 |
| 审计级（记录） | 上周三那笔写到底成没成？ | ⚠️ 两张表（`ops_capability_receipts` / `_idempotency`）已落库，**但没有查询入口** |

### 1.2 验收

| 方式 | 谁做 | 现状 |
|---|---|---|
| 自动验收 | CI / 任何人 | ✅ 820 单测 + 26 项真桩服务联调<br>❌ **没有一个命令能跑完**（要手工起桩服务、设 6 个环境变量、敲 JDK 路径） |
| 人工验收（可看） | 点一下就看见 | ❌ 零入口 |
| 剧本验收 | 不熟的人照着走 | ❌ 没有剧本 |

### 1.3 已有的验收范式（**要复用的，不要另起一套**）

仓里**已经**有模块化验收设计，形态正是「不关心内部实现、但有一套题集」：

| 已有 | 位置 | 关键性质 |
|---|---|---|
| 按模块的黑盒题集 | `evals/agent/golden/<module>/cases_v1.yaml` | 每个 case = `setup`（注入输入）+ `expect`（**与节点出口字段同名**）→ **验收者不需要读模块内部** |
| 确定性判分器 | `tests/eval/eval_agent_graders.py` | 集合/枚举相等 → 1/0；指标名对齐 `acc.*` |
| 禁 silent skip | `graders.require_expect()` | fixture 缺 `expect` **直接 fail** —— 题集自己不能悄悄失效 |
| 评测卫生 | `evals/golden/hygiene_denylist.yaml` | 剔除含金样原文的污染源（**这是防虚高，不是行为红线**） |
| 已覆盖模块 | `router` · `strategy_builder` · `supervisor` · `e2e` | **4 个，capability 不在其中** |

### 1.4 三个明确缺口

| # | 缺口 | 后果 |
|---|---|---|
| **G1** | **capability 层没有题集** | 我加的东西全靠**贴着实现写的单测**——换实现就得改测试，**这不是验收** |
| **G2** | **没有"红线"层** | 现有只有准确率型得分（掉分）。「无放行时写能力必须被拒」这类**踩到即否决**的断言无处安放 |
| **G3** | **没有产出基线 diff** | 「产出不能大范围变化」若只靠 `expect` 精确相等，**expect 写得不全就看不出来** |

> **G2 是最要紧的**：红线不是"分数"，是"**否决项**"。
> 把红线混进准确率里，等于允许"用别处的高分补一处红线"——那就不叫红线了。

## 2. 目标与不做什么

**目标**：一个**不读 capability 内部实现**的人，能在 10 分钟内回答三个问题——
1. 现在这套东西**是不是活的**（持久化配了吗？有没有卡住的写？）
2. 我这次改动**有没有踩红线**？
3. 我这次改动**产出漂移了多少**、漂在哪？

**明确不做**：
- 不引入 Prometheus / Grafana 依赖（指标先做最小可用 JSON，要接再说）
- 不在 capability 包内挂 `APIRouter`（包内禁止 router 是既有纪律，有测试守）
- 不为"能看"而放宽鉴权（观测端点同样要管理员身份）

---

## 3. 路线（六步，每步给验收标准）

### 步 ①：观测端点 —— 让"能看"

**做什么**：新增 `app/ops/admin/capability.py`（**包外**，复用 `AdminSyncAuth` 鉴权，照 `admin/sync` 先例），挂到 `app/ops/router.py`。

| 端点 | 给出什么 | 数据源（都已存在） |
|---|---|---|
| `GET /runtime` | **持久化模式**、租约配置、能力总数/启用数、清单版本 | `get_idempotency_store()` / `get_receipt_sink()` / `get_capability_manifest_metadata()` |
| `GET /catalog` | 可见集 + **被裁掉的是谁、为什么** | `capability_catalog_snapshot()` |
| `GET /receipts?capability_id=&tenant_id=&limit=` | 最近回执（含 `captured` / `write_confirmed`） | `ops_capability_receipts` |
| `GET /idempotency?stuck=true` | 防重行；**筛出卡住的 `in_flight`** | `DbIdempotencyStore.asnapshot()` |

**★ `GET /runtime` 是这一步的核心**。因为「`OPS_CAPABILITY_PERSISTENCE` 没配 = **没有防重**」是目前**唯一会静默失效**的地方——它不报错、不改行为，只是悄悄不生效。
**人必须能一眼看出来，而不是去翻环境变量。**

**顺带**：`GET /idempotency?stuck=true` 就是原路线里"第 ② 步租约巡检"的落点——**一石二鸟，不用再单独造入口**。巡检**只发现、不自动重试**（要不要重试取决于下游到底有没有生效，那是人或专门的查询能力才能判断的）。

**验收标准（这一步怎么算完成）**：
- 未登录/非管理员访问 → 401/403（有测试）
- `OPS_CAPABILITY_PERSISTENCE` 分别设 `db`/`memory`/不设时，`/runtime` 返回对应模式，且**不设时能明显看出"未启用"**（比如 `idempotency.enabled: false` + 一行 reason）
- `/catalog` 能复现「匿名 principal 看不到 `visibility` 受限能力」，并给出 `reason`
- `/idempotency?stuck=true` 能列出人为造出的过期 `in_flight` 行

### 步 ②：红线断言 —— "踩到即否决"

**做什么**：新增 `tests/eval/test_capability_redlines.py` + `evals/agent/redlines/capability_v1.yaml`。

红线是**独立的判据**，与准确率分开统计，**任一条踩到即整体否决**（不是扣分）：

| 红线 | 断言 | 为什么是红线 |
|---|---|---|
| R1 | 无 `allow_write` 时，**任何** `side_effect ∈ {write, irreversible}` 调用必须 `ok=False` + `policy_blocked`，**且下游零请求** | 写操作失控是最高代价 |
| R2 | 任何出站请求**不得**包含未在 `args_schema` 声明的模板变量 | 静默渲染成空串 = 把语义交给下游猜 |
| R3 | 任何错误**不得**包含下游原文（只允许稳定错误码 + 我们自己的详情） | 错误原文外泄 = 数据边界失守 + 模型无法决策 |
| R4 | 含非 ASCII 参数的写调用**必须**成功（幂等键须 ASCII 化） | 这条曾经让**所有中文写操作全发不出去** |
| R5 | 写操作超时后**不得**重发（对端 `attempts == 1`） | 超时≠失败，重发会建第二张单 |
| R6 | 出站请求**不得**经环境代理（除非显式配 `OPS_CAPABILITY_HTTP_PROXY`） | 内网调用被劫持成看不懂的 502 |
| R7 | 命中幂等键的那次调用**不得**再发请求、**不得**留第二条回执 | 防重的全部意义 |

**验收标准**：
- 每条红线配一条**会触发它的反例**，反例必须**真的 fail**（否则红线是死代码——我们在 V7 上踩过这个坑）
- 红线文件与判分器分离：`.yaml` 只声明断言，逻辑在 runner

> **为什么红线要单独一层**：混进准确率就允许"用别处的高分补一处红线"。红线必须是**否决项**。

---

### 步 ③：capability 验收题集 —— 让"不关心内部"

**做什么**：新增 `evals/agent/golden/capability/cases_v1.yaml`，**复用现有范式**（`setup` + `expect`，出口字段同名，集合/枚举相等）。

覆盖（全部黑盒，只看 `invoke` 的**出口**）：

| case 组 | `expect` 看什么 |
|---|---|
| 可见集裁剪 | `visible_ids` / `hidden[{id, reason}]` |
| 加载期校验 | V1–V9 各自一组：给定 manifest 片段 → 期望 `ManifestError` 的**匹配串** |
| 错误归一 | `error_code`（只比稳定码，不比详情文案） |
| 幂等/防重 | `duplicated` / `downstream_calls`（对端被调用次数） |
| 写闸 | `ok` / `error_code` / `downstream_calls` |

**关键约束**：`expect` **只允许引用出口字段**（`CapabilityResult.meta` / `status` / `error_code`），
**不允许断言内部函数、内部字段名、日志文案**。这条是"不关心内部怎么改"的落地保证。

**验收标准**：
- 题集里**至少有一条 case 在改动实现时仍应通过**（把 `http_generic` 的内部实现重写一遍，case 不动、全绿）——**这是对"黑盒"本身的验证**
- 沿用 `require_expect()`，缺 `expect` 即 fail

---

### 步 ④：一键验收脚本 —— 让"一条命令验"

**做什么**：`ops-desk-api/scripts/acceptance/capability_acceptance.sh`

```
起桩服务(mock-oa) → 等待真实监听(lsof，不用 curl) → 跑单测 → 跑题集
  → 跑红线 → 跑 26 项联调冒烟 → 跑 DB 持久化测试 → 出汇总报告 → 退出码
```

**报告要带证据**，不是"全部通过"四个字：每条失败附原始输出片段；红线单独一节；题集通过率单独一节。

**验收标准**：
- 一条命令跑完，**退出码可直接接 CI**（0 / 非 0）
- 报告能贴进 PR（Markdown）
- 桩服务起不来时**明确说"桩服务未就绪"**而不是把联调记成失败（区分"环境没准备好"与"代码有问题"）

---

### 步 ⑤：产出基线 diff —— "不能大范围变化"

**做什么**：把一次全量 case 的**全部出口产出**序列化成 `evals/agent/golden/capability/baseline_v1.json`，
runner 支持 `--against-baseline`，给出逐 case diff（新增/消失/字段变化）。

**为什么需要**（`expect` 精确相等不够）：`expect` 只覆盖**你想到的字段**；
基线 diff 覆盖**你没写进 `expect` 的那些字段**——漂移往往就发生在那里。

**验收标准**：
- 故意改一处实现（如把某个 `reason` 文案改了）→ diff 能指出**具体哪条 case 的哪个字段变了**
- 基线更新必须是**显式动作**（`--update-baseline`），不允许"跑一遍自动覆盖"——那等于没有基线

---

### 步 ⑥：验收剧本 + 指标

**做出两个**：
1. **验收剧本**（文档）：给不熟的人一份照着走的清单——每条 `curl` + **期望输出** + **为什么这条重要**。
2. **最小指标**：`GET /admin/capability/metrics` 返回 JSON（按 `capability_id × 错误码` 的调用数 / 拦截数 / 延迟分位），进程内计数器，不引依赖。

**验收标准**：
- 剧本：**没参与过这个项目的人**照着走能走完，且能被明确告知"哪一步不符合预期意味着什么"
- 指标：能回答"过去这段时间，**被 Policy 拦下的写有多少次**"（这是最该被盯的数字）

## 4. 顺序理由

```
① 观测端点   ← 先让"能看"；顺带落掉租约巡检
② 红线       ← 最便宜、价值最高；且独立于题集，先立规则
③ 题集       ← 复用现有范式，把"不关心内部"变成事实
④ 一键脚本   ← 把 ①②③ + 既有单测/联调串成一条命令
⑤ 基线 diff  ← 补上 expect 覆盖不到的漂移
⑥ 剧本+指标  ← 最后，锦上添花
```

**① 在 ② 之前**，因为红线要跑就得先能起服务、能观测；
**② 在 ③ 之前**，因为红线是"规则"、题集是"样例"，**规则先立，样例才有所依**；
**④ 在 ③ 之后**，因为脚本要有东西可跑。

## 6. 一句话回答"如何让人观测并验收"

> **红线管"不能碰"，题集管"不能变"，基线 diff 管"变在哪"，观测端点管"现在活着吗"，一键脚本管"谁来跑"。**
> 五件事分开做，因为它们回答的是**五个不同的问题**——把它们混成一个"测试通过率"，就等于什么都没保证。
