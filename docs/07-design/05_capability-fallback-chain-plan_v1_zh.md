# 降级链落地方案（P1 · 八问 Q3 下半）v1

> 结论先行：**是的，降级链与业务强相关——而且这正是它和熔断的本质区别。**

---

## 0. 熔断 vs 降级：一个横切、一个纵向

| | 熔断 | 降级链 |
|---|---|---|
| 回答的问题 | 这个下游**还打得通吗** | 打不通时**给什么** |
| 需要业务知识吗 | **不需要**：只判通不通，任何能力一样 | **必须**：每个能力"退到哪一步"不同 |
| 能不能框架替业务决定 | 能（阈值/时长是运维参数） | **不能**——框架猜出来的降级结果是静默错误 |
| 失败形态 | 明确失败（`circuit_open`） | **成功但降级**（`ok=True` + `degraded=True`） |

一句话：**熔断是横切机制，降级是业务决策**。

所以切分方式必须是：

- **通用的**：什么时候降级、降级了要怎么标记、链条能有多深、怎么观测
  —— 这些框架做，任何能力都一样。
- **业务的**：**降级成什么** —— 必须由**能力清单声明**（走 Git + PR + 人闸），
  框架只负责忠实执行声明，绝不自己发明一个降级结果。

> 反例（不要这么做）：框架在工具失败时"自动换一个相似工具"或"返回上一次的结果"。
> 前者是猜，后者可能把三小时前的数据当成实时数据回答——
> **静默降级比明确报错危险得多**，因为它不会有人来查。

## 1. 声明形态（`fallback:` 进 manifest）

```yaml
- id: oa.doc.search
  fallback:
    triggers: [transport, 5xx, "429", circuit_open]  # 触发条件（框架判定）
    action: capability                                # 业务声明：退到哪
    capability_id: oa.doc.recent
    args_map: {keyword: q}          # 目标参数名 ← 源参数名（只做键改名，不做模板）
    max_depth: 2                    # 链条上限（防成环，默认 2）
```

> **字段名是 `triggers` 不是 `on`（实测踩到）**：YAML 1.1 会把裸键 `on`
> 解析成布尔 `True`（`on/off/yes/no` 都是），于是 `on: [...]` 被读成
> `{True: [...]}`，声明**静默失效**——报错还会指向一个看起来不存在的字段。
> 同理 `429` 要加引号，否则是整数（代码里做了 `str()` 兜底，但清单里写清楚更好）。

| action | 含义 | 适用场景 | 谁定 |
|---|---|---|---|
| `none`（**默认**） | 不降级，明确失败 | 大多数能力 | 框架默认 |
| `capability` | 换成另一个能力（可带 `args_map`） | 有更粗/更稳的替代接口 | **业务** |
| `cache` | 返回上次成功结果（带 `ttl_seconds`，默认 300s） | 结果变化慢、陈旧可接受 | **业务** |
| `static` | 返回声明好的静态兜底值 | "服务暂不可用"这类文案 | **业务** |

**默认必须是 `none`。** 让"不降级"成为需要显式改掉的默认，
而不是需要显式守住的底线——后者一定会漏。

**`args_map` 刻意只做键改名、不支持模板**：模板会把"降级"变成一门小语言，
而降级的参数语义必须由业务在清单里想清楚。改不动时原样传，
目标能力有自己的 `args_schema`，不兼容会被它自己拒绝（失败可见）。

## 2. 三条硬边界（违反任一条，降级就从兜底变成事故）

### B1 · 写能力**禁止**降级

单据没建就是没建，不存在"降级成建了一半"。

- 写能力失败 = 明确失败 + 告知人工，**没有任何降级动作**。
- 唯一例外是人工审批链（那是另一回事，见 04 号文档 §9）。

理由（对应模式库"出错代价高 → 强制人工确认"）：写操作的失败必须**看得见**。
一旦允许降级，就会出现"用户以为提交了、实际没提交"的最坏结果。

### B2 · 降级结果必须**显式标记**

```json
{"ok": true, "meta": {"degraded": true, "degraded_from": "oa.doc.search",
                      "degraded_action": "cache", "degraded_trigger": "transport",
                      "degrade_depth": 1, "degraded_at": "2026-09-20T12:00:00Z",
                      "stale_at": "2026-09-20T11:00:00Z",
                      "degraded_reason": "upstream_error: 传输失败: TimeoutError",
                      "result_contract_skipped": true}}
```

不标记的话，模型和编排层分不清「真实结果」和「降级结果」——
拿三小时前的缓存当实时数据回答，是**静默错误**，没人会来查。

- **`degraded_reason` 必须留着**：降级是"给了个替代答案"，不是"问题消失了"。
  把它丢掉，排障时就只剩一个看起来正常的成功。
- **`result_contract_skipped: true`**：降级结果**跳过** `output_schema` 校验
  （契约描述的是"真实结果长什么样"，降级结果本来就不是真实结果），
  但跳过必须**显式可见**，不能悄悄跳。
- 标记要一路带到：span metadata、`/runtime`、metrics、以及给模型的输出里。
- **降级不落回执**：这次调用没有真的执行副作用，留回执等于声称做了没做的事。

### B3 · 链条**有界**（对应 C5 有界自主）

`A → B → C → A` 会成环，`A → B → C → …` 会拖长延迟。

- `max_depth` 默认 **2**（最多退两级）
- 执行时带 `visited` 集合，重复出现立即停止
- 降级链上的每一次调用**独立计时**，总时长受能力自身 `timeout_ms` 约束

## 3. 触发条件（什么时候才降级）

不是所有失败都该降级。只有**下游不可用**才降级；**参数错/没权限**降级没有意义
（换个接口，参数还是错的）。

触发条件词表只有四个（**框架不接受业务发明新的"不可用"**）：
`transport`（超时/连接失败/不响应）、`5xx`、`429`、`circuit_open`。
判据全部取**结构化字段**（异常上的 `cause` / `http_status`），
与熔断同一套分类（见 `errors.is_environmental_failure`），**不解析错误文案**。

| 失败 | 降级吗 | 理由 |
|---|---|---|
| 超时 / 连接失败（`transport`） | ✅ | 下游不可用 |
| `5xx` / `429` | ✅ | 下游不可用 / 过载 |
| **熔断 open**（`circuit_open`） | ✅ | 下游已知不可用，正是降级的时机 |
| 业务码失败（4xx 语义） | ❌ | 请求本身有问题，换接口也一样 |
| `args_schema_invalid` | ❌ | 参数错，降级无意义 |
| `permission_denied` | ❌ | 换了也没权限 |
| 结果契约不符 | ❌ | 下游活着，是结构问题 |
| 本地装配问题（缺 base_url / 凭证） | ❌ | 是我们自己没配好，不是下游坏了 |
| **任何写能力失败** | ❌ | B1 |

`cause` / `http_status` 缺失时**一律不降级**——宁可少降，不可误降。

## 4. 在调用链上的位置

```
Policy → 熔断 check → 配额 → 执行
                          └─ 失败 → 【降级判定】→ 有声明且允许 → 执行降级动作 → 标记 → 返回
                                              └─ 否则 → 明确失败
```

降级是**执行失败之后**的动作，不是执行前的分支——先试真的，真失败了才退。

与熔断的关系：熔断 open 时**不再尝试原能力**，直接走降级（如果有声明）。
这样熔断期间用户拿到的是降级结果而不是 `circuit_open` 错误——
但**必须带着 `degraded` 标记**，否则等于用降级掩盖了故障。

## 5. 观测

`/runtime` 与 metrics 增加：

| 指标 | 为什么必须看 |
|---|---|
| `degraded_calls` | 降级发生的频率；**突然涨 = 下游在悄悄坏** |
| `degraded_by_action` | 是退到别的接口、还是用了缓存 |
| `degrade_depth_hist` | 是否经常退到第二级（说明第一级长期不可用） |

**降级率要和熔断率一起看**：熔断 open 但降级率 0 = 用户正在硬吃错误。

## 7. 落地时实测到的三个坑（新增）

1. **熔断层和降级层会互相掩盖观测口径（本次真踩到）**
   `oa.doc.search` 声明降级后，熔断闸门原本的断言
   "被熔断挡住的调用必须失败并报 `circuit_open`"**永远不成立**——
   降级把它变成了"成功"。这不是 bug，是设计（熔断管打得通吗、降级管给什么），
   但**分层验证时必须挑一个未声明降级的能力**（改用 `oa.org.whois`），
   否则两层各证各的、互相把对方的证据吃掉。
   反过来也有一条断言：降级接管了 `circuit_open`，但 **breaker 状态仍是 open**
   ——"用户拿到兜底答案"不等于"故障好了"，状态才是诚实的信号。

2. **缓存必须按 (能力, 租户, 参数) 分桶，不能只按能力 id**
   只按 id 缓存的话，`oa.todo.mine` 这类个人数据会让 A 用户的待办出现在
   B 用户的回答里——一次跨租户泄漏，而它长得完全像一次"成功的降级"。
   过期即不降级（`ttl_seconds`，默认 300s）：陈旧数据比明确报错更危险。

3. **降级结果会跳过 `output_schema` 契约校验**
   契约描述"真实结果长什么样"，静态兜底本来就不满足它——
   强制校验会让 `static` 这个动作永远不可用。跳过可以，但必须留
   `result_contract_skipped: true` 让人看得到。

## 8. 业务已定的三条声明（2026-09-20 业务输入）

| 能力 | 降级成什么 | 为什么是它 |
|---|---|---|
| `oa.doc.search` | 静态：服务暂不可用 + 空 items | 没有更粗的替代接口；缓存会把昨天的检索结果当今天的答案 |
| `oa.org.whois` | 静态：**按最小权限假设 = 普通员工** | 见下方 ⚠️ |
| `oa.todo.mine` | 静态：功能不可用 + 空 items | 个人数据**没有可退的安全缺省值** |

### ⚠️ `oa.org.whois` 这条必须按"最小权限"理解，不是"查到他是普通员工"

- **不是**伪造一条人员记录说他是普通员工（那样是在编造事实）。
- **是**：查不到组织关系 ⇒ 未确认任何管理权限 ⇒ 按最低权限对待。
  `items` 保持**空**，假设值单独放在 `data.degraded_assumption`。
- 降级方向必须是**往安全一侧退**，不能往宽松一侧退。
- **任何权限判定都不得依赖降级结果**——这句话写进了给模型的提示、
  也写在清单的 `note` 里。真要做授权，必须拿到真实组织数据或走 HITL。

### `oa.todo.mine` 为什么不能"降级成空列表"

"查不到待办"和"确实没有待办"在系统里**长得一模一样**。
如果降级返回空列表，模型会回答"你当前没有待办"——这是把故障说成了事实。
所以文案必须明确写"**无法确认**你有没有待办"。

## 9. `action: cache` 到底缓存的是什么（TTL=300s 指什么）

它不是性能缓存，是**降级专用的"上次成功结果"**：

- **只有调用失败时才读**。正常调用永远走实时数据，缓存不参与成功路径。
- **只给声明了 `action: cache` 的能力记账**。没声明的能力不会在内存里
  躺着一份永远用不到的过期数据。
- 分桶键 = **(能力 id, 租户, 参数摘要)** —— 不能只按能力 id，否则
  `oa.todo.mine` 这类个人数据会让 A 的待办出现在 B 的回答里。
- `ttl_seconds`（默认 **300s**）= 这份结果**最多能用多久**。
  超过就当没缓存、直接明确失败——陈旧数据比报错更危险。
- 进程内存、512 条上界 FIFO、**重启即丢**（不是跨实例共享的缓存）。
- 降级结果**绝不入库**，否则陈旧数据会被当成新结果再降一次级。

## 10. 让模型感知"这是兜底结果"

**标记打在 meta 上等于没打**——模型只看工具输出，看不到 meta。
所以降级标记必须**跟着数据走**：

```json
{
  "code": 503, "data": {"items": []},
  "_degraded": {
    "capability": "oa.org.whois", "action": "static", "trigger": "transport",
    "at": "2026-09-20T08:37:49Z",
    "reason": "upstream_error: 网络错误: ConnectionRefusedError(61, 'Connection refused')",
    "notice": "【降级结果】oa.org.whois 调用失败（…）。以下为能力清单声明的**静态兜底值**，
               **不是查询结果**：不要把它当事实陈述，回答时应明确告诉用户该服务当前查不到。"
  }
}
```

- `notice` 按动作分别措辞（静态兜底 / N 秒前的缓存 / 来自替代能力），
  都要求模型**说清楚这不是真的**。
- 子任务结果上再打一层 `degraded: true`（`tool_exec_node`），
  让聚合器与前端也能筛出来。
- 输出不是 mapping（塞不进字段）时**不假装成功**：
  记 `metrics.degrade.unmarked`，这个数必须恒为 0。
