# 步骤契约 + 可恢复点落地方案（P1 · 八问 Q4 / Q8）v1

对应 `03_agent-tool-reliability-8q-gap-analysis_v1_zh.md` 优先级表 P1 第二行：
「步骤契约 `consumes/produces` + 可恢复点 | Q4 / Q8 | 与幂等天然咬合，投入产出比高」。

---

## 0. 先核准现状：读代码读出来的两个实证缺陷

方案不能建立在"文档说缺什么"上，要建立在"代码里真的发生了什么"上。
读 `app/ops/lg_rag/multi/nodes.py` 得到两条**可复现**的事实：

### 缺陷一：`depends_on` 只表达**顺序**，不表达**数据流**——当前是"伪串联"

工人节点拿的是计划里**写死的** `input`：

```python
# rag_subtask_node
result = _base_result(subtask)          # input 来自计划项，静态
... astream_router_agent(result["input"], ...)
```

`_worker_state()` 派给工人的载荷里只有 `assigned_subtask`（id/type/input/tool/args/depends_on），
**前驱的 output 从来没有进入后继的输入**。所以今天 `depends_on` 的真实语义是
"等它先跑完"，而不是"用它的结果"。

后果比"没串起来"更麻烦：planner 完全可以写出
`t2.input = "查一下 t1 查到的那个人的待办"`，而 `t1` 的结果根本没被注入——
模型以为串上了，其实没有。**这是"看起来有链式推理、实际是并行 + 空引用"。**

> 因此步骤契约如果只做"声明 + 校验"而不做**绑定**，就是一道空门：
> 声明了 `consumes` 却没人把数据喂进去，等于没串。

### 缺陷二：前驱失败，后继**照跑**（Q4 的字面病灶）

```python
# _join_subtasks
done = _terminal_index(..., plan_ids)     # ← 同时收录 output 与 error 终态
...
if all(dep in done for dep in deps):      # ← error 也算 "done"
    ready.append(sid)
```

`_terminal_index` 的收录条件是 `"output" in row or "error" in row`，
于是**失败终态被当成"前驱已完成"**，依赖它的后继照常下发。

这就是 Q4 原题——"中间某步错，后面步步错"——在本仓的**具体形态**：
不是数据污染，而是**前驱都失败了，后继还拿着计划里的占位输入继续跑**，
一路跑到 aggregator，最后综合出一份看起来完整的答案。

### 这两条决定了方案的形状

| 缺陷 | 补什么 | 属于 |
|---|---|---|
| 前驱失败后继照跑 | **前驱失败即终止**的编排层硬闸（不靠 critic / 模型判断） | Q4 |
| depends_on 不传数据 | `consumes` / `produces` 声明 + **喂入前校验 + 真绑定** | Q4 |
| （重规划无锁定） | 不可变前缀 + 可变后缀 + 可恢复点 | Q8 |

## 1. Q4 · 步骤契约

### 1.1 声明形态（`produces` / `consumes` 进计划项）

supervisor 产出的每个子任务可声明：

```json
{
  "id": "t1", "type": "tool", "tool": "oa.issue.get",
  "args": {"issue_id": "OPS-42"},
  "produces": ["status", "assignee"]
}
{
  "id": "t2", "type": "tool", "tool": "oa.todo.mine",
  "depends_on": ["t1"],
  "consumes": {"t1": ["assignee"]}
}
```

- `produces`：本步**承诺**产出的字段名（不是值）。
- `consumes`：`{<前驱别名>: [字段名...]}`，声明本步要吃前驱的哪些字段。
- 两者都**可选**。不声明 → 不校验（契约是显式声明出来的，系统不替你猜，
  与 R10「未声明契约的能力不得被推测性拦截」同一条纪律）。

**为什么不让契约自动从 `output_schema` 推导**：`output_schema` 是**能力**的契约
（这个工具保证返回什么），`consumes/produces` 是**这一次计划**的契约
（这一步我要用哪些字段、给下游哪些字段）。同一个 `oa.issue.get`，
在"查状态"的计划里 `produces=[status]`，在"查负责人"的计划里 `produces=[assignee]`。
前者兜不住后者——**能力契约全绿，计划仍可能是错的**。

### 1.2 三条硬边界

**C1 · 契约校验发生在"喂入前"，不是"执行后"**
在**派工人之前**判：前驱终态的 output 里有没有 `consumes` 声明的字段。
没有 → 该步直接写错误终态，**一次工具都不打**。
事后校验只能"发现错了"，喂入前校验才能"不让它错"。

**C2 · 前驱失败即终止，且这是编排层判断，不是模型判断**
`dep` 终态带 `error` → 依赖它的步一律写错误终态，理由写清楚
（"前驱 <id> 失败，本步未执行"）。
critic 是**模型侧**判断，可以让它继续做质量评估，但"跑不跑"这件事
不能交给模型——Q4 要的就是一道不依赖模型的闸。

**C3 · 绑定是确定性的，不是自由模板**
`consumes` 命中后，编排层按字段路径取值并注入：
- `type=tool` → 注入 `args[字段名]`；
- `type=rag|extract` → 在 `input` 尾部追加**由编排层生成**的固定格式上下文块
  （`【上游产出】t1.assignee = ...`），不把插值权交给模型。

模型写模板（如 `{{t1.assignee}}`）会引入字符串拼接类故障：
拼错、拼进 prompt 注入、拼出 SQL/JSON 片段。**取哪些字段由模型声明，
怎么拼由代码决定**——这条和 capability 的 `args_map`（只做键重命名，不做模板）
是同一条纪律。

### 1.3 失败分类

| 情形 | 处置 | 理由 |
|---|---|---|
| 前驱 `error` 终态 | 本步错误终态，**零调用** | C2 |
| 前驱 `output` 缺 `consumes` 字段 | 本步错误终态，**零调用** | C1 |
| 本步 `produces` 与实际 output 不符 | 本步置契约失败（错误终态），后继按 C2 停 | 声明了就要兑现 |
| 未声明 `consumes`/`produces` | 不校验，正常执行 | 契约不推测 |

最后一行是**反向对照**：如果"不声明也校验"，那"干脆一步都不跑"也能满足红线——
必须有一条证明系统**没有**过度拦截。

## 2. Q8 · 不可变前缀 + 可恢复点

### 2.1 锁定不是"校验它没改"，是"根本不让它写"

朴素做法是让 supervisor 输出全量计划，再比对前 N 项有没有被改动。
这有个硬伤：LLM 复述前缀时改一个字（把 `input` 换个说法）就算"改了"，
而比对松了又等于没锁。

正确做法：**重规划时，前缀不进入 LLM 的可写区域**。
supervisor 第二次及以后入口只收到两样东西：
- 只读的前缀摘要（"已完成、不可更改"）；
- "请只规划**剩余的**步骤"。

新计划 = **锁定的前缀快照**（从 state 取，不经模型）+ LLM 产出的后缀。
模型没有机会改前缀，也就不需要"事后验它没改"。

> 一句话版本：**锁定靠收回写权限，不靠校验写结果。**

### 2.2 前缀为什么"重跑是安全的"——与幂等的咬合点

写能力的幂等键由 `(tenant_id, 能力声明的 idempotency_key 模板 + args)` 派生
（`adapters/http_generic.py: _idempotency_key`），**不是**由 `subtask_id` 派生。

所以：锁定前缀 = 锁定 `(tool, args)` ⇒ 即使前缀被重放，派生的幂等键**与首次相同**
⇒ 命中已有回执 → **重放上次结果，不重复副作用**（R9）。

反过来说明为什么"改前缀"必须人工确认：**改 args = 换了一个幂等键 = 一次新的写**。
这正是 Q8 原题第 4 条要挡的东西。

### 2.3 可恢复点

| 概念 | 定义 |
|---|---|
| 不可变前缀 | **由 `plan_prefix_ids` 显式声明**（supervisor 重规划 / critic 回环时写入），含 `subtask_id`/`type`/`tool`/`args` |
| 可变后缀 | 尚未执行的步骤；重规划只能动这里 |
| 可恢复点 | `= len(前缀)`，即**下一个真正要执行的步骤下标**；恢复 = 沿用前缀结果 + 从该点继续，**不重跑前缀** |

> **前缀必须是声明出来的，不能从"有 output 的终态"反推。**
> 第一版就是反推的，结果：本轮刚跑完的前驱也被当成前缀 ⇒ 任何缺字段都判成
> `prefix_touch_required` ⇒ `contract_missing_field` 成了**走不到的死分支**，
> Q4（别把坏数据喂下去）和 Q8（改历史得交人）被混成同一件事。
> 死分支比没分支更危险——它让人以为两件事都管了。

新工具注入天然只能落后缀（因为模型只写后缀）。

### 2.4 参数调整影响已执行步骤 → HITL

识别信号：**后缀某步 `consumes` 了前缀某步当时没有 `produces` 的字段**。
含义是"要满足新计划，必须重跑并改动一个已执行步骤"——按 §2.2 这等于一次新的写。
处置：不做自动补跑，写 `hitl_required` 终态 + 上报，交人。

这是 Q4 与 Q8 的**交汇点**：同一个 `consumes` 校验，
在前驱**未执行**时是 Q4 的"别把坏数据喂下去"，
在前驱**已执行**时是 Q8 的"你要的东西得改历史才能拿到，得人来批"。

## 3. 观测

- span metadata：`step_contract_blocked`（次数）、`step_contract_bound`（绑定成功的字段数）、
  `plan_prefix_len` / `recoverable_point`、`replan_suffix_only`、`prefix_touch_required`（HITL 信号）。
- 结果行：被拦截的步骤带 `blocked_by: predecessor_failed | contract_missing_field | prefix_immutable`，
  与 capability 的七个稳定错误码同规格——**不新增错误码词表**，用 detail 区分。
- 判据：`step_contract_blocked` 恒为 0 时，与降级那次学到的教训一样，
  可能是"没人真的用多步依赖"，也可能是"闸没装上"，必须与总量合看。

## 5. 红线（草稿，落地时以 `evals/agent/redlines/capability_v1.yaml` 为准）

**R14 · 步骤契约**
前驱失败（`error` 终态）或前驱输出缺 `consumes` 声明字段时，后继步骤必须
**不执行且下游零请求**；未声明 `consumes`/`produces` 的步骤不得被拦截。

**R15 · 可恢复点**
重规划不得改写已执行前缀（`type`/`tool`/`args` 逐字段一致），前缀步骤不得被重新执行
（调用计数不增）；无前缀时（首次规划）一切照常。

两条都要有**正向断言 + 反向对照 + 变异检验**。只做正向会得到假通过：
"一律不派工人"天然满足 R14 的前半句。

## 6. 落地时实测到的坑（新增）

### 坑一：critic 回环整批清空结果 ⇒ 前缀根本无从锁定

`critic_node` 回环时写 `subtask_results = None`。于是"重规划"其实是**全量重来**：
已跑过的步骤被再打一遍，Q8 要的不可变前缀在代码里根本不存在。
改成裁剪到前缀（`SubtaskResultBatch([], prefix_ids, replace=True)`）之后，
`supervisor_node` 才第一次能算出前缀。

顺带说明为什么这条坑容易被漏：幂等保证了"重跑一次也不会重复副作用"，
所以这个 bug **不会造成数据错误**，只会白跑一遍——没有报警、没有红灯，
只有账单。

### 坑二：契约只校验不绑定 = 空门

第一版把 `consumes` 只用在闸门上。跑通之后回头看：声明写了、校验也过了，
但**没有任何代码把值注入后继**——`depends_on` 依旧只表达顺序。
闸门全绿，链子还是断的。所以 R14 把"命中后必须真的注入"写进了红线正文，
并用"绑定必须覆盖占位值"这条断言守着（`setdefault` 会让它变成假通过）。

### 坑三：锁定的实现方式是"收回写权限"，不是"写完再验"

让 supervisor 输出全量计划再比对前 N 项，会陷入两难：
比对严了（连 `input` 措辞都算），模型换个说法就被判"改了前缀"；
比对松了等于没锁。改成**模型只输出后缀、前缀以只读形态出现在提示里**
之后，模型没有改的机会，也就不需要事后校验。

### 坑四：提示词版本号必须跟着内容走

给 `lg_rag.supervisor.system` 加 `produces`/`consumes` 说明时顺手把
`version` 从 v1 顶到 v2，三处既有断言（"product 侧零影响"）随之失败。
这不是意外而是**信号**：版本号不跟内容走，版本号本身就是假信号。
同时把那条"集合恒等"断言改成"既有两枚仍在（超集）"——
真正的零影响是既有 key 与渲染行为不变，新增模板是加法。

## 7. 待定

- `type=rag/extract` 的上游上下文块格式（现为 `【上游产出】alias.field = value`），
  要不要带类型标注、要不要截断（长值污染 prompt）。
- 后缀为空时（模型认为不需要补步骤）是"直接 aggregate"还是"允许一次 critic 重问"。
- `prefix_touch_required` 的 HITL 落地形态：本仓已有 `hitl_required` 快照字段，
  但编排层当时**没有真实的审批通道**，第一版先做"停下来 + 上报"，不假装已批。
