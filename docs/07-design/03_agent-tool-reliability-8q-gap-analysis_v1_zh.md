> 幻觉失控 / 多工具漏选循环 / 动态变更重规划）。
> 本文不写"标准答案"，而是**把这八类失败逐条对着本仓代码过一遍**：

## 落地状态（2026-09-20 更新）

两项 P0 已落地，验收进了六层一键脚本（含真桩服务联调）：

| 项 | 对应缺口 | 实现 | 红线 | 验收层 |
|---|---|---|---|---|
| **P0-1 输出契约** `output_schema` | Q2 / Q4 —— 唯一"错了还报成功"的口子 | `app/ops/capability/result_contract.py`（校验）+ `manifest.py` V10（加载期形状）+ `gateway` 成功路径 | **R10** | 单测 / 题集（+3 用例）/ 红线 |
| **P0-2 会话配额 + kill switch** | Q6 —— 已有预算管步数，管不了"打了多少次写" | `app/ops/capability/budget.py` + `gateway` 准入 | **R11** | 红线 / **失控兜底（配置级）** |

两条约束在落地时被显式守住了：

- **错误码词表七个、不增**：契约不符落 `upstream_error`（detail `result_contract: …`）；
  kill switch 落 `disabled`；配额耗尽落 `policy_blocked`。用 detail 区分，不新造码。
- **契约是显式声明出来的**：`output_schema` 未声明 → **不校验、不拦截**。
  系统不替你猜契约，否则"能用"会变成"随机不可用"。

落地过程中**顺带挖出的三个更危险的既有问题**（都不是新功能，是修洞）：

1. **假门**：配额原按 `subtask_id` 分桶，而子任务是 `run_id:seq`、一个子任务基本只打一次
   工具 ⇒ 每个桶最多 1 次，配额**永远打不满**。改为按 `run_id`（`tool_exec_node` 已补传）。
2. **跨用例状态泄漏**：配额是进程内全局，不传 ctx 的调用全落匿名桶 `""`，跑满 64 次后
   后续全部被拦。conftest 加了 autouse reset，题集 runner 按 case reset。
3. **无界字典**：`_SESSIONS` 按 run_id 无限累积 = 内存泄漏。加了 512 上界 + FIFO 淘汰，
   并在 `/runtime` 的 `budget` 里把 `evicted_sessions` 报出来，不假装没发生。

## 0. 总纲：八问其实是四类错误，不能指望一种机制

| 类 | 八问里的哪几条 | 性质 | 正确打法 |
|---|---|---|---|
| **A. 选择错**（调了 A 该调 B、参数格式错、漏必填） | Q1 | **可确定性判定** | 形态校验 + 候选集裁剪，别让模型背 |
| **B. 结果错**（工具返回有错/缺失却被当正确） | Q2、Q4 | **只能事后对账** | 输出契约 + 对账凭据 + 观测 |
| **C. 环境错**（超时、限流、下游挂） | Q3 | 可判定但**要策略** | 超时/重试/熔断/降级/配额 |
| **D. 失控**（幻觉、循环、乱规划） | Q5、Q6、Q7、Q8 | 只能**收敛 + 兜住最贵的后果** | 预算 + 审批 + 幂等 + 可回滚 |

一句话：**能确定性判定的，绝不让模型判断；只能事后发现的，靠契约和对账；
只能收敛的，靠预算、审批、幂等把最贵的后果（重复写）锁死。**

## Q1 · 工具选错 / 参数格式错 / 漏必填 → 怎么兜底

### 现状（三道，且都在调用路径上）

1. **加载期**：`app/ops/capability/manifest.py` 的 V1–V9 —— 缺 `args_schema`、
   缺 `when_to_use`、密钥形字段、模板变量未声明 → **加载即拒**，坏工具进不了目录。
   （`when_to_use` 强制非空：`manifest.py:365`，因为它是模型选工具的唯一依据。）
2. **可见集裁剪**：`baseline.py:baseline_filter` —— `deny_write=True` +
   `deny_high_risk=True` + `kinds`/`allow_tags_any`。写能力和高危能力在**裁剪阶段**
   就不进模型视野：模型看不见的东西，就不会选错。
3. **运行期形态校验**：`gateway.py:274` → `schema_validate.validate_capability_args`
   —— 校验 `required` / `type` / `additionalProperties`，失败返回
   `args_schema_invalid: 缺必填字段: x`，**请求不出门**。

外加：真到了下游才报错时，`error_map` 把下游码归一成稳定码（`http_generic.py:849`），
且**不外泄下游原文**（红线 R3）——避免模型拿着一堆无法决策的字符串继续瞎试。

### 缺口

- **"选错工具"（A vs B）没有运行期判定**：目前只靠 `when_to_use` 文本喂给模型。
  模型选了另一个合法工具，系统层面**看不出这是错的**。
- 参数只验**形态**，不验**语义**：`subject` 传成了 `id` 这种只有下游能判。
- `when_not_to_use` 目前只是文本，**不参与任何判定**。
- 参数错了就失败，**没有一次纠错重试**（`args_schema_invalid` 的 detail 没回喂模型）。

### 补齐

| 项 | 做法 | 约束 |
|---|---|---|
| 参数纠错重试 | `args_schema_invalid` 的 detail 回喂模型重试 **1 次**；**读可重试、写不可**（与 R5 同源） | 重试次数写死在能力层，不交给模型 |
| 选择理由一致性 | 要求模型输出"为什么选它"，与 `when_to_use` 做关键词/向量一致性检查，不一致 → 降级为"请澄清" | 只降级不代选 |
| `when_not_to_use` 生效 | 命中反例描述时**从候选集剔除**（进裁剪，不是进提示词） | 与可见集同一判序 |

## Q2 · 工具返回有错 / 有缺失，却被当成正确结果继续规划

### 现状

- **成功判定不只看 HTTP 状态码**：`_is_success`（`http_generic.py:833`）读声明式
  `success_when` —— HTTP 200 但业务码失败会**判为失败**（联调 D4 验过）。
- `error_map` 归一 + 不外泄原文（R3）。
- **回执凭据**：`receipt_capture` 抓关键字段（ticketId/url）落库（`receipts.py:44`），
  回执带 `subtask_id` / `tenant_id` / `idempotency_key` → 有事后可对账。
- 观测端点 `/receipts`、`/metrics`。

### 缺口（**这一类目前最薄弱**）

- **没有输出契约**：工具返回缺字段、字段类型变了、列表为空，**都照样 `ok=True`**。
  "查到 0 条"和"被限流返回空"在系统里长得一模一样 —— 这正是 Q2 问的"整条链路全错"。
- 没有"结果可信度"信号回给规划层：空结果会被当成"确实没有"继续规划。
- 题集/基线判的是**规划侧出口**（router/strategy/supervisor），**不判工具结果**。

### 补齐（P0）

给 capability 增加输出契约，失败即 `upstream_result_invalid`（新稳定码）：

```yaml
output_schema:
  required: ["$.data.ticketId", "$.data.url"]
  min_items: "$.data.items >= 1"      # 可选：最小条数
  empty_is_suspicious: true           # 空结果不得当成"查无"，要升级为可疑
```

要点：**空结果必须是一个显式状态**（`EMPTY_SUSPICIOUS`），不能静默等于成功。
这条建议直接做成红线（候选 R10），因为它的失效模式和 Q2 描述的一模一样。

## Q3 · 超时 / 限流 / 接口挂了 → 直接失败，还是有降级和备选

### 现状

- **声明式超时**：`timeout_ms`，超时判失败**不挂起**（联调 C2 验过）。
- **重试策略显式分化**：`attempts = 2 if method == "GET" else 1`
  （`http_generic.py:798`）—— **写操作绝不自动重试**（红线 R5）。
- **错误码带可重试性**：`RETRYABLE_CODES = {upstream_error}`、`NO_RETRY_CODES`
  （`errors.py:38`）；幂等释放**只在"确无副作用"的错误码上**（fail-closed）。
- 写超时后保持 `in_flight` + 租约 → 不重发，等人工/查询确认；
  `/idempotency?stuck_only=true` 就是干这个的（**只发现、不自动重试**）。

### 缺口

- **没有降级 / 备选工具**（全仓 grep 无 fallback）：A 挂了不会自动换 B。
- **没有熔断器**：连续失败的下游会被反复打。
- **没有调用配额**（每人/每分钟）。

### 补齐（P1）

| 项 | 做法 | 约束 |
|---|---|---|
| 降级链 | 清单加 `fallbacks: [id]`；**只允许同 `side_effect`、同类契约**的能力 | 降级必须可观测（`/metrics` 记 degraded） |
| 熔断 | 每能力连续 N 次 `upstream_error` → 打开；半开探测恢复 | 写能力**永不**半开探测重试（R5） |
| 配额 | per-tenant / per-user 每分钟调用上限，超限给稳定码而非 500 | 超限不得静默降级为"成功" |

## Q4 · 多步串联，中间某步错 → 后面步步错，怎么提前拦截

### 现状

- 每步都有**可追溯凭据**：回执带 `subtask_id` + `idempotency_key`。
- **幂等 + 重放**（R9）：重跑同一步拿到同样结果 → **重跑是安全的**。
- 规划侧有 critic（`app/ops/strategy/critic.py`）和预算收束。
- 红线/题集锁出口面不变。

### 缺口

- **步骤之间没有契约**：上一步输出的字段**没校验**就喂给下一步（Q2 的延伸）。
- 没有"**前驱失败即终止**"的显式闸门（现在靠 critic 判断，属模型侧）。
- 没有明确的"可恢复点"（从哪一步重跑）—— 幂等已具备，但编排层没声明。

### 补齐（P1）

`step_contract`：每步声明 `consumes` / `produces`，编排层在**喂入前**校验；
不合格即停，并给出可恢复点（因为幂等已就位，从该步重跑不会重复副作用）。

## Q5 · 有没有不靠大模型自己判断的方案

**这是本仓最强的一块**，面试里应该重点讲——因为它是"机制"而不是"提示词"。

| 机制 | 落点 | 挡住什么 |
|---|---|---|
| 白名单 + Git/PR + 人闸 | 能力清单走 PR；`risk_level` 降级等价拆闸，**不能靠改库生效** | 随意新增/放宽能力 |
| 禁止热加载 | 变更必须重启或显式 reload；包内禁 `APIRouter`（有测试守） | 运行时悄悄换工具集 |
| 可见集裁剪 | `baseline_filter`：deny_write / deny_high_risk / kinds / allow_tags_any | 模型**看不到**就调不到 |
| Policy 硬闸 | `policy.py`：高危/写默认 blocked；租户谓词强制 | 越权与写失控 |
| 运行期形态校验 | `gateway.py:274` | 参数错在出门前拦住 |
| 稳定错误码 | `errors.py` + `error_map`，不外泄原文 | 模型拿到无法决策的字符串 |
| 幂等 + 租约 + 回执 | `idempotency.py` / `receipts.py` | 重复写（最贵的错误） |
| 确定性判分 + 题集 + 基线 | `evals/agent/golden/*`、`graders.py` | "模型给自己打分" |
| 预算与循环上限 | `budget.py`：32 步 / 墙钟；`MAX_SUBTASKS=4`；critic 重试/重绑 =1 | 无限循环 |
| rewrite 熔断 | `lg_rag/nodes.py:235/273`：重写后与原 query 相同 → 终止 | 自我复读式循环 |

缺口：熔断、降级、配额（见 Q3/Q6）。

## Q6 · 幻觉 / 失控 / 单点风险

### 现状

- 可见集裁剪（看不见 → 调不到）+ Policy 默认拒 + `hitl_required` /
  `hitl_snapshot_fields`（人工审批快照）。
- **即使幻觉调了写**：未放行 → 出不去（R1）；放行了 → 幂等保证只执行一次；
  留回执 → 可审计、可对账。
- 预算/熔断/cirtic 上限 + rewrite 熔断。
- `/metrics` 的 `write.blocked` 可观测（**恒为 0 既可能是没人用，也可能是闸没装上**，
  必须与 `/runtime` 合看）。

### 缺口

- **没有全局 kill switch**：不能一键停掉某能力 / 某租户的所有写。
- **没有每会话工具调用预算**：现在预算是 supervisor **步数**，不是"调用次数 /
  写操作数"。幻觉可以在一步里连打十次。
- **没有异常模式检测**：同一能力短时间高频调用是典型失控信号，现在没人看。

### 补齐（P0）

| 项 | 做法 |
|---|---|
| per-session 配额 | 最大调用数 + **最大写操作数（默认 1–2）**，超限即停并上报 |
| kill switch | 按 capability / tenant 的紧急停用；**独立审计**（正常变更仍走 PR，不混用） |
| 异常模式 | 同 `(capability_id, args)` 短时间重复 → 判循环；接入 `/metrics` 与红线 |

## Q7 · 十几个工具动态选择 → 漏工具 / 跳步骤 / 循环

### 现状

- 可见集裁剪缩小候选；`node_role` 让不同节点看到不同视野。
- `when_to_use` 强制声明。
- 循环有硬上限：预算 32 步 / `MAX_SUBTASKS=4` / critic 重试上限 =1 / rewrite 熔断。
- **漏工具、跳步骤能被"测出来"**：题集判规划出口（`acc.route_match` / `acc.plan_match`）。

### 缺口

- **工具集是全量喂给模型的**（裁剪后全部）。到几十个时会退化：选择困难 + 漏选。
- 没有"**必备步骤检查单**"（这类任务必须调用哪些能力）。
- 循环检测目前是"步数上限"，不够精准。

### 补齐（P1/P2）

1. **按需检索式选工具**：`when_to_use` 向量召回 top-k（5–8）再交给模型选。
2. **任务模板 `required_capabilities`**：编排层校验，缺了就是"跳步骤"，直接失败。
3. **循环指纹检测**：同 `(capability_id, args)` 出现 2 次即判循环，比步数上限更早、更准。

## Q8 · 执行中需要新增工具 / 调整参数 → 全量重规划还是增量修正

### 现状

- **幂等键 + 回执 + `subtask_id`** → 已执行步骤可识别、可重放（R9）。
- **禁止热加载**（清单变更必须重启/显式 reload）→ 规划中途工具集**不会悄悄变**。
  这是刻意的一致性优先：宁可不支持"边跑边加工具"，也不要出现"计划里的工具变了"。
- 基线 diff → 改动后产出是否漂移可测。

### 缺口

- **没有"已执行步骤锁定"的显式结构**：现在靠状态里的历史消息，没有
  "不可变前缀"这种声明。
- 没有增量重规划的策略定义（现在要么全量重规划，要么 critic `rebind` 一次）。
- 参数调整若影响已执行步骤，没有明确的处理规则。

### 补齐（P1）

1. 规划表示成 **不可变前缀 + 可变后缀**：已执行步骤进前缀，重规划只动后缀。
2. 前缀每步用**幂等键锚定** → 前缀重跑天然安全（这是幂等真正的价值）。
3. **新工具注入只允许落在下一个未执行步骤**，不允许改写前缀。
4. 参数调整若影响已执行步骤 → **必须人工确认**（hitl），不能自动改。

## 优先级（按"失效一次有多贵"排）

| 优先级 | 项 | 挡住哪问 | 理由 |
|---|---|---|---|
| **P0** | 输出契约 `output_schema` + 空结果显式可疑（候选红线 R10） | Q2 / Q4 | 现在**唯一**"错了还报成功"的口子，且会污染整条链路 |
| **P0** | per-session 配额（尤其写操作数）+ kill switch | Q6 | 失控的代价是重复写；幂等已就位，只差配额与开关 |
| **P1** | 熔断 + 降级链 + 调用配额 | Q3 | 下游挂了要有策略，不能只有"失败"和"重试"两种 |
| **P1** | 步骤契约 `consumes/produces` + 可恢复点 | Q4 / Q8 | 与幂等天然咬合，投入产出比高 |
| **P1** | 循环指纹检测 | Q7 | 比步数上限更早更准 |
| **P2** | 工具检索 top-k + `required_capabilities` | Q7 | 工具变多后才痛 |
| **P2** | 参数纠错重试 + 选择理由一致性 | Q1 | Q1 已有三道拦，这是锦上添花 |

## 面试怎么答这八问（结构比内容重要）

不要逐条背"我们有 X"。先分层，再举例：

1. **先分类**：这八条不是八个问题，是四类（选择错 / 结果错 / 环境错 / 失控）。
2. **每类选不同武器**：能确定性判定的（形态、权限、副作用）**绝不让模型判断**；
   只能事后发现的（结果缺失）靠**契约 + 对账 + 观测**；
   只能收敛的（幻觉）靠 **预算 + 审批 + 幂等 + 可回滚**。
3. **给一个自己踩过的例子**：db 持久化下同步 `invoke` 会 fail-closed（R8）——
   "危险不在报错，而在报错的替代方案：退化成'防重没生效但仍发请求'，一次重试就两张单"。
4. **主动说缺口**：Q2 的输出契约、Q6 的会话配额目前没有 ——
   承认缺口并给出补齐顺序，比声称"都有"可信得多。
