# 07 · 案例：第一个完整任务（issue #311 / PR #312 / PR #313）

**TL;DR：** 人工闸模式全流程：10 帽起草 → 人工把设计闸三决策点逐一裁决写进 PR review → issue 下达 30 授权（六条交付条件）→ 红测先行的 PR → 逐文件审查合并。确立了"裁决写进 issue、bot 逐字引用"的范式。

> 第一个走完全流水线的 task：人工签闸 + 30 授权模式。
> 价值：建立了"裁决写进 issue"的工作范式，以及红测先行的验收标准。

## 3. 人工审查与三决策裁决（这一环节是全文重点）

我没有只签"approved"，而是把设计闸的三个决策点逐一裁决写进 PR review：

| 决策点 | 裁决 | 理由 |
|---|---|---|
| ① resume 链租户来源 | **A+B 组合** | 单据 `tenant_id` 为唯一真源做快照还原（对齐守卫 `row.tenant_id` 语义）；手动入口 session 租户存在且 ≠ 单据租户 → 403（有 `lg_rag/router.py:376-384` 先例）；auto-scan 无请求上下文 → 纯 A；fail-closed：单据 tenant 空 → 拒 resume |
| ② delegation 消费守卫 | **扩列纳入校验** | T-fix-2 打戳后守卫查非空成立，真空真正收口；豁免文档化等于留洞 |
| ③ 历史 `tenant_id=''` 40 行 | **默认从严** | 一律 fail-closed 拒 resume、不回填；真有诉求走单独授权的数据修复 |

## 6. 踩坑记录

- `gh api ... -f body=@/tmp/auth311.md` **不会展开文件**，发出了字面 "@/tmp/auth311.md"。正确：`gh issue comment N --body "$(cat file.md)"`（bot 靠 PR review 里的裁决上下文仍正确执行，但评论本身是废的）。
- `gh pr merge` 返回 0 ≠ 合上了：必须验证 `merged: true` + master HEAD（详见 09 篇）。
