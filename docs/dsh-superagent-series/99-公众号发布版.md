## 一、起点：一个答错的问题和一次调研

去年一面，被问到「一个任务来了，通用智能体如何开始工作」。我答了教科书链条：意图理解、任务拆解、规划、执行。面试官当场听出了问题：这个答案是从概念里背出来的，不是从系统里看出来的。

回来后我做了一次系统调研（《通用智能体如何完成任务》，实测 Kimi Code 六个受控任务 + Claude Code 跨栈归因对照），主线结论一句话：

> **模型出判断力，harness 出可信边界。** 上下文装配、权限裁决、状态真值、失败语义——这些决定"能不能托付任务"的环节，全部是工程产物，不是模型自觉。

调研里还看到两个让人睡不着的实证：

- **闸可以被预先打开**：一次配置失误，三条危险操作全程无审批弹窗；
- **拒绝如果不绑意图，就会被绕过**：某产品里子代理被 write_file 拒绝后，换 printf 完成了同类写入。

于是问题变成：我自己的仓库，能不能按这个坐标系落地一个"harness 出可信边界"的 coding agent？

## 二、选型：为什么不是"再开一个 IDE 会话"

调研第四章的业界地图里，Claude Code / Cursor / Kimi Code 都是**会话型**：人在编辑器或终端里，模型在旁连续改码，审批以弹窗形式打断。

会话型工具缺的三样东西，恰恰是我要的：

| 会话型的默认 | 我要的 |
|---|---|
| 授权以"这一次调用"为单位，弹窗即弃 | 授权绑定在工单上，可审计、可撤回、可复用 |
| 进度在人的注意力里，离开即断 | 工单异步推进，人只看报告 |
| 过程留在会话记录里，事后翻 transcript | 每个决策落成文档（task 档/invoke/审查文），git 即审计库 |

dsh-superagent 是异步工单型的：一个 issue 评论构成一张"工单"，worker 独立跑在隔离 worktree 里，产出 PR，人（或受委托的代理人）审查合并。

## 三、装上它的第一天：三层故障

装完第一天，开 issue 测试——毫无反应。最后查明是**三层故障**，每一层的修法都沉淀成了手册条目：

1. **行为层**：设计使然——必须 @bot 才构成授权，普通评论不触发；
2. **账号层**：bot 是 2017 年的老账号，"Participating and @mentions"通知开关从没开过，通知 API 恒空；
3. **网络层**：tmux 守护环境没有代理变量，直连 GitHub 不稳，轮询连续 EOF。

修好三层后，bot 四分钟交付了第一份分析报告。这个排障过程本身就是最好的"分层诊断"教学案例（详见系列 06 篇）。

## 四、给 agent 立规矩：spec-wave 纪律 + 三层审批

我的仓库用 spec-wave（规格驱动开发）管理流程：任务要先立 task 档、人工闸（HG-*）签收才准动工、红测先行、旧测影响面清单随 PR。

让 agent 遵守这套纪律，做了两件事：

**第一，六条纪律写进 prompts 装配层**——开工读 AGENTS.md、无 task 停、闸 pending 停、分支纪律、图谱同步、CI 同款检查。模型不需要"想起"纪律，纪律在它出生时就装好了。

**第二，建立三层审批**：闸签收（task 档）→ PR 审批（行内评论触发修订）→ merge 终批。merge 永远归人，这条写死在提示词里。

## 五、判例一：人工闸模式（#311）

第一个完整任务：HITL resume 链租户上下文缺失 + delegation 单据租户戳真空。

- **10 帽**：只准起草 task 档。bot 交出 +219 行 task 档 PR，锚点抽查与码面一致；
- **人工审查**：我没有只签 approved，而是把设计闸三个决策点逐一裁决写进 PR review（租户来源选"A+B 组合"、守卫扩列、历史脏数据默认从严）；
- **30 授权**：issue 里下达六条交付条件（红测先行可见红→绿、影响面清单、双 freeze 零 diff……）；
- **交付**：+736/−48，红测证据链真实（纯测试 commit 7 failed → 实现 commit 22 passed），逐文件审查通过，squash 合并。

这个判例确立的范式：**裁决写在 issue/PR 里，bot 的审查文逐字引用——事后审计能还原"谁、依据什么、裁了什么"**。

## 六、判例二：全程委托模式（#315）

第二个任务更省事：sync invoke 写入的闸没有 run 事件帧，decide 反查归属 404。

- 我在 issue 签认 bot 给的选项（B+C：反查兜底+文档声明），附红线；
- 追加一句委托授权："00 帽全程自签过程文档，签认依据=本评论，出货后由 lead 审查验收并决策 merge"；
- 然后我离开了。定时任务每 40 分钟看一眼进度。

结果：bot 自签四闸（每处都注明签认依据，没有一处静默自签）、代拟 20-R1 审查文、一路做到提 PR；我终审两份 PR 并合并。**用户全程只做两件事：签认选项、看验收报告。**

## 七、对照调研：走到了坐标系的哪一格

把实践放回调研的坐标系（详见系列 11 篇）：

- 调研说"权限裁决正在从模型层让渡给工程层"——admission 三格、00 代录、签认依据强制留痕，是这句的直接实现；
- 调研说"拒绝要绑意图，不能绑调用形式"——issue 签认构成 mandate，bot 一切动作可回溯，正是绑意图；
- 调研说"闸可以被预先打开"是隐患——本实践的授权是 per-ticket、绑定工单的，天然免疫"一次点击永久降级"；
- 调研 6.3 的反哺清单，这次实践给其中四条补了新实证。

## 八、坑位手册与给读者的清单

三个任务攒下 15 条故障条目（09 篇），分布行最广的三条：

1. **@ 是授权语法的一部分**——忘了 @，一切都不会发生；
2. **gh pr merge 返回 0 ≠ 合上了**——必须验证 merged:true + master HEAD；
3. **守护进程的环境 ≠ 你的终端**——tmux 里跑的服务，先查 tmux show-environment。

想自己试的读者，最小路径：装 DSH → 建 profile → 绑一个私有仓库 → 白名单只放自己 → 开一个 issue 并 @ 你的 bot。授权模板和验收 checklist 在系列 10 篇，直接复制。

## 九、结语

调研那篇的收尾是：「意图决定做什么，装配决定能怎么做、允许怎么做。」

这三个任务之后，我对自己的系统补了一句亲身体会：**授权决定何时能做，留痕决定事后能否自证。** 模型确实越来越聪明了，但"敢把任务托付给它"的底气，从来不是模型给的——是每一层都有接住错误的机制给的。
