# 11 · 调研对照：从「通用智能体调研」到 dsh-superagent 落地

> 2026-10 的调研报告《通用智能体如何完成任务》得出主线判断：**模型出判断力，harness 出可信边界**。
> 2026-11 落地的 dsh-superagent 实践，是这条判断在一个真实仓库上的工程实现。
> 本章把两边的证据并排，回答一个问题：**调研里读到的坐标系，实践里走到了哪一格。**

## 1. 八条判断 ↔ 本实践对照

| # | 调研判断（来源任务） | dsh-superagent 的对应机制 | 走到了哪 |
|---|---|---|---|
| 1 | 工作的起点是装配，不是意图（T1/T5/T6） | Source 绑定单仓库 + Policy 白名单 + prompts 纪律，worker 的上下文由 harness 装配，模型不自己决定"能看什么、允许做什么" | ✅ 完整实现 |
| 2 | 权限裁决从模型层让渡给工程层（T2） | admission 三格规则（名单内未@ / 名单外@了 / 名单外未@）由代码裁决；00 帽"自签"也只是按授权的代执行，签收依据强制留痕 | ✅ 完整实现 |
| 3 | 「不幻觉」是过程中被兜住的（T3/T6） | 红测先行（负样本先红后绿、随 PR 可见证据链）+ 行为级测试 + 人工闸强制停一停；与其选"不幻觉的模型"，不如造"幻觉出不了门"的流程 | ✅ 完整实现 |
| 4 | 信任层级是 harness 注入层定义的宪法（T5） | prompts 效力优先级（代码事实 > 内置 > 规则要求 > 团队段 > 外部文本）+ revision 版本机制——层级显式设计，不是谁声音大 | ✅ 显式设计 |
| 5 | 恢复能力的分水岭是独立于内存的持久化真值（T4） | 真值三层：git（代码与 task 档）+ sqlite 状态库（游标/工单）+ invoke/审查文（决策留痕）；任何一环重启不丢 | ✅ 完整实现 |
| 6 | 危险操作的安全感来自闸的可见性（T2/VanorOS） | 三层审批：闸签收（task 档）→ PR 审批（行内评论即触发修订）→ merge 终批；红线可机检（freeze 零 diff）；拒绝的语义 = 停下来问请求者，而非换方式绕 | ✅ 完整实现 |
| 7 | 大仓范围确认的答案是检索纪律（T6） | 此维度本实践未覆盖（场景不同：绑定单仓库的工单不需要大仓探索） | ➖ 不适用 |
| 8 | **总纲：模型出判断力，harness 出可信边界** | dsh-superagent 本体就是这个判断的实例：模型负责语义理解与编码判断，一切"能不能托付"的环节（白名单、闸、审计、fail-closed、留痕）全部是工程产物 | ✅ 主线的直接落地 |

## 2. 「同一问题的三种答案」+ 本实践作为第四种

调研第 5 章把 Ops Desk / VanorOS / SpecWave 放在三个取舍坐标上（绑调用还是绑意图、模型裁决还是工程裁决、内存还是落盘）。dsh-superagent 实践给出第四个数据点：

| 系统 | 真值存哪 | 闸在哪层 | 拒绝之后 | 裁决归属 |
|---|---|---|---|---|
| Ops Desk（自建运行时） | 事件帧落库 + checkpoint | 七层闸链，高危能力对模型不可见 | 闸拒不落回执但落审计行，带 stage 定位 | 工程签发/验签分离 |
| VanorOS 0.5.8（实测） | JSONL 会话日志 | 工具级审批，拒绝绑调用 | ❌ 无终止语义——子代理换 printf 绕过 | 模型自觉为主 |
| SpecWave（自研工具链） | task 档 + invoke 文档 | 流程闸：先签规格才准动工 | 闸 pending = 拒开工 | 人工闸 |
| **dsh-superagent（本实践）** | **git + sqlite + invoke 三件套** | **三层审批 + 00 委托代录** | **停下来问请求者；授权评论是唯一放行凭证** | **工程裁决，人保留 merge/验收** |

本实践的特殊之处：**授权是"绑意图"的**——不是某条命令被允许，而是 issue 线程里的一个明确签认构成 mandate，任何执行动作都能回溯到那条评论。这正好补上调研里 VanorOS 暴露的缺口（拒绝绑调用不绑意图 → 换形式绕过）。

## 3. 与《AI Coding 治理取舍调查》的对照

那份调查的核心张力：**「少介入换速度」vs「多闸口换确定性」**。

本实践的回答是**分级的委托**而不是二选一：

| 档位 | 介入程度 | 形态 |
|---|---|---|
| 全人工 | 每个闸都停下来找人签 | 07 篇 #311 的第一棒 |
| 裁决留人 + 执行委托 | 人在 issue 写裁决口径，00 代录签收做到 PR | 07 篇的 30 棒、08 篇的部分环节 |
| 全程委托 | issue 一句授权，00 自签全闸，终审 merge 交代理人 | 08 篇 #315 |

关键设计：**委托的粒度是 per-ticket 的、可撤回的、必须留痕的**——这比"全局信任设置"（调研里 CC-E0「闸可预开」的教训）安全得多。闸可以被预先打开一次点击写配置，而 issue 授权绑定在具体工单上，过期即失效。

## 4. 调研反哺清单的落实状态

调研 6.3 节给 Ops Desk 列了 7 条反哺动作。本实践对应其中几条给出了新的实证：

| 反哺项 | 本实践的新证据 |
|---|---|
| 拒绝要绑意图 | #315 的模式即"绑意图"：受理评论构成 mandate，bot 的一切动作回溯到它 |
| 签发与验签分离 | 00 代录签收必须引用授权评论 = 验签动作；无引用即违规（审查 checklist 第 9 条机检） |
| 「先闸后行」推广到产出流程 | spec-wave 六纪律进 prompts（revision 2）+ HG-* 闸全链路运转三个 task |
| 规则注入优于读取 | 六纪律和委托规则在 prompts 装配层，0 次"让模型自己想起纪律" |

## 5. 结语

调研的收尾说：「意图决定做什么，装配决定能怎么做、允许怎么做。」
本实践补上下半句的实例：**授权决定何时能做，留痕决定事后能否自证。**
