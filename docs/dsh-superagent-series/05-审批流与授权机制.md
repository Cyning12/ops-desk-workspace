# 05 · 审批流与授权机制

**TL;DR：** 六条 spec-wave 纪律进 prompts；三层审批（闸签收→PR 审批→merge 终批）；issue 里一句明确授权即可让 00 自签全闸做到 PR，但 merge/验收永远归人，每处签收必须引用授权评论。

> superagent 仓库本身用 spec-wave 流程开发，要求 agent 也按这套纪律干活。
> 本章是授权相关的全部规则：纪律、三层审批、00 帽委托、模板。

## 1. spec-wave 六条纪律（prompts scope 段，revision 2 起生效）

1. 开工前读 `AGENTS.md`；
2. 先扫 `docs/tasks/active/task_*.md`，没有对应 active task 就停下；
3. 跑 `npx spec-wave verify`，**有闸 pending 必须停下来找请求者签，禁止绕过**；
4. 分支纪律：`task/<desc>` 或 `fix/<desc>`，禁止直推 main；
5. 动路由/表/事件必须同步 `docs/_tech_graph/`（l0/l1/l2/shared），PR 前 `./scripts/graph-compile.sh` 通过；
6. PR 前跑 CI 同款检查。

单一真值是仓内 `AGENTS.md`——改了它 agent 自动跟随，不用改 superagent 的 prompts。

## 2. 三层审批模型

| 层 | 时机 | 载体 | 谁 |
|---|---|---|---|
| ① 人工闸签收 | 开工前 | task 文件闸表（HG-*） | 维护者（可委托 00 代录） |
| ② PR 针对性审批 | 每根 PR | PR review（行内评论/Request changes 触发修订） | 维护者或受委托人 |
| ③ merge 终批 | 交付时 | 点合并的人 | **永远是人（或其明确委托的代理人）** |

PR 本身就是审批载体——审查记录、签认依据、验收勾选全在上面，事后可审计。

## 3. 00 帽委托授权（prompts revision 3，双态规则）

> 规则原文（scope 段附录）：当工单线程里存在**明确授权**（如"授权 00 帽自签过程文档"），worker 可以代执行签收：把 task 档闸表更新为 approved 并在每处注明签认依据（引用授权评论）、代拟并落档 20-R1 审查文、一路做到提 PR。**merge 与最终验收永远归人。** 每处委托签收必须引用授权评论——禁止静默自签。没有明确授权时，闸 pending = 停下来问。

设计要点：

- **授权载体 = issue 线程**：绑定工单、审计留痕、可 per-ticket 撤回。
- **双态**：有授权→自签全闸+做到 PR；无授权→停并问。
- **决策与执行分离**：00 可以"代录签收"，但裁决口径最好由人在 issue 里写明（判例见 07 篇的三决策裁决）。
- 全闸放开（含设计闸）是基于用户的选择；保守用法可以只预授权 HG-TASK-DRAFT / HG-GRAPH-MODULES，设计闸保留人工。

## 4. 授权模板（复制到 issue 用）

**签认选项 + 10 帽**（立项）：

```markdown
@cyning12-bot <任务描述>
签认：<选项，如 B+C>。<必要的裁决口径>
授权：10 帽起草 fix task + 出 PR。
红线：<不可动的东西，如 SSE 事件表零 diff>。
```

**00 帽全程委托**（代表模式，见 08 篇）：

```markdown
@cyning12-bot 补充授权：00 帽全程自签过程文档（闸表签收 + 20-R1 审查文），
签认依据 = 本评论；出货后由 <lead/维护者> 审查验收并决策 merge。全程文档留痕。
```

**30 改码授权 + 交付条件**（07 篇实例）：

```markdown
闸表更新 + 审查文落档完成后，开始 30 改码，要求：
红测先行可见红→绿 / 旧测影响面清单随 PR / 双入口单实现 /
双 freeze 零 diff / 本地三检全绿 / PR 说明逐条对照验收。
```

## 5. 何时人工、何时委托

| 场景 | 建议 |
|---|---|
| 涉及新设计裁决（多方案取舍） | issue 写明裁决口径 + 00 委托；或直接人工签 |
| 纯修复、契约已清晰 | 直接 00 全程委托 |
| 动 freeze 面 / 安全敏感 | 人工逐闸签，不委托 |
| 探索性/没把握的需求 | 只授 10 帽，task 档出来人再审 |
