## 3. 授权模板（issue 评论，复制即用）

**立项（签认 + 10 帽）**

```markdown
@cyning12-bot <任务描述。写清触发条件和期望产出>

签认：<选项字母+一句裁决口径>
授权：10 帽起草 fix task + 出 PR，不改码。
红线：<不可动的面，如 SSE 事件表零 diff；红测必须覆盖 xxx>
```

**全程委托（00 帽）**

```markdown
@cyning12-bot 补充授权：00 帽全程自签过程文档（闸表签收 + 20-R1 审查文），
签认依据 = 本评论；出货后由 lead 审查验收并决策 merge。全程文档留痕。
```

**30 改码（含交付条件）**

```markdown
闸表更新 + 审查文落档后，开始 30。要求：
1. 红测先行：负样本先红后绿，PR 可见红→绿证据；
2. 旧测 grep 影响面清单随 PR，禁静默改测；
3. <任务特有红线，如双 freeze 零 diff / 双入口单实现>；
4. 交付前 ruff + pytest + graph-compile 全绿；
5. PR 说明逐条对照 task 档验收标准勾选。
```

## 4. 验收 checklist（PR 终审时逐项勾）

- [ ] diff 范围 = task 档钉的范围，无夹带
- [ ] 红线逐条机检（freeze 零 diff / 单实现 / 守卫单真源）
- [ ] 红测证据链：RED commit（纯测试）在 GREEN commit（实现）之前，以 commit date 为准
- [ ] 新测试是行为级（驱动真实代码断言），非 import 假红
- [ ] 有帧/正路径零漂移护栏（mock 断言不走新逻辑）
- [ ] 旧测影响面清单齐全，零静默改测
- [ ] 全量测试失败数 == master 基线失败数（零新增红）
- [ ] spec-wave verify / GATE_VERIFY PASS
- [ ] 闸表签收每处注明签认依据（无静默自签）
- [ ] 合并后验证 `merged: true` + master HEAD
- [ ] 人工验收项写清"在哪、做什么、看什么字段"（如 C6 复测）

## 5. 日常节奏参考

| 场景 | 动作 |
|---|---|
| 小修复/兜底，契约清晰 | 立项评论 + 00 委托，等验收报告 |
| 有设计取舍 | 立项评论写明裁决口径 + 00 委托（或先只授 10 帽） |
| 动 freeze / 安全敏感 | 人工逐闸签，不委托 |
| 没把握的需求 | 只授 10 帽，task 档出来人再审 |
| bot 没反应 | 查 09 篇 S1-S3 |
| 网络报错 | 查 09 篇 S4-S5 |

## 6. 升级与迁移注意

- 升级 DSH → `scripts/dsh-superagent restart`，然后面板确认 plugins loaded。
- token 会变，重新取（见上表）。
- 换机器 = 01 篇 checklist + 02 篇凭据 + 03 篇四件套。
- 本系列文档脱敏，真实值一律回 `~/.dsh/` 下对应文件取。
