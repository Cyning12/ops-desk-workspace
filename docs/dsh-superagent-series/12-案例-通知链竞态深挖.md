# 12 · 案例：通知链竞态深挖（issue #323，2026-11-05）

**TL;DR：** 一条 @ 评论三次才触发成功——先是 GitHub 通知管道延迟 18 分钟，后是"通知 updated_at 回填时刻落在轮询 since 游标之后"的结构性竞态把通知永久过滤。根因都在轮询设计里，已给出三个上游修复方向。操作手册见 09 篇 S3/S3b。

> 前三个判例（06–08）验证了系统在正常路径上的行为；本判例是第一个**深挖到源码级根因**的故障——面板可见性 + 决定不可变设计让现场完全可读，源码 [github.ts:298-343](../../dsh-superagent-prototype/src/sources/github.ts) 让根因可定位。

## 1. 任务与背景

issue #323：SPEC 审查与选型签收（阶段 W 扩写能力）。用户在标题里写了 `@cyning12-bot`，但标题 mention 不构成 addressing（见 09 篇 S1）——线程被正确标记"未订阅"。

修复动作：以 Cyning12 身份在评论里 @bot 发 hat 20 受理（kick #1）。

## 2. 完整时间线（全部为本地时间 2026-11-05）

| 时刻 | 事件 |
|---|---|
| 11:22 | #323 创建（@ 在标题）→ 03:23 poll 到达 → gate `no_mention` → **ignore（设计正确）** |
| 11:29 | kick #1 评论发出（@ 在正文） |
| 11:29–11:47 | bot 通知 API **持续为空 18 分钟**——GitHub 通知管道延迟（故障 F1） |
| ~11:46 | kick #2（触发补发 #1）：通知**秒级生成**，但 `updated_at` 回填为评论时刻 03:46:56 |
| 11:47–11:52 | 通知 API 查得到该 mention，但源健康持续 "0 notifications"，线程时间线无新事件 |
| 11:52 | 源码定位：轮询 `since` 游标竞态（故障 F2，见 §3） |
| ~11:54 | kick #3（触发补发 #2）：`updated_at`=now > since → 下轮必中 |
| 11:54:46 | 事件入线 → gate explicit → 主 Session `accept · explicitRouted` → 工单 working |

总耗时：从首条 @ 评论到接单 ≈ **26 分钟**，其中约 18 分钟耗在 F1（等一条永远不来的通知），约 6 分钟耗在 F2 的确认与决策。

## 3. 根因：两个故障串联

### F1 · GitHub 通知管道延迟（外部，不可控）

kick #1 的 mention 通知 **18 分钟未在 API 出现**。昨天（#315）同操作几分钟内到达，今天同评论下午（kick #3）也是秒到——**延迟是时段性变量，不是常量**。没有任何客户端手段加速。

### F2 · since 游标竞态（结构性，上游代码）

[github.ts:304](../../dsh-superagent-prototype/src/sources/github.ts)：轮询查询 `notifications?all=true&since=<上一轮开始时间>`；[github.ts:341](../../dsh-superagent-prototype/src/sources/github.ts)：每轮结束把 `since` 原子推到**本轮开始时刻**。

GitHub 通知的 `updated_at` **回填为评论发表时刻**。于是存在一个约一个轮询周期（≥60s）的死亡窗口：

```
时刻        动作
T           评论发表（T = 03:46:56）
T+4s        轮询轮 R3 开始：查询 since=03:46（R2 开始时刻）
            → 通知还没生成（GitHub 物化耗时 δ > 4s），R3 看到 0 条
R3 结束     since 推进到 03:47:00
T+δ         通知物化，updated_at 回填为 T（03:46:56）
T+65s       轮询轮 R4：查询 since=03:47:00
            → 03:46:56 < 03:47:00，被 since 过滤 ★ 永久丢失
此后每轮    since 只增不减，这条通知再也不可能被查到
```

判据（现场特征）：**通知 API 里查得到 mention，但源持续报 "0 notifications"**——两者矛盾即 F2。

### 为什么重试机制救不了 F2

github.ts 的 retry map 只覆盖"**读线程失败**"（EOF/TLS 之类）；F2 是"**通知从未进入待读集合**"——读都还没开始，重试无从谈起。同族先例是 S3（旧事件不补发），F2 是它在"通知层"的对偶形态。

## 4. 恢复与验证

kick #3 制造 `updated_at`=now 的新通知 → 下轮 poll 命中 → `readNotified` 以游标 `github-cursor:323`=03:22:16 拉取**全部三条评论** → 新事件评估 → `accept · explicitRouted`（与旧 `ignore · no_mention` **并存**，决定不可变设计的现场演示）→ 工单 `hat 20 审查 SPEC-stage-w-expand v0` working。

无数据丢失；代价是线程里多两条"触发补发"评论（审计噪音，但诚实）。

## 5. 设计评析：为什么这个故障可以被精确诊断

1. **面板即真相**：触发 tab 的"未订阅/决定/reason code"让 F1 阶段一眼排除"bot 没干活"；
2. **决定不可变**：旧 ignore 永不被改写，新 accept 追加——不存在"状态被覆盖后无法还原现场"的问题；
3. **健康面只反映持续状态**：源的 ready/"0 notifications" 与通知 API 的矛盾把调查直接指向轮询层；
4. **源码可读**：pollRound 的失败隔离注释（"Each step and each Issue, PR, or Thread fails independently"）明确了设计意图，排除"整轮失败"假设。

## 6. 上游修复方向（给 dsh-superagent 仓库，按推荐度排序）

1. **兜底 sweep（推荐）**：`pollThreads` 已周期性重读订阅线程；对"最近 N 小时有人类活动的未订阅线程"每 k 轮做一次无条件重读。彻底关闭"提示丢失"类故障（S3 与 F2 同治），代价是少量冗余 API 调用。
2. **since 跟随通知时间戳**：游标推进到 `max(已见通知.updated_at)` 而非轮次开始时刻。回填的通知会一直被重扫到被更新的通知取代为止；代价是窗口内通知增多时的分页成本。
3. **重叠窗口 + 去重**：`since = 本轮开始 - 2×interval`，通知按 id 去重（需引入 seen-set 及 TTL）。经典 at-least-once 改造，改动面最大。

操作层现状已够用：09 篇 S3/S3b 的判据 + "最多补发两次"实践（本次三连发是极端情况，一次成功是常态）。
