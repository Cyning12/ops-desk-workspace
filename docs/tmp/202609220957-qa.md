## 1. 面试准备

### 用户

上面是我的简历，同时再附带准备的开场白

---

面试官好，我是刘新宁，11 年研发，最近两年在百果园做 Agent 应用与工程效能负责人。

根据猎头的初步了解和我看到的公开信息，我判断这次聊的重点会落在多 Agent 的治理与可靠性上，不只是编排出一个能跑的 Agent。如果和你们实际关注的有偏差，请随时打断我。

我给两句判断。

第一句：多 Agent 平台真正难的不是编排，是「谁有权调什么」。编排框架现在满街都是，一周能出 demo；但能力一上几十个、一有写操作，先崩的是授权模型而不是编排。所以我做的那一层是：能力以注册表登记——`capability_id`、`kind`、`risk_level`、`side_effect`、`hitl_required`、`tenant_scoped`；Gateway 做可见集裁剪和精确 id 分发，执行前串一道 Policy 硬闸。模型能决定的是「在名单里点哪个」和「参数长什么样」，决定不了名单里有什么。

第二句：写操作和高危不能靠「配置放行」，得有确定性的刹车。我的做法是三件事同时成立：清单加载期就强制（写能力必须声明幂等键、必须声明要人工确认，否则加载失败，坏能力根本进不了目录）；执行前落闸（高危、写、沙箱、CLI 默认拒，放行键只有 Host 能给，模型写在 plan 里不算）；失控时有一键熄火（按能力的紧急停用 + 每个会话的调用数/写操作数上限）。这三道都不在提示词里——凡是写进提示词的安全约束，都不算闸。

边界我也直接交代：这套东西现在是进程内的注册表，不是跨进程注册中心；委派降权没做；我还不敢说它在你们那个量级上验证过。我更想先听你们的业务落点，再判断哪些要推翻重做。

所以想先确认一件事：这个多 Agent 平台主要服务车内用户，还是内部员工？

### AI

你的简历和开场白已经建立了一个非常清晰、有力的技术人设。基于你提供的背景和北汽的公开信息，我帮你梳理了面试的准备方向，核心思路是：**用你在治理与可靠性上的深度，去匹配北汽在多 Agent 量产落地上的真实痛点。**

#### 简历与岗位的匹配度

你简历中的亮点，恰好击中北汽的痛点：

- **Agent Host / Agent Gateway + 能力注册表**：`capability_id`、`risk_level`、`hitl_required` 等设计，直接对应北汽「1+N」架构中，中枢大模型如何安全地向 N 个垂域智能体分发任务。
- **HITL 安全门禁 + Policy 硬闸**：北汽强调「生命守护」；写操作和高危必须有确定性刹车。
- **SSE 流式 + Langfuse 可观测**：车载对延迟和稳定性要求极高。
- **AICoding 规格驱动协作流**：可对标研究总院内部效能场景（SpecWave / dsh-coding-kit）。

需要主动「翻译」的短板：

- **汽车行业经验**：强调你处理的是「生产级 Agent」的通用治理问题；汽车座舱是安全要求最高的应用场景之一，能力迁移性强。
- **端侧 / 车机部署**：可坦诚承认；展示思考框架——任务规划与执行分离，轻量端侧快速响应，复杂规划交云端或高性能座舱芯片。

#### 开场白优化建议

1. 第一句判断更「北汽化」：在「1+N」里，中枢决定「派谁去」，你的工作是确保「谁有资格被派去，以及派去后能做什么」。
2. 第二句加入量产视角：三道闸不仅是安全，更是可审计、可量化、可量产。
3. 收尾提问可更具体：车内用户 → 多模态意图收敛；内部员工 → 跨系统 API 安全编排。

#### 技术准备方向（摘要）

| 方向 | 要点 |
|---|---|
| 通用 Agent | LangGraph State；Supervisor vs if-else；为何多 Agent（上下文隔离、专业化、容错） |
| 北汽「1+N」 | 任务分解与意图路由；分层记忆；安全护栏与降级 |
| 治理与可靠性 | 死循环终止条件；幂等与工具治理；可观测（工具调用、权限、授权决策） |
| 安全与权限 | 最小权限；提示词注入防御（安全约束不算闸）；不可逆操作强制 HITL |

#### 反问建议

- 「1+N」任务分解是基于规则还是微调 LLM？准确率与延迟如何权衡？
- 垂域能力注册是静态配置还是动态发现？如何防恶意/故障能力？
- 多 Agent 评测侧重端到端完成率还是单 Agent 准确率？有无 Golden Test Set？

#### 总结

用「能力注册表 + Policy 硬闸 + HITL」回答「中枢如何安全调度 N 个垂域智能体」。可追问素材：多个 Agent 同时请求同一高风险能力（如修改车辆设置）时的冲突与优先级。

## 2. 模拟面试

### 用户

你现在身为一面的技术研发来开始对我进行模拟

### AI · 第 1 问（能力注册表 / Gateway 链路）

你好，刘新宁。我是北汽新能源 AI+数智化委员会的技术面试官，姓陈。感谢你来参加一面。

你开场白里提到的方向我听到了——多 Agent 的治理与可靠性，不只是编排。这个判断和我们现在「1+N」架构下遇到的真实问题很接近。我们直接进入技术环节。

先问一个关于你做的能力注册表和 Gateway 的问题。你简历里写，能力注册表包含 `capability_id`、`kind`、`risk_level`、`side_effect`、`hitl_required`、`tenant_scoped` 这些字段。我想请你详细描述一下：

**当一个用户请求进入系统后，从意图理解到最终执行工具调用，整个链路里，Gateway 和 Policy 硬闸分别在哪些节点介入？**

特别是，如果中枢大模型生成的 plan 里包含了一个不在当前会话可见集里的 `capability_id`，Gateway 会怎么处理？是直接拒绝，还是有别的机制？

### 用户 · 答

我先把链路拆成两段讲——编排侧三道，执行侧六道——因为「可见性」这件事，真正起作用的地方在编排侧，不在 Gateway。

**编排侧**

1. **策略 Builder**（不调大模型）：路由候选 id ∩ 注册表可见集 → `allowed` / `stripped`，剔除写进 span。安全默认：宁可退化成无工具，也不全开。
2. **拼 prompt 之前算可见集**：场景维（kind / 风险 / 写副作用 / tags）× 身份维（部门 / 角色 / 项目 / 密级）。主体从 `ctx` 构造；模型写在 payload 里的 departments、roles 一律无效。
3. **模型出完 plan 立刻校验**（最易被忽略）。

**执行侧（Gateway 六道门，顺序有意）**

查表 → 是否启用 → Policy 硬闸 → 下游熔断 → 熄火开关与会话配额 → 参数 schema。

- 熔断优先于配额（下游挂了还扣配额是浪费）
- 参数校验放最后（前面任一道拒了，不该让模型以为「改改参数就能过」）

Policy 硬闸判四件事，闸序：危险程度 → 副作用 → 危险形态 → 输入完整性。写入判断挂在副作用上，不挂在执行等级上——所以 `medium + write` 这种「普通提交」在只看风险等级的实现里会被放行，在我这儿不会。放行只有两个来源：进程环境变量，或 Host 构造的 `ctx["_host_policy"]`。

若出现不可见 id：**不是到 Gateway 被拒，是在编排层就被判整份 plan 非法**。子任务标记失败；主 Agent 验收全部 plan 时会思考下一轮安排。

### AI · 第 2 问（双重校验 / 危险形态 / 委派降权）

好，你这段回答信息量很大，而且把「可见性」放在编排侧而不是 Gateway，这个判断我认可。但我顺着你的链路追问三个点，你逐个回答，不用急。

**第一，双重校验的一致性**

编排层已做可见集过滤，Gateway 还有一道「查表」。两层是同一份注册表吗？若编排层放行后，Gateway 发现能力已被紧急停用或策略变更——怎么处理？返回给主 Agent 的错误会不会含「这个 id 不可用」的细节？下一轮是换相似 id 重试，还是怎么修正？

**第二，危险形态与输入完整性**

Policy 硬闸四件事里，「危险形态」指什么？举车控例子：什么情况下直接拒绝而不是走 HITL？「打开车窗」和「解锁车门」分别落在哪一档？「输入完整性」是只校验 schema，还是也校验值是否落在安全域？

**第三，委派降权**

简历写「委派降权没做」。在「1+N」下，中枢调垂域、垂域再调工具，若不做降权有何风险？「查询车况」的垂域能否间接调到「解锁车门」？若要补，权限继承与衰减怎么设计？

### 用户 · 答

1. **是共用注册表**。返回给主 Agent 也会标记错误内容，有 errors 模块做整体语义转换。工具匹配本身不看 id，主要靠配置中的 `desc` / `when_to_use` / `when_not_to_use` 语义匹配取 top-10，再分配；若仍召回错误 id，会根据之前的错误内容筛掉。
2. **危险形态**按操作失败会造成的危害定，需结合业务。正常情况下：打开车窗走 HITL；解锁车门默认拒绝。开窗改变车状态，一般不直接危及生命，决策权交给人；自动解锁人身安全风险更大，故默认拒绝。
3. **委派降权**表述可能不准：实际是同进程 Agent 管理，子 Agent 完全受主 Agent 管理，不会越权。提到这句是为了对齐层级。类比此场景可提方案：解锁车门权限在主 Agent；给 sub 的能力范围本身不可见该能力。基于 A2A 中间做校验网关（**A2G2A**）：主 Agent 感知/编排/分发，向网关携带授权能力范围、任务、密钥；sub 完成后交网关校验前后密钥、权限范围、权限携带参数等；不合法直接报错给主 Agent。

### AI · 第 3 问（时序停用 / 值域 / 令牌攻击面）

好，三个点都答了，但有两个地方我需要往下钻一层。

**第一**：编排层放行后 Gateway 发现刚被紧急停用——主 Agent 下一轮怎么修正？靠错误语义换相近 id，还是直接标失败？前者如何保证换的 id 不在同一停用批次？后者用户感知如何解释？

**第二**：「输入完整性」还没展开。假设参数 `{temperature: 22, unit: "celsius"}`——是只校验 schema，还是也校验值域（如 16–30，且由车控域声明）？若只校验 schema，`{temperature: 999}` 会过网关、到执行侧才报错，你怎么看这个边界？

**第三**：A2G2A 密钥设计。若 subagent 被提示词注入拿到密钥，能否用该密钥向网关申请「原本不在授权范围」的能力？「权限携带参数」校验的是密钥绑定白名单，还是请求参数是否在授权范围内？损失边界在哪？

### 用户 · 答

1. state 中保存 tool 调用简报；再次规划时直接把之前的 id 裁剪出去。最终没有工具可继续完成任务时，把简报中的错误内容展示给用户，如「权限不足或无法满足需求」。
2. 你说的情况就是针对字段的语义定义，例如 temperature 注释要求小于 100。
3. 无法拿到。网关防护分步：
   - **第一层（入口）**：令牌、白名单等，快速筛非法请求
   - **第二层（执行前）**：params 满足 `cap.constraints`；封闭世界——未声明参数 / 不在注释范围一律拒绝
   - **第三层（真实资源端）**：独立校验网关签发的执行凭证，不信任网关结论
   - 「密钥」实为**能力令牌**，能力集编码在签名内容里；子 Agent 无私钥，无法改能力集；网关只信令牌签名内容
   - 白名单在入口（集合运算），参数在能力执行前（值域）；损失边界 = 能力集 × TTL × 一次性 × 参数约束 × 主体绑定

### AI · 第 4 问（部分成功 / 约束归属 / 车速约束 / 令牌绑定）

好，三个点都往下走了，但每个点我都还有一层要钻。

1. **裁剪粒度与错误语义**：「打开天窗并播放音乐」，天窗停用、音乐正常——是只裁天窗还是整 plan 失败？「权限不足或无法满足需求」是否把 CAPABILITY_DISABLED / USER_PERMISSION_DENIED / 无法拆解混在一起？
2. **值域注释写在哪**：注册表还是车控域代码？Policy 能否读到并执行？谁来写、如何防漏写？（类比「写能力必须声明幂等键否则加载失败」）
3. **令牌爆炸半径**：高速上天窗打开是否仍「安全」？车速 >80 禁止自动开天窗写在令牌还是车控域？你更接受「一次合法打开」还是「一次被拒绝的请求」？令牌绑定到子 Agent 怎么实现？「令牌签发」本身是否高危需 HITL？

### 用户 · 答

1. 颗粒度看 plan 任务是否有关联：并行无依赖可只执行一个；有依赖（如开空调并设风量最大）则空调受阻时风量也不执行。「权限不足…」三种情况**内部必须区分**，展示给用户可合并措辞；主 Agent 下一轮依据精确错误码。例：CAPABILITY_DISABLED →「暂时无法完成，请稍后再试」；USER_PERMISSION_DENIED →「您没有权限执行此操作」。
2. 写在 capability 注册表（YAML）；策略闸门读约束、版本号等，防能力更新造成语义不一致。值域约束主责是开发者；专业场景由专人出规则并审核；发布前 CI/CD 验证。
3. 「>80 禁止自动打开」约束在注册表。复杂场景最终执行处兜底。**我更接受一次被拒绝的请求。** 令牌：两者结合——「令牌签发」本身高危，必须 HITL；子 Agent 可拿身份令牌，主 Agent 才能申请会话令牌（如 TTL 10s），只用于下发具体操作。

### AI · 第 5 问（工程落地五题）

好，这几个回答都落地了。我不再钻细节，换几个更偏工程落地和组织协作的问题，你放松点答。

1. **性能**：链路经策略 Builder、可见集、plan 校验、六道门等——车端受限下端到端延迟量级？「打开车窗」期望 P99？配置热加载 / 内存缓存 / 版本失效？
2. **开发者体验**：声明很严，多垂域团队怎么愿意写？内部能力「不用写 HITL」怎么处理？有无脚手架？
3. **异构**：跨进程垂域如何同步注册表？挂了是「存在但不可用」还是「不存在」？
4. **业务关系**：HITL 导致审批变长，业务抱怨「以前点一下现在点三下」——怎么平衡？
5. **主动服务**：打哈欠主动调温/放音乐——与「写操作必须 HITL」如何兼容？

### 用户 · 答

**1. 性能**  
结论：策略链路不应是瓶颈，LLM 才是。P99 期望约 1.5–2s（>2s 觉得卡，>3s 觉得没反应）。必须做：配置热加载 + 内存缓存；版本号失效；YAML 预编译成函数/决策树；可见集用 bitmap/哈希集。

**2. 开发者体验**  
三层：脚手架/模板 → 默认值策略（不写 `hitl_required` 默认 true，不写 `risk_level` 默认 high）→ 分级治理。不写就默认严格；想放宽需安全域审批并写明理由（`hitl_exempt`）。

**3. 异构**  
主 Agent 应看到「存在但不可用」而非「不存在」。同步用 A2A Agent Card（`/.well-known/agent.json`），定期拉取/推送；变更通知 Gateway 并递增版本号。

**4. 业务沟通**  
话术：「不是我要卡你，是监管和审计要求；我可帮你做风险分级，低风险快速通道。」用数据证明 HITL 拦截价值；安全设计与业务方共同定风险等级。

**5. 主动服务**  
本质是「预授权 + 可撤销」，不是无授权。用户设置里勾选允许类型；范围内低风险写：自动执行 + 通知 + 可撤销；超出范围必须确认。原则修正：**高风险写必须 HITL；低风险写可自动执行，但必须可撤销、可审计。**

### AI · 第 6 问（可撤销 / 默认值 / 第三方）

挑两个最值得往下钻的点：

1. **可撤销**：撤销是针对「操作」还是「状态」？车控有无统一 snapshot/restore？`reversible: false` 能否进预授权？
2. **默认严格**：几百个低风险能力若全默认 high+HITL，体验崩了怎么办？领域默认值 / 批量审核？
3. **第三方**（高德/腾讯/字节）：Gateway 如何跨域映射？信不信第三方自己的 risk 声明？

### 用户 · 答

**一、可撤销：撤销的是状态，不是操作**  
状态版本化：操作前 snapshot（如 temperature=22, v1）→ 操作后 v2 → 窗口内恢复；用户已手动改则 version 不匹配，放弃撤销。各域无统一接口——域自己实现 snapshot/restore，注册表只声明契约；未实现则不能标 `reversible: true`。`reversible: false` **不能进预授权**，必须 HITL。

**二、默认值：领域默认值 + 批量审核**
