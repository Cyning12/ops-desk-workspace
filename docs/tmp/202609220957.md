一、可撤销：撤销的是状态，不是操作
你这个问题问得很准。“撤销”如果只是发一条反向指令，那它和“再执行一次相反的操作”没区别，谈不上安全。真正的撤销，是针对状态的。

状态版本化
空调温度从 22°C 被 Agent 调到 20°C。撤销不是“发一条升温到 22°C 的指令”，而是：
操作前：记录状态快照 (temperature=22, version=v1)
操作后：温度变为 20，version=v2
撤销窗口内：如果用户没动，执行恢复 → 温度回到 22，version=v3
撤销窗口外 或 用户已手动修改：撤销失效

关键在 version。如果用户在 Agent 操作后手动把温度调到了 24°C（version=v3），那么 Agent 的撤销逻辑检查到“当前 version ≠ 我操作后的 version”，就放弃撤销，而不是强行把温度调回 22。
车控域有没有统一的状态快照接口？
没有。 这是现实。空调、座椅、车窗、娱乐，各域的软件栈不一样，没有统一的 get_state() / set_state() / snapshot() 接口。

所以“可撤销”的落地方式，是在能力声明里定义：
每个域自己实现 snapshot/restore，注册表只声明契约。 如果某个域没有实现 snapshot 接口，它的能力就不能声明 reversible: true，只能声明 reversible: false，那就必须走 HITL。

“可撤销性”应该和 side_effect、risk_level 并列吗？
应该。而且它应该是预授权模型的准入条件。
规则：reversible: false 的能力，不能进入预授权范围，必须走 HITL。

因为预授权的本质是“用户提前同意，Agent 自动执行，用户事后可撤销”。如果不可撤销，那“事后可撤销”就不成立，预授权就变成了“用户提前同意，Agent 自动执行，用户事后只能接受”——这不是预授权，这是空白支票。

所以：可撤销性是预授权的必要条件，不是可选项。

一、可撤销的时序问题
你说得对，空调调温不是瞬时的。t=0 发指令，t=2 用户撤销，但压缩机已经启动，风门已经调整，物理系统正处于中间状态。这时候发一条“调回 22°C”的反向指令，能不能正确执行？

答案是：能，但语义不是“回滚”，而是“收敛到新目标”。

空调控制系统本身就是一个状态机。它的目标温度是一个设定值，物理系统会向这个设定值收敛。当 Agent 把目标从 22°C 改成 20°C，系统开始向 20°C 收敛。撤销时，Agent 把目标改回 22°C，系统会放弃向 20°C 收敛，转而向 22°C 收敛。物理系统可能正处于 21°C 的中间状态，但它会继续向 22°C 走。

所以，对于“目标值型”操作（温度、音量、座椅位置），撤销就是改目标值，物理系统自然收敛。 不需要“停止+反向”两个动作。

但对于“过程型”操作（打开天窗、打开车窗），撤销就复杂了。天窗打开到一半，用户撤销，需要“停止+反向”两个动作。这时候：

如果天窗电机支持“停止”指令，那就先停止，再反向。

如果天窗电机不支持“停止”，那就只能等它开完，再关回去。

所以，可撤销能力必须声明“执行类型”：
规则：execution_type: process 且 requires_stop_support: true 的能力，如果 ECU 不支持停止指令，就不能标记 reversible: true，必须走 HITL。

这就是你说的“指令生效时间 < 撤销窗口”的工程化表达。不是所有可撤销能力都必须瞬时生效，但必须能在撤销窗口内被有效中断或改向。

revoke_window：用户发起撤销的时间窗口。超过 5 秒，用户不能再点撤销。

如果 max_reversal_latency > 30s：Gateway 拒绝这个能力标记 reversible: true，必须走 HITL。因为恢复时间太长，用户体验不可接受。

我踩过的坑： 在百果园做退款撤销时，遇到过一模一样的问题。退款不是瞬时的，用户点撤销时，退款可能已经在银行处理中。我们的方案是：

撤销受理：立即标记“撤销受理中”，用户看到“正在处理”。

异步恢复：退款完成后，发起反向操作（追回退款）。

超时告警：如果 30 秒内没完成恢复，告警人工介入。

状态漂移检测：如果用户在此期间又发起了新的退款，放弃撤销，避免状态打架。

关键教训：撤销不是“回滚”，是“向新目标收敛”。 用户点撤销时，系统要立即响应“我收到了”，而不是等物理系统完全恢复才告诉用户“撤销成功”。用户体验上，“正在恢复”比“撤销失败”好得多。

二、行为基线监控：自动降级立即生效，但区分硬降级和软降级
你说得对，“第一次异常调用”本身就是一个危险信号，检测到异常到完成降级之间，确实有响应延迟。

我的方案是：自动降级立即生效，但区分硬降级和软降级。

降级类型	触发条件	生效方式	误报处理
软降级	疑似异常（频率偏高、参数偏移）	立即生效，限流或只读	自动恢复（5分钟后）
硬降级	明确攻击（UNKNOWN_ACTION、契约违反）	立即生效，完全封禁	需人工确认恢复
软降级：高德正常更新了一个新功能，调用了一个你注册表里没有的新接口。系统检测到 UNKNOWN_ACTION，但因为是第一次，触发软降级：该能力变为只读，限流 10 次/分钟。同时告警，但不完全封禁。高德那边发现“写接口调不通了”，可以来申诉。

硬降级：高德的 Agent 被注入，开始尝试调用写接口，且频率异常高、参数异常。系统检测到多个异常信号叠加，触发硬降级：完全封禁该能力，直到人工确认。

第二，写操作和高危不能靠“配置放行”，得有确定性的刹车。我的做法是三件事同时成立：注册表加载期就强制，写能力必须声明幂等键，并且必须明确安全策略——是必须人工确认，还是允许在预授权范围内自动执行但必须可撤销、可审计；不声明默认按“必须人工确认”处理，坏能力根本进不了目录。执行前落闸，默认不自动放行，必须走显式授权路径：高危默认走人工确认，写操作默认需要显式授权，放行键只有宿主能给，模型写在 plan 里不算。失控时有一键熄火，按能力紧急停用，加上每个会话的调用数和写操作数上限。这三道都不在提示词里——凡是写进提示词的安全约束，都不算闸。

这套目前是进程内注册表，跨进程和车控这个场景还没验证。不过我觉得它的治理思路对多 Agent 管理有可迁移性。具体怎么适配，得看贵司的业务落点。所以我想先听听贵司期待的方向，再判断哪些能复用、哪些要重做。

4. 可撤销 + 主动服务（北汽座舱重点）
可撤销：撤销的是状态，不是操作
状态版本化： 操作前 snapshot（温度=22, v1）；操作后 v2；撤销窗口内恢复 → v3；用户手动改过 → version 不匹配，放弃撤销。

目标值型操作（温度、音量、座椅位置）：撤销 = 改目标值，物理系统自然收敛。

过程型操作（天窗、车窗）：可能需要“停止+反向”；ECU 不支持停止 → 不能标 reversible: true，必须 HITL。

动态配置： 区分“撤销受理”和“撤销完成”；max_reversal_latency 字段存在；超过 30s 才恢复 → 拒绝标 reversible。

金句： 撤销不是回滚，是向新目标收敛。

主动服务：预授权 + 可撤销
用户提前开启“主动服务”，选择允许类型：✅疲劳调温 ✅提神音乐 ❌开车窗 ❌调座椅。

低风险写操作：自动执行 + 通知 + 5秒可撤销。

超出预授权：必须确认。

原则修正： 高风险写操作必须 HITL；低风险写操作可自动执行，但必须可撤销、可审计。

可撤销性是预授权准入条件： reversible: false 不能进预授权，必须 HITL。

新增能力： 意图来源从显式指令 → 多模态信号推断；预授权模型；可撤销窗口；通知机制。

复用： 令牌、能力注册表、风险分级、审计日志、Gateway 强制点。

追问1：HITL_EXEMPT 和 PRE_AUTHORIZED 有什么区别？

HITL_EXEMPT 是“这个操作永远不需要人工确认”，比如只读查询。PRE_AUTHORIZED 是“在用户预授权范围内可以自动执行，但超出范围还是要确认”，比如调低空调温度。两者都需要安全域审核，但 HITL_EXEMPT 的门槛更高，因为它等于永久放弃人工确认。

追问2：加载期强制，如果开发者就是不肯声明怎么办？

不声明默认 HITL_REQUIRED，能力能加载，但每次调用都会弹人工确认。开发者如果觉得“太烦”，他会主动来补声明。不是“不写就不让加载”，是“不写就默认最严格”。想放宽，必须显式声明并审批。

追问3：执行前落闸，放行键只有宿主能给，那宿主是谁？

宿主是 Agent Host，也就是编排层的运行时。它不信任模型输出的 plan，只信任自己构造的 ctx。模型可以在 plan 里写“我已确认”，但 Host 不会读这个字段。放行键是 Host 在运行时注入的，来源只有两个：进程环境变量，或者 Host 自己构造的 ctx["_host_policy"]。
