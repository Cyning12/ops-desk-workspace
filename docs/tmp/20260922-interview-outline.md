## 1. 完整开场白

面试官好，我是刘新宁，11 年研发，离职前一年在百果园主要做 **Agent 应用与工程效能负责人**。

我根据猎头信息和贵司公开资料，判断这次聊的重点会落在多 Agent 的治理与可靠性上，而不只是编排出一个能跑的 Agent。如果和你们实际关注的有偏差，请随时打断我。

第一，多 Agent 真正难的不是编排，而是“谁有权调什么”。编排框架现在很多，一周能出演示；但能力一多、一有写等高危操作，先崩的往往是能力授权，不是编排。我对此落地的能力管理模块方案：全量能力以注册表登记，登记表内功能信息至少包含静态功能声明、参数 schema、执行语义、安全属性、运行时状态。实际可用能力表由策略模块动态裁剪，裁剪这一步是纯代码逻辑，不调大模型。模型能决定的是“在名单里点哪个”和“参数长什么样”，决定不了名单里有什么。网关做权限校验和精确能力分发。

第二，高危不能靠「配置放行」，得有确定性的刹车。我的做法是三道递进的防线，按调用生命周期分：

**第一道，能力被 Agent 获取前——准入与裁剪。** 

加载期强制：写能力必须声明幂等键，必须明确安全策略——是必须人工确认，还是允许在预授权范围内自动执行；不声明默认按“必须人工确认”处理；想放宽，必须安全域审批并写明理由；校验不过，能力根本进不了目录。

可见集裁剪：策略 Builder 按身份维和场景维，从全量注册表裁出当前会话可见集；模型只能在可见集范围内规划，决定不了名单里有什么。这一步解决的是“坏能力进不来，且模型看不到不该看的”。

**第二道，执行前——运行时落闸。** 每次调用前，网关默认不自动放行，必须走显式授权路径。高危默认走人工确认；写操作默认需要显式授权——要么运行时 HITL 通过，要么在用户预授权范围内。放行键只有宿主能给，模型写在 plan 里的“已确认”不算数。这一步解决的是“模型不能自己给自己发通行证”。

**第三道，执行失败或失控时——兜底熄火。** 按能力支持紧急停用；每个会话有调用数上限和写操作数上限；下游熔断优先于配额扣减；必要时降级到只读或规则引擎。这一步解决的是“出了事能刹住，不会无限扩散”。

这套目前是进程内注册表，跨进程场景没有在企业内落地。不过我觉得它的治理思路对多 Agent 管理有可迁移性。具体怎么适配，还是需要根据实际情况适配。

另外对于 AI coding 提效，落地方案是基于 SDD，我离职后也一直在更新迭代，若对此也感兴趣可以提出我再详细说说。

所以想先确认一件事：这个多 Agent 平台主要服务范围是什么？车内用户，还是内部员工？ 

如果是车内用户，我理解核心挑战是多模态感知输入下的意图收敛和主动服务的安全边界；如果是内部员工，核心挑战可能更偏向跨系统 API 的安全编排。你们目前更侧重哪个方向？



先把需求写成可签收的 SPEC 与可验收的 task，再配技术图谱把系统结构、流程边界钉成单一事实来源。它要解决的是 AI 编码常见失控——范围漂移、凭聊天瞎改、实现与架构脱节。强调的 HITL，关键节点无签收强制停止任务。

这个纪律包在我离开团队后也在一直更新中。库名已经不是简历中的名字了，现在是 SpecWave。

## 2. 技术主线：编排侧三道 + 执行侧六道



### 编排侧三道（可见性真正起作用的地方）

1. **策略 Builder**（不调大模型）：路由候选 id ∩ 注册表可见集 → allowed / stripped；剔除写 span。宁可无工具，也不全开。
2. **拼 prompt 前算可见集**：场景维（kind / 风险 / 写副作用 / tags）× 身份维（部门 / 角色 / 项目 / 密级）。主体从 `ctx` 构造；模型 payload 里的 departments / roles **一律无效**。
3. **模型出 plan 后立刻校验**：不可见 id → **整份 plan 非法**（不是拖到 Gateway 才拒）；子任务失败，主 Agent 下一轮重规划。



### 执行侧六道（Gateway，顺序有意）

查表 → 是否启用 → Policy 硬闸 → 下游熔断 → 熄火开关与会话配额 → 参数 schema

- 熔断优先于配额（下游挂了还扣配额是浪费）  
- 参数校验放最后（前面已拒，不让模型以为「改改参数就能过」）



### Policy 硬闸四件事

危险程度 → 副作用 → 危险形态 → 输入完整性

- **写判断挂在副作用上**，不挂在执行等级上（防 `medium + write` 漏放）  
- 放行来源只有两个：进程环境变量，或宿主构造的 `ctx["_host_policy"]`

## 3. 关键追问速记（开场后最可能问）


| 追问                   | 回答核心                                        | 金句                       |
| -------------------- | ------------------------------------------- | ------------------------ |
| 不可见 id 怎么办？          | 编排层判 plan 非法；Gateway 再查表作纵深                 | 可见性在编排侧，不在 Gateway       |
| 编排放行后能力被紧急停用？        | 共用注册表；错误回主 Agent；state 裁掉失败 id 再规划          | 内部精确错误码，对外可合并措辞          |
| 部分成功？（天窗坏、音乐好）       | 看任务依赖：并行无依赖可只执行一个；有依赖则整条断                   | —                        |
| 危险形态？开窗 / 解锁？        | 按失败危害定；开窗 HITL；解锁默认拒                        | 决策权交人 vs 默认拒             |
| 输入完整性 / 值域？          | 约束在注册表 YAML；Gateway 读；封闭世界拒未声明参数            | 约束不在提示词里                 |
| 令牌泄露 / 提权？           | 能力集签在令牌里；子 Agent 无私钥；白名单入口 + 参数执行前          | 损失边界 = 能力集×TTL×一次性×参数×主体 |
| 令牌签发？                | 本身高危，须 HITL；子 Agent 身份令牌；主 Agent 短 TTL 会话令牌 | —                        |
| 主动服务怎么不破 HITL？       | 预授权 + 可撤销；高风险 HITL；低风险可自动但须可撤销可审计           | 不是无授权，是决策权下放             |
| 可撤销怎么落地？             | 撤销的是状态；version 防打架；目标值型改目标；过程型需能停           | 撤销不是回滚，是向新目标收敛           |
| `reversible: false`？ | 不能进预授权，必须 HITL                              | 可撤销是预授权准入条件              |
| 默认全 high+HITL 体验崩？   | 领域默认值 + 批量审核；不写=继承领域默认                      | 不写就默认严格，想放宽要审批           |
| 第三方能力（高德等）？          | 适配映射；只信动作类型/可撤销性，不信对方 risk                  | 第三方说什么不重要，规则说了算          |
| 跨进程 / 1+N？           | 现状进程内；扩展可讲 A2G2A；垂域挂了看「存在但不可用」              | 边界已开场交代                  |
| 三月出原型？               | 先可见性再可控性；MVP=注册表+审计+核心高危硬拦                  | 领导要的是看到治理能力              |
| 首月只做一件事？             | 先聊一圈，出路线图，不先写代码                             | —                        |

## 4. 主动服务 + 可撤销（座舱重点）

**预授权模型**

- 用户设置勾选允许类型（如疲劳调温 ✅ / 开车窗 ❌）  
- 范围内低风险写：自动执行 + 通知 + 可撤销  
- 超出范围：必须确认

**可撤销要点**

- 状态版本化；用户手改过 → version 不匹配 → 放弃撤销  
- 区分「撤销受理」与「撤销完成」（用户看到「正在恢复」）  
- `max_reversal_latency` 过长 → 拒绝标 reversible

## 5. 性能 / DevEx / 落地（后半场）


| 主题    | 要点                                                    |
| ----- | ----------------------------------------------------- |
| 性能    | 策略链路不是瓶颈，LLM 才是；「打开车窗」P99 约 1.5–2s；热加载+内存缓存+预编译+位图可见集 |
| DevEx | 脚手架 → 默认严格 → 分级治理；HITL_EXEMPT 须安全域审批                  |
| 仲裁    | 安全域定「什么情况下不能做什么」；业务方定怎么实现                             |
| 监控    | 行为基线 + 契约测试；软降级（限流/只读可恢复）vs 硬降级（封禁需人工）                |
| 落地    | 最小可用治理层 → 标杆 → 自愿接入；未治理跨域默认 high+HITL                 |
| 无强制权  | 仍可推：价值吸引 + 未接入自然降级；一把手是最后手段                           |

## 6. SpecWave / AICoding（1 分钟版）

1. **问题**：范围漂移、凭聊天瞎改、实现与架构脱节
2. **做法**：可签收 SPEC + 可验收 task + 技术图谱（单一事实来源）
3. **闸**：关键节点无签收 → 强制停任务（过程 HITL，不在提示词）
4. **现状**：离开后仍更新；现名 **SpecWave**（简历旧名主动对齐一句）
5. **和治理的关系**：都是把约束从「聊天/提示词」挪到「可强制的签收与门禁」

## 8. 金句库

- 多 Agent 真正难的不是编排，是「谁有权调什么」  
- 模型只能在名单里点，决定不了名单里有什么  
- 放行键只有宿主能给；plan 里的「已确认」不算  
- 坏能力从源头进不来 / 模型不能自己发通行证 / 出事能刹住  
- 主动服务 = 预授权 + 可撤销，不是无授权  
- 我更接受「一次被拒绝的请求」  
- 撤销不是回滚，是向新目标收敛  
- 第三方说什么不重要，你的规则说了算  
- 先做可见性，再做可控性  
- 领导要的不是全量治理，是看到治理的能力  
- （可选补强）凡是写进提示词的安全约束，都不算闸
